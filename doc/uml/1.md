## The Step-by-Step Documentation Workflow

The workflow is **requirements → structure → behavior → architecture → living documentation**. It is iterative, not a one-time waterfall. You start with the highest-risk or highest-value parts of the system and expand only as needed.

| Phase | Core Question | Main Diagram | Text Companion | Done When |
|---|---|---|---|---|
| 0. Scope | What must be documented? | — | Documentation plan | Audience, critical flows, and diagram budget are agreed |
| 1. User goals | Who uses the system, and what do they want? | Use Case diagram | Use case specifications | Actors, system boundary, and critical use cases are clear |
| 2. Static structure | What are the main concepts and rules? | Class diagram | Glossary / data dictionary | Core classes, relationships, and multiplicities are defined |
| 3. Dynamic behavior | How do critical flows actually work? | Sequence / Activity diagrams | Scenario descriptions | Risky flows have ordered steps and alternatives documented |
| 4. Architecture | How do larger parts and infrastructure fit together? | Component / Deployment diagrams | Interface and environment notes | Boundaries, dependencies, and deployment nodes are visible |
| 5. Assembly | Can someone navigate and trust the docs? | — | Documentation package + traceability matrix | Diagrams and text are linked and reviewed |
| 6. Maintenance | How do docs stay alive? | — | Versioned diagrams-as-code + change log | Docs are updated with requirement/design changes |

---

## Step 0 — Set the Documentation Scope

Before drawing anything, decide **what not to document**.

**Do:**
- Identify the audience: developers, testers, product owners, DevOps, new hires.
- List the **3–7 critical flows** that carry the most risk or business value.
- Choose a small diagram set. For most projects: **Use Case + Class + Sequence + Component** is enough.
- Agree on where docs live: repository, wiki, or both.

**Output:** a one-page documentation plan:
- Audience
- Critical flows
- Diagram types to produce
- Tooling
- Review cadence

**Avoid:** trying to model the entire system before writing any code.

---

## Step 1 — Capture User Goals with a Use Case Diagram

**Purpose:** Define scope and answer: *Who interacts with the system, and what goals do they have?*

**Steps:**
1. Identify **actors**: humans, external systems, scheduled jobs.
2. List their high-level **use cases** — goals, not UI steps.
3. Draw the **system boundary**.
4. Add only the most important actor-to-use-case associations.
5. For each critical use case, write a short **use case specification**:
    - Preconditions
    - Main success flow
    - Key alternative/exception flows
    - Postconditions
    - Business rules

**Done when:**
- Every critical actor has at least one use case.
- Every critical use case has a text specification.
- Scope boundaries are explicit — including what is out of scope.

**Common mistake:** turning the use case diagram into a flowchart. Keep it high-level.

---

## Step 2 — Model the Static Structure with a Class Diagram

**Purpose:** Show the core concepts, their data, behavior, and rules.

**Steps:**
1. Extract nouns from use cases and domain language: e.g., `User`, `Task`, `Project`, `Comment`.
2. Keep only classes needed for the current scope.
3. Add essential **attributes** and **operations** — not every getter/setter.
4. Define relationships:
    - Association
    - Inheritance
    - Composition / aggregation
5. Add **multiplicity** early: `1 Project has * Tasks`, `1 Task has 0..* Comments`.
6. Create or update a **glossary** defining each core term.
7. Review multiplicities and business rules with a domain expert.

**Done when:**
- Core business rules are visible in relationships and multiplicities.
- Each class has a one-line responsibility.
- Ambiguous terms are defined in the glossary.

**Common mistake:** drawing a database schema instead of a domain model. A class diagram is about concepts and behavior, not only tables.

---

## Step 3 — Model Dynamic Behavior with Sequence and Activity Diagrams

**Purpose:** Show how critical scenarios actually execute over time.

**Use a Sequence Diagram when:**
- You need to show message order between objects/services.
- You are designing or debugging an interaction: login, payment, password reset, order submission.
- You need to expose missing steps such as timeout, retry, or authorization checks.

**Use an Activity Diagram when:**
- The flow has decisions, parallel work, or multiple actors.
- You are documenting a business process rather than object interaction.

**Steps:**
1. Pick one critical use case or scenario.
2. Draw the **main success path** first.
3. Add the most important **alternative and error paths**.
4. Name messages clearly — avoid vague labels like “process.”
5. Link the diagram back to the use case ID.
6. Repeat only for high-risk flows.

**Done when:**
- Each critical use case has either a sequence diagram or an activity diagram.
- Error and alternative paths are represented where they matter.
- The diagram can be traced to a use case and to the classes/components involved.

**Common mistake:** documenting every trivial flow. Focus on risk, complexity, and shared understanding.

---

## Step 4 — Document Architecture with Component and Deployment Diagrams

**Purpose:** Zoom out from code and show how larger pieces and infrastructure fit together.

**Component diagram steps:**
1. Group the system into logical, replaceable components: e.g., `Auth Service`, `Task Service`, `Notification Module`.
2. Show **provided and required interfaces**.
3. Show dependencies between components.
4. Link components to repositories, modules, or teams.

**Deployment diagram steps:**
1. Identify execution environments: browser, app server, database, queue, cloud services.
2. Show which components deploy to which nodes.
3. Add protocols or communication paths where useful: HTTPS, SQL, AMQP.
4. Note environments: dev, staging, production.

**Done when:**
- Major boundaries and dependencies are explicit.
- External systems and infrastructure are visible.
- New team members can understand the system’s shape without reading all the code.

**Common mistake:** drawing a component diagram that is just a class diagram with bigger boxes. Focus on boundaries and interfaces.

---

## Step 5 — Assemble the Documentation Package

A diagram alone is a sketch. Pair it with concise text and make it navigable.

**Suggested structure:**

```text
/docs
  README.md                 # How to navigate the docs
  glossary.md               # Core terms and definitions
  use-cases/
    UC-001-login.md
    UC-002-create-task.md
  diagrams/
    use-case.puml
    domain-model.puml
    sequence-login.puml
    component-architecture.puml
  architecture/
    decisions/              # ADRs
    deployment.md
  traceability.md           # Use case → class → sequence → component
```

**Add a traceability matrix:**

| Use Case | Classes | Sequence/Activity | Component |
|---|---|---|---|
| UC-001 Login | User, Session | seq-login | Auth Service |
| UC-002 Create Task | User, Task, Project | seq-create-task | Task Service |

**Done when:**
- A reader can go from a use case to the relevant diagram and code area.
- Diagrams have titles, dates/versions, and short descriptions.
- Decisions are recorded as ADRs where architecture choices matter.

---

## Step 6 — Review, Baseline, and Version

- Review diagrams with both technical and business stakeholders.
- Store diagrams as **text-based source** where possible — e.g., PlantUML, Mermaid — so they live in Git.
- Treat documentation changes like code changes: pull request, review, merge.
- Tag or baseline docs for major releases.

**Done when:**
- Docs are version-controlled.
- Review comments are resolved.
- The current baseline matches the released system.

---

## Step 7 — Maintain as Living Documentation

Update documentation when:
- A requirement changes.
- A critical flow or interface changes.
- An architecture decision is made.
- An incident reveals a missing or wrong assumption.
- A release changes deployment topology.

**Practical rule:** update the smallest relevant diagram and text, not the whole documentation set. Keep diagrams small and focused.

---

## A Quick Example: “Password Reset”

1. **Use Case:** Actor `User` has use case `Reset Password`. Write a spec with main flow and expired-token alternative.
2. **Class Diagram:** Add `User`, `PasswordResetToken`, `Session`; define multiplicity and expiry rule.
3. **Sequence Diagram:** Show `User → UI → Auth Service → Email Service → Database`, including token validation and expiry.
4. **Component Diagram:** Show `Auth Service` depends on `Email Service` and `User Database`.
5. **Traceability:** UC-003 → `User`, `PasswordResetToken` → `seq-password-reset` → `Auth Service`.
6. **Maintain:** If token expiry changes from 15 to 30 minutes, update the use case spec, sequence diagram note, and class constraint.

---

## Final Checklist

- [ ] Documentation scope and audience are explicit.
- [ ] Critical actors and use cases are documented.
- [ ] Critical use cases have text specifications.
- [ ] Core domain classes and multiplicities are defined.
- [ ] High-risk flows have sequence or activity diagrams.
- [ ] Components, interfaces, and deployment nodes are visible.
- [ ] Glossary and traceability matrix exist.
- [ ] Diagrams are versioned and reviewed.
- [ ] Documentation has an owner and update triggers.

The key principle: **document decisions and risky boundaries, not everything.** The workflow above gives you enough structure to be useful without turning documentation into a burden.
