## ۲. بهترین شیوه‌ها (Best Practices)

### ۲.۱. اصل «یک ایده در هر بخش»

هر سرفصل باید یک ایده را پوشش دهد. اگر عنوان «نصب و پیکربندی و عیب‌یابی» داری، آن را به سه سرفصل جدا بشکن.

### ۲.۲. اصل «مخاطب را بشناس»

- **مخاطب مبتدی:** قدم‌به‌قدم، توضیح هر دستور، پیش‌نیاز صریح.
- **مخاطب حرفه‌ای:** مختصر، مستقیم، بدون توضیح واضحات.

یک سند نمی‌تواند همزمان عالی برای هر دو باشد. اگر لازم است، **دو سند جدا** بنویس: `QUICKSTART.md` برای مبتدی و `REFERENCE.md` برای حرفه‌ای.

### ۲.۳. اصل «مثال واقعی»

هیچ‌چیز بدتر از `{{placeholder}}` و `مقدار-اینجا` نیست. مثال واقعی، قابل‌اجرا بده:

```bash
# ❌ بد
your-command --arg=value

# ✅ خوب
npm run build -- --production
```

### ۲.۴. اصل «خوانایی فایل خام»

Markdown هم در پیش‌نمایش خوانده می‌شود، هم در فایل خام (در Git diff، در ویرایشگر ساده، در terminal). فایل خام هم باید خوانا باشد:

- جدول‌ها را در کد هم‌تراز بنویس.
- بین بلوک‌ها و پاراگراف‌ها خط خالی بگذار.
- لینک‌های طولانی را با **لینک ارجاعی** جدا کن.
- سرفصل‌های بلند را نشکن.

### ۲.۵. اصل «لینک، نه تکرار»

اگر مفهومی در جای دیگری توضیح داده شده، **لینک بده**، دوباره توضیح نده. تکرار باعث می‌شود با هر تغییر، چند جا باید اصلاح شود.

### ۲.۶. اصل «تاریخ و نسخه»

هر سند فنی را با **تاریخ آخرین به‌روزرسانی** (در Front Matter) همراه کن. سند بدون تاریخ، بی‌اعتبار است.

### ۲.۷. اصل «کد قابل کپی»

بلوک‌های کد باید **قابل کپی مستقیم** باشند. توضیحات را داخل کد نگذار (مگر به‌صورت کامنت)، بیرون از کد توضیح بده.

### ۲.۸. اصل «سازگاری اصطلاحات»

یک مفهوم = یک اصطلاح. اگر یک جا «کاربر» گفتی، جای دیگر «یوزر» نگو. اگر «وظیفه» گفتی، «تسک» نگو. یک **واژه‌نامه** در پروژه داشته باش.

### ۲.۹. اصل «حساس به ابزار»

قبل از استفاده از یک ویژگی، مطمئن شو **در ابزار مقصد** (GitHub؟ Obsidian؟ VS Code؟) رندر می‌شود. جدول سازگاری جلسه ۳ را یادت هست.

## ۳. اشتباهات رایج (و راه‌حل)

### اشتباه ۱: پرش در سلسله‌مراتب عنوان‌ها

```markdown
# عنوان
### زیربخش بدون ##
```

✅ راه‌حل: همیشه پله‌به‌پله. `#` → `##` → `###`.

### اشتباه ۲: بلوک کد بدون زبان

````markdown
```
npm install
```
````

✅ راه‌حل: زبان را بنویس: ` ```bash `.

### اشتباه ۳: فراموش کردن خط خالی اطراف بلوک‌ها

````markdown
متن قبل
```bash
npm install
```
متن بعد
````

در بعضی پارسرها بلوک کد به‌درستی بسته نمی‌شود. ✅ راه‌حل: **قبل و بعد** از بلوک کد خط خالی بگذار.

### اشتباه ۴: لینک نسبی اشتباه

```markdown
[نصب](install.md)   ← اگر سند در پوشه دیگری است، این شکسته می‌شود
```

✅ راه‌حل: مسیر را نسبت به **محل خود فایل** حساب کن: `[نصب](setup/install.md)` یا `[نصب](../setup/install.md)`.

### اشتباه ۵: متن جایگزین تصویر خالی یا بی‌معنا

```markdown
![](image.png)
![image](image.png)
```

✅ راه‌حل: متن جایگزین **توصیفی** بده: `![نمودار معماری سیستم](architecture.png)`.

### اشتباه ۶: فاصله در نام فایل

```text
راهنمای نصب.md   ❌
```

URL آن به `%20` تبدیل می‌شود و در بعضی ابزارها می‌شکند. ✅ راه‌حل: `INSTALLATION.md` یا `installation-guide.md`.

### اشتباه ۷: غفلت از RTL در جدول

جدول فارسی در GitHub چپ‌چین رندر می‌شود و ستون‌ها جابه‌جا به‌نظر می‌رسند.

✅ راه‌حل: برای جدول‌های حساس، از HTML با `dir="rtl"` استفاده کن.

### اشتباه ۸: پانویس و Alerts در ابزارهای ناسازگار

پانویس در GitHub خوب است، در بعضی ابزارها رندر نمی‌شود. ✅ راه‌حل: جدول سازگاری جلسه ۳ را چک کن و برای اسناد چند-ابزاره از سینتکس محافظه‌کارانه استفاده کن.

### اشتباه ۹: سند بدون تاریخ و نسخه

سندی که نمی‌دانی مال کِی است، بی‌ارزش است. ✅ راه‌حل: در Front Matter، تاریخ آخرین ویرایش را بنویس.

### اشتباه ۱۰: تکرار به‌جای لینک

توضیح یک مفهوم در سه فایل مختلف. ✅ راه‌حل: یک منبع حقیقت (single source of truth) + لینک.

## ۴. چک‌لیست نهایی (قبل از هر commit)

این چک‌لیست را کنار دستت داشته باش. هر سند Markdown فارسی که می‌نویسی، این‌ها را چک کن:

### ساختار
- [ ] فایل فقط **یک** `#` دارد (عنوان سند)
- [ ] سلسله‌مراتب عنوان‌ها پله‌به‌پله است (بدون پرش)
- [ ] هر سرفصل یک ایده را پوشش می‌دهد
- [ ] فهرست مطالب در اسناد بلند وجود دارد

### Front Matter
- [ ] Front Matter در خط اول فایل است
- [ ] `title`، `author`، `date` پر شده
- [ ] YAML معتبر است (فاصله، نه Tab)

### محتوا
- [ ] هر بلوک کد **زبان** دارد
- [ ] قبل و بعد از هر بلوک کد **خط خالی** هست
- [ ] بلوک‌های کد **قابل کپی** هستند
- [ ] مثال‌ها **واقعی** و قابل اجرا هستند
- [ ] بخش عیب‌یابی وجود دارد (برای اسناد فنی)
- [ ] اصطلاحات یکدست هستند (یک مفهوم = یک واژه)

### لینک‌ها و تصاویر
- [ ] همه لینک‌ها **مسیر نسبی** دارند
- [ ] لینک‌های لنگر (مثل `#نصب`) به سرفصل موجود اشاره می‌کنند
- [ ] همه تصاویر **متن جایگزین** دارند
- [ ] نام فایل‌ها **بدون فاصله** است

### RTL (برای اسناد فارسی)
- [ ] پاراگراف‌های فارسی داخل `<div dir="rtl">` هستند
- [ ] جدول‌های حساس با HTML و `dir="rtl"` نوشته شده‌اند
- [ ] اصطلاحات انگلیسی داخل `` `backtick` `` هستند
- [ ] پیش‌نمایش سند را در **ابزار مقصد** چک کرده‌ای

### نسخه و تاریخ
- [ ] تاریخ آخرین ویرایش ثبت شده
- [ ] نسخه سند (در صورت لزوم) مشخص است

### سازگاری
- [ ] فقط از ویژگی‌هایی استفاده کرده‌ای که در **ابزار مقصد** کار می‌کنند
- [ ] جدول سازگاری را برای پانویس، Alerts و چک‌لیست چک کرده‌ای

## ۵. تمرین نهایی: پروژه واقعی

یک پروژه که الان داری (یا یک پروژه فرضی) انتخاب کن و **همه** مستنداتش را بنویس:

1. `README.md` با Front Matter، سه Badge و لینک به `docs/`
2. `docs/setup/QUICKSTART.md` با فهرست، جدول پیش‌نیاز و دستورات اجرا
3. `docs/setup/INSTALLATION.md` با بخش عیب‌یابی و دو `<details>`
4. `docs/reference/API.md` با مثال‌های JSON و جدول کد وضعیت
5. همه پاراگراف‌های فارسی داخل `<div dir="rtl">`
6. همه چک‌لیست نهایی را روی هر سند اعمال کن

اگر این پروژه را کامل کنی، **هر سند Markdown دیگری** را می‌توانی با اطمینان بنویسی.

### آخرین توصیه

Markdown یک **ابزار** است، نه هدف. بهترین سند آن است که خواننده را از نقطه A به نقطه B برساند. اگر یک ویژگی Markdown به این هدف کمک نمی‌کند، از آن استفاده نکن. سادگی، بزرگ‌ترین مزیت Markdown است — آن را از دست نده.
