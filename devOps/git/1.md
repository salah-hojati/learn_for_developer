You've built a solid foundation with the core Git workflow and the basics of collaborating on GitHub and GitLab. The next step is to move from "using" Git to "mastering" it—handling the inevitable tricky situations and adopting the workflows that professional teams use.

Here are the key intermediate topics that will take you to the next level.

### ⚔️ 1. Resolving Merge Conflicts

A merge conflict happens when Git cannot automatically reconcile changes made to the same part of a file on two different branches. This is a normal part of collaboration, not an error.

**How to resolve one:**
1.  **Identify the conflicted files:** Run `git status`. Git will list the files under "Unmerged paths".
2.  **Open the file(s):** You will see conflict markers: `<<<<<<< HEAD` (your changes), `=======` (the divider), and `>>>>>>> branch-name` (the incoming changes). You also have a `|||||||` marker showing the common ancestor for a three-way merge.
3.  **Edit the file:** Manually edit the file to keep the version of the code you want, removing the conflict markers.
4.  **Stage and commit:** Once resolved, run `git add <filename>`, then `git commit` (or `git merge --continue`) to complete the merge.

**Escape hatch:** If you get overwhelmed, you can always abort the merge and return to the state before you started with `git merge --abort`.

### ⏪ 2. Undoing Changes Safely

Git's "undo" system is not like a word processor. You must choose the right tool for the situation, based on whether the change is local or already shared.

| Command | What It Does | When to Use It |
| :--- | :--- | :--- |
| `git restore <file>` | Discards changes in your working directory (the file returns to its last committed state). | You want to throw away uncommitted local edits. |
| `git reset --soft HEAD~1` | Undoes the last commit but **keeps** your changes staged. | You committed too early and want to add more files to that commit. |
| `git reset --hard HEAD~1` | **Destructive.** Undoes the last commit and **discards all associated changes** permanently. | You want to completely erase a local, unpushed commit. |
| `git revert <commit-hash>` | Creates a **new commit** that undoes the changes of a previous commit. | You need to undo a commit that has **already been pushed** to a shared branch. This is the safe, non-destructive option for public history. |

**Golden rule:** Use `git reset` only on local, unpushed commits. Use `git revert` for anything that is already shared with others.

### 📝 3. Using a `.gitignore` File

A `.gitignore` file tells Git which files and folders to never track. This is essential for keeping your repository clean and secure. You should ignore things like:
*   **Dependencies:** e.g., `node_modules/` or `vendor/`
*   **Build artifacts:** e.g., `dist/`, `build/`, or `*.log` files
*   **Sensitive files:** `.env` files containing secrets or API keys
*   **OS-generated files:** e.g., `.DS_Store` on macOS

**Basic syntax:** Create a file named `.gitignore` in your project's root directory.
*   `*.log` ignores all files ending in `.log`.
*   `node_modules/` (trailing slash) ignores the entire directory.
*   `!important.log` (exclamation mark) is a negation pattern that **un-ignores** a specific file.

A best practice is to use a single `.gitignore` file in your repository root, which applies to all subdirectories.

### 🔀 4. Integrating Branches: Merge vs. Rebase

When your feature branch has diverged from `main`, you have two primary ways to integrate the latest changes: `merge` and `rebase`.

*   **`git merge`**: Preserves history exactly as it happened. It creates a new "merge commit" that ties the two branch histories together. This is **safe for shared branches** because it does not rewrite history.
*   **`git rebase`**: Rewrites history to create a clean, linear sequence of commits. It takes your branch's commits and "replays" them on top of the latest `main`. This results in a cleaner history but **should be avoided on branches that others are working on**, as it changes commit hashes.

**Rule of thumb:** If you are working alone on a feature branch and want a clean history, rebase. If you are collaborating on a shared branch, merge to avoid disrupting others.

### 🧹 5. Cleaning Up History with Interactive Rebase

You can use interactive rebase to clean up your local commit history before sharing it. This is most commonly used to **squash** (combine) several small, messy commits (like "WIP" or "fix typo") into one meaningful commit.

Run `git rebase -i HEAD~<number_of_commits>`. In the editor that opens, change `pick` to `squash` (or `s`) for the commits you want to combine into the one above it. Git will then prompt you to write a new, unified commit message for the squashed commit.

### 🗺️ 6. Understanding Branching Strategies

A branching strategy is an agreed set of rules for how a team uses branches. The main options are:

*   **GitHub Flow (Recommended Default):** A simple, lightweight model. You create a short-lived feature branch from `main`, open a pull request, and merge it back. It's the sensible default for most teams.
*   **Trunk-Based Development:** An even more extreme model where developers commit to `main` (the "trunk") directly, or use very short-lived branches (≤ 1-2 days) that are merged after passing automated tests. This requires strong CI/CD and is used by high-performing teams.
*   **Git Flow:** A more complex, legacy model with long-lived `develop` and `release` branches. It is now considered best suited for projects with scheduled, versioned releases, not continuous delivery.

### 🚀 7. Automating with CI/CD (GitHub Actions & GitLab CI/CD)

Continuous Integration/Continuous Deployment (CI/CD) is the practice of automatically testing and deploying your code whenever you push changes. Both platforms have built-in CI/CD tools.

*   **GitHub Actions:** You define workflows in YAML files stored in `.github/workflows/`.
*   **GitLab CI/CD:** You define a pipeline in a single `.gitlab-ci.yml` file in your repository root.

A basic pipeline might have **stages** for `build`, `test`, and `deploy`. Here is a minimal example for GitHub Actions that runs on every push:
```yaml
name: CI
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Run a one-line script
        run: echo "Hello, CI/CD!"
```
This automation is what allows teams to merge code confidently and frequently.

### 🏷️ 8. Marking Releases with Tags

Tags are like permanent bookmarks for specific commits, commonly used to mark release versions (e.g., `v1.0.0`). There are two types:
*   **Lightweight Tags:** A simple pointer to a commit. Good for temporary markers.
*   **Annotated Tags (Recommended for Releases):** A full object in the Git database that includes the tagger's name, email, date, and a message. This is the standard for marking official releases.

Create an annotated tag with:
```bash
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0
```
