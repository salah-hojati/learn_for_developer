# مرحله ۳: Volume و Network — قلب Docker عملی 🗄️🌐

هدف این مرحله: بفهمی **دیتا چطور زنده می‌مونه** و **container ها چطور با هم حرف می‌زنن**. این دو تا مفاهیم، همون‌هایی هستن که compose هات رو زنده نگه می‌دارن.

---

## بخش اول: Volume — چرا و چطور

### ۱. مشکل: دیتا با `rm` می‌ره

بیایم یه آزمایش کنیم:
</div> 



```bash
# یه Postgres راه بنداز
docker run -d --name learn-pg1 -e POSTGRES_PASSWORD=secret postgres:15

# صبر کن تا بالا بیاد (چند ثانیه)
sleep 5

# یه جدول و دیتا بساز
docker exec -it learn-pg1 psql -U postgres -c "CREATE TABLE test(id int, name text);"
docker exec -it learn-pg1 psql -U postgres -c "INSERT INTO test VALUES (1, 'hello');"
docker exec -it learn-pg1 psql -U postgres -c "SELECT * FROM test;"

# حالا container رو حذف کن
docker rm -f learn-pg1

# یه container جدید بساز
docker run -d --name learn-pg2 -e POSTGRES_PASSWORD=secret postgres:15
sleep 5

# چک کن دیتا مونده؟
docker exec -it learn-pg2 psql -U postgres -c "SELECT * FROM test;"
# ❌ خطا: relation "test" does not exist
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**درس:** دیتا با container مرد. چون فایل‌های Postgres داخل **لایه نوشتنی** container بودن.

### ۲. ذهنیت درست: لایه‌های یک container
</div> 


```
┌─────────────────────────────┐
│  لایه نوشتنی (Read-Write)    │  ← این با rm می‌ره!
│  (همه تغییرات runtime)       │
├─────────────────────────────┤
│  لایه ۳: COPY . .            │
│  لایه ۲: RUN npm install     │  ← اینا از image میان
│  لایه ۱: FROM node           │
├─────────────────────────────┤
│  image (Read-Only)          │
└─────────────────────────────┘
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**ایده Volume:** یه تیکه از فایل‌سیستم **بیرون** این دیاگرام قرار می‌گیره و به مسیر داخل container **mount** می‌شه. با `rm` container، اون تیکه **می‌مونه**.
</div> 


```
   ┌──────────────┐
   │  Volume      │  ← بیرون، مستقل از container
   │  /var/lib/docker/volumes/...
   └──────┬───────┘
          │ mount
   ┌──────▼───────┐
   │  Container   │
   │  /var/lib/pg │
   └──────────────┘
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">

### ۳. سه نوع mount در Docker

### 🔹 A. **Named Volume** (پیشنهاد اول برای دیتا)
</div> 


```bash
docker volume create learn-pgdata
docker run -d --name learn-pg3 -e POSTGRES_PASSWORD=secret \
  -v learn-pgdata:/var/lib/postgresql/data \
  postgres:15
```

<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


- Docker خودش یه مسیر مدیریت می‌کنه (`/var/lib/docker/volumes/learn-pgdata/_data`)
- **بهترین گزینه برای دیتابیس**
- با بکاپ گرفتن Docker راحته
- cross-platform (روی Mac/Windows هم کار می‌کنه)

**تست کنیم دیتا می‌مونه:**

</div> 


```bash
sleep 5
docker exec -it learn-pg3 psql -U postgres -c "CREATE TABLE test(id int);"
docker exec -it learn-pg3 psql -U postgres -c "INSERT INTO test VALUES (1);"

# حذف container
docker rm -f learn-pg3

# container جدید با همون volume
docker run -d --name learn-pg4 -e POSTGRES_PASSWORD=secret \
  -v learn-pgdata:/var/lib/postgresql/data \
  postgres:15
sleep 5

# دیتا هست؟
docker exec -it learn-pg4 psql -U postgres -c "SELECT * FROM test;"
# ✅ دیتا موند!
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**پاک کردن:**
</div> 


```bash
docker rm -f learn-pg4
# volume هنوز هست
docker volume ls | grep learn-pgdata

# پاک کردن دستی (⚠️ دیتا می‌ره!)
docker volume rm learn-pgdata
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


---

### 🔹 B. **Bind Mount** (برای development)
</div> 


```bash
docker run -d --name learn-nginx-dev -p 8888:80 \
  -v $(pwd)/html:/usr/share/nginx/html:ro \
  nginx:alpine
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


- یه **پوشه واقعی از هاستت** رو mount می‌کنه
- برای dev عالیه: کد رو ویرایش کنی، container فوراً می‌بینه
- `:ro` = read-only (برای امنیت)

**تفاوت با Named Volume:**
| Named Volume | Bind Mount |
|--------------|------------|
| Docker مدیریت می‌کنه | خودت مدیریت می‌کنی |
| بهترین برای دیتا | بهترین برای dev |
| cross-platform | مسیر absolute می‌خواد |
| بکاپش با Docker راحته | بکاپش با cp/r sync |
| performance تو Mac/Windows بهتر | ممکنه کند باشه |

**آزمایش bind mount:**
</div> 


```bash
mkdir -p ~/docker-learn/step3/html
echo "<h1>V1</h1>" > ~/docker-learn/step3/html/index.html

docker run -d --name learn-nginx-dev -p 8888:80 \
  -v ~/docker-learn/step3/html:/usr/share/nginx/html:ro \
  nginx:alpine

curl http://localhost:8888   # V1

# از هاست فایل رو عوض کن
echo "<h1>V2 - changed!</h1>" > ~/docker-learn/step3/html/index.html

curl http://localhost:8888   # V2 - فوری!
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">

### 🔹 C. **tmpfs mount** (برای دیتای موقت و امنیتی)
</div> 


```bash
docker run --tmpfs /tmp:size=100m myimage
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


- فقط تو **RAM** ذخیره می‌شه (روی دیسک نمی‌نویسه)
- با `stop` می‌ره
- برای دیتای حساس (مثل رمز موقت) یا فایل‌های موقت سریع

### ۴. `VOLUME` در Dockerfile
</div> 


```dockerfile
VOLUME /data
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**این چیکار می‌کنه؟**
- اعلام می‌کنه این پوشه دیتا داره
- اگه کاربر `-v` نده، Docker **anonymous volume** می‌سازه
- **مشکل:** هر بار `docker run` یه volume جدید → دیتای قدیمی گم می‌شه

**بهترین practice:**
- `VOLUME` تو Dockerfile: نه ممنوع، نه ضروری
- برای دیتابیس‌های رسمی (postgres, mysql) گذاشتنش عالیه
- برای app: بهتره تو compose یا runtime تعریف بشه

---

### ۵. دستورات Volume
</div> 


```bash
# ساخت
docker volume create myvol

# لیست
docker volume ls

# جزئیات (مسیر واقعی!)
docker volume inspect myvol

# حذف یکی
docker volume rm myvol

# ⚠️ خطرناک: حذف همه volume های بلااستفاده
docker volume prune
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**قانون امنیتی برای تو:** ❌ **هرگز `docker volume prune` نزن** بدون اینکه `docker volume ls` رو چک کنی. ممکنه volume های setup اصلیت رو نابود کنه.

### ۶. بکاپ و ریستور Volume
</div> 


```bash
# بکاپ از یه volume به فایل tar
docker run --rm \
  -v learn-pgdata:/data:ro \
  -v $(pwd):/backup \
  alpine tar czf /backup/pgdata-backup.tar.gz -C /data .

# ریستور
docker run --rm \
  -v learn-pgdata:/data \
  -v $(pwd):/backup \
  alpine sh -c "cd /data && tar xzf /backup/pgdata-backup.tar.gz"

# کپی محتوا از یه volume به volume دیگه
docker run --rm \
  -v learn-pgdata:/from:ro \
  -v learn-pgdata-new:/to \
  alpine sh -c "cp -av /from/. /to/"
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**سناریو واقعی:** قبل از آپدیت setup اصلیت، از volume هاش بکاپ بگیر. یاد بگیر این کارو.

## بخش دوم: Network — چطور container ها با هم حرف می‌زنن

### ۱. مشکل: پیش‌فرض همه isolation
</div> 


```bash
# دو تا container تو پیش‌فرض
docker run -d --name learn-a alpine sleep 3600
docker run -d --name learn-b alpine sleep 3600

# از b، a رو ping کن
docker exec learn-b ping -c 2 learn-a
# ❌ ping: bad address 'learn-a'
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**چرا؟** هر container تو یه **namespace شبکه مجزا** با IP خودشه، ولی DNS خودکار ندارن.

---

### ۲. انواع Network در Docker
</div> 


```
┌─────────────────────────────────────────────────┐
│  bridge   → پیش‌فرض، isolation تو یه هاست     │
│  host     → container از شبکه هاست استفاده می‌کنه│
│  none     → هیچ شبکه‌ای نداره                  │
│  overlay  → برای swarm، بین چند هاست          │
│  macvlan  → MAC address جدا                   │
│  ipvlan   → IP جدا                            │
└─────────────────────────────────────────────────┘
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**۹۹٪ کارها با `bridge` (یا user-defined bridge) انجام می‌شه.**

---

### ۳. Bridge پیش‌فرض vs User-defined Bridge

### Bridge پیش‌فرض (`docker0`):
</div> 


```bash
docker network ls
# NETWORK ID     NAME      DRIVER
# abc...         bridge    bridge    ← اینه پیش‌فرض
# def...         host      host
# ghi...         none      null

# container جدید به این network می‌ره اگه چیزی نگیم
docker run -d --name app1 nginx
docker inspect app1 --format '{{.NetworkSettings.Networks}}'
# map[bridge:...]
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">



**محدودیت‌های bridge پیش‌فرض:**
- ❌ DNS داخلی نداره (اسم container resolve نمی‌شه!)
- ❌ فقط با IP می‌تونی وصل شی
- ❌ همه container های روی bridge پیش‌فرض با هم accessible هستن (امنیت پایین)

### User-defined Bridge (پیشنهاد همیشگی):
</div> 


```bash
docker network create learn-net

docker run -d --name learn-a --network learn-net alpine sleep 3600
docker run -d --name learn-b --network learn-net alpine sleep 3600

# حالا DNS کار می‌کنه!
docker exec learn-b ping -c 2 learn-a
# ✅ PING learn-a (172.xx.xx.xx): 56 data bytes
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**مزایای user-defined bridge:**
- ✅ **DNS خودکار** — با اسم container بهش وصل می‌شی
- ✅ **isolation** — فقط container های این network با هم حرف می‌زنن
- ✅ **alias** و **static IP** قابل تنظیمه
- ✅ **بهبود امنیت**

**قانون:** برای هر stack (مثل یه compose)، یه network جدا بساز. اینجوری stack ها از هم ایزوله می‌شن.

---

### ۴. دستورات Network
</div> 


```bash
# ساخت
docker network create learn-net

# ساخت با subnet مشخص
docker network create --subnet 172.20.0.0/16 learn-net

# لیست
docker network ls

# جزئیات (چه container هایی وصلن؟)
docker network inspect learn-net

# connect / disconnect container
docker network connect learn-net learn-a
docker network disconnect learn-net learn-a

# حذف
docker network rm learn-net
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">

### ۵. سناریوی واقعی: App + DB + Cache

بیایم یه stack دستی بسازیم (بدون compose هنوز — برای فهم):

</div> 


```bash
# ۱. شبکه جدا
docker network create learn-stack-net

# ۲. Postgres
docker volume create learn-stack-pgdata
docker run -d --name learn-stack-db \
  --network learn-stack-net \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=mydb \
  -v learn-stack-pgdata:/var/lib/postgresql/data \
  postgres:15

# ۳. Redis
docker run -d --name learn-stack-cache \
  --network learn-stack-net \
  redis:alpine

# ۴. یه "app" ساده (alpine با ابزارهای تست)
docker run -d --name learn-stack-app \
  --network learn-stack-net \
  alpine sleep 3600

# حالا از app به db و cache وصل شو:
docker exec learn-stack-app sh -c "apk add --no-cache postgresql-client redis"

# تست اتصال به Postgres با اسم container
docker exec learn-stack-app psql -h learn-stack-db -U postgres -c "\l"
# ✅ لیست دیتابیس‌ها

# تست Redis
docker exec learn-stack-app redis-cli -h learn-stack-cache PING
# ✅ PONG
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**نتیجه:** بدون اینکه IP بدونی، با اسم container به همه وصل شدی. **این کلیدیه که compose روش کار می‌کنه.**

### ۶. تفاوت `localhost` و اسم سرویس (اشتباه رایج)

اگه تو container یه app داری که به `localhost:5432` وصل می‌شه، **اشتباهه** — چون localhost یعنی **خود container**، نه هاست.
</div> 


```
❌ app → localhost:5432    → خود app (پورت 5432 باز نیست)
✅ app → learn-stack-db:5432 → container دیتابیس
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**تست:**
</div> 


```bash
# اشتباه: از app به localhost
docker exec learn-stack-app sh -c "nc -zv localhost 5432"
# ❌ connection refused

# درست: با اسم
docker exec learn-stack-app sh -c "nc -zv learn-stack-db 5432"
# ✅ open
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


---

### ۷. پورت publish vs expose
</div> 


```
┌──────────────────────────────────────┐
│  هاست                                │
│  ┌────────────────────────────────┐  │
│  │  پورت 8888 (publish با -p)     │  │  ← از بیرون accessible
│  └──────────┬─────────────────────┘  │
│             │                        │
│  ┌──────────▼─────────────────────┐  │
│  │  network learn-net             │  │  ← بین container ها
│  │  ┌────────┐  ┌────────┐       │  │
│  │  │ app    │  │ db:5432│       │  │
│  │  │ :3000  │──┤        │       │  │
│  │  └────────┘  └────────┘       │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


- `-p 8888:3000` = پورت ۸۸۸۸ هاست → ۳۰۰۰ container. از **بیرون** accessible.
- `EXPOSE 3000` = فقط **مستند**. برای **داخل** network.

**قانون:**
- برای db و cache: **هیچ‌وقت** `-p` نده (فقط داخل network دسترسی باشن)
- برای app که کاربر بهش وصل می‌شه: `-p` بده
- اگه فقط برای dev می‌خوای از بیرون تست کنی: `-p 127.0.0.1:8888:3000` (فقط از localhost)

## بخش سوم: تمرین بزرگ — همه با هم

**هدف:** یه stack ساده با volume + network بساز، بعد دیتا رو زنده نگه دار.
</div> 


```bash
# پاک‌سازی اول
docker rm -f learn-stack-app learn-stack-db learn-stack-cache 2>/dev/null
docker network rm learn-stack-net 2>/dev/null
docker volume rm learn-stack-pgdata 2>/dev/null

# ─── ساخت ───
docker network create learn-final-net
docker volume create learn-final-pgdata

docker run -d --name learn-final-db \
  --network learn-final-net \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=testdb \
  -v learn-final-pgdata:/var/lib/postgresql/data \
  postgres:15

sleep 5

# ─── تست دیتا ───
docker exec learn-final-db psql -U postgres -d testdb -c "
  CREATE TABLE items (id serial primary key, name text);
  INSERT INTO items (name) VALUES ('first'), ('second');
  SELECT * FROM items;
"

# ─── حالا container رو نابود کن ───
docker rm -f learn-final-db

# ─── با همون volume، دوباره بساز ───
docker run -d --name learn-final-db2 \
  --network learn-final-net \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=testdb \
  -v learn-final-pgdata:/var/lib/postgresql/data \
  postgres:15

sleep 5

# ─── دیتا هست؟ ───
docker exec learn-final-db2 psql -U postgres -d testdb -c "SELECT * FROM items;"
# ✅ باید دو ردیف ببینی!
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**این دقیقاً همون کاریه که compose خودکار انجام می‌ده.**

## بخش چهارم: نکات مهم برای setup فعلیت

### 🔴 خطرات پنهان که ممکنه setup اصلیت رو نابود کنه:

1. **`docker volume prune`** — همه volume های بلااستفاده رو می‌بره. دیتابیس setup اصلیت رو نابود می‌کنه.
2. **`docker system prune -a --volumes`** — همه چیز.
3. **`docker network rm $(docker network ls -q)`** — network های setup رو می‌بره.
4. **اسم network تکراری** — اگه یه network به اسم `backend` تو setup داری و تو یه network به همین اسم بسازی، collide می‌شه.

### ✅ راه‌های امن:
</div> 


```bash
# فقط چیزهایی که learn- دارن رو ببین
docker network ls | grep learn
docker volume ls | grep learn

# پاک‌سازی امن (فقط learn-)
docker ps -a --filter "name=learn-" --format "{{.Names}}" | xargs -r docker rm -f
docker network ls --filter "name=learn-" --format "{{.Name}}" | xargs -r docker network rm
docker volume ls --filter "name=learn-" --format "{{.Name}}" | xargs -r docker volume rm

# ⚠️ دقت: --filter name=learn- خیلی مهمه
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">

## بخش پنجم: برای درک بهتر setup فعلیت

برو یه نگاه کن (فقط خوندن، تغییر نده):
</div> 


```bash
# network هایی که setup استفاده می‌کنه
docker network ls

# کدوم container ها تو کدوم network هستن؟
for net in $(docker network ls --format "{{.Name}}"); do
  echo "=== $net ==="
  docker network inspect "$net" --format '{{range .Containers}}{{.Name}} {{end}}'
done

# volume های setup
docker volume ls

# کدوم container به کدوم volume وصله؟
docker ps -a --format "{{.Names}}" | while read c; do
  echo "=== $c ==="
  docker inspect "$c" --format '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{"\n"}}{{end}}'
done
```
<div dir="rtl" style="text-align: right; font-family: 'B Nazanin', Tahoma, sans-serif;">


**این تحلیل بهت نشون می‌ده compose هات زیر کاپوت چطور کار می‌کنن.** اینطوری وقتی به مرحله ۴ (Compose) برسیم، همه‌چیز طبیعی به نظر می‌رسه.

## سوالات خودآزمایی

1. تفاوت named volume و bind mount چیه؟ کِی از هر کدوم استفاده می‌کنی؟
2. چرا `docker rm -f` روی container دیتابیس بدون volume، دیتا رو نابود می‌کنه؟
3. چرا user-defined bridge بهتر از bridge پیش‌فرضه؟
4. تفاوت `-p 8080:80` و `EXPOSE 80` چیه؟
5. اگه یه app تو container هست که به `localhost:5432` وصل می‌شه، چرا کار نمی‌کنه؟
6. چطور از یه named volume بکاپ بگیری؟
7. چرا برای دیتابیس نباید `-p 5432:5432` بدی؟ کِی ممکنه لازم باشه؟
8. `docker volume prune` چرا برای setup فعلیت خطرناکه؟

<details>
<summary>جواب‌ها</summary>

1. Named: Docker مدیریت می‌کنه، برای دیتا. Bind: مسیر هاست، برای dev.
2. چون دیتا تو لایه نوشتنی container بود که با rm می‌ره. Volume خارج از این لایه‌ست.
3. DNS داخلی، isolation بین network ها، امنیت بالاتر.
4. `-p` پورت رو از هاست باز می‌کنه (از بیرون). `EXPOSE` فقط مستندسازیه.
5. چون localhost یعنی خود container، نه هاست یا db. باید اسم container یا service رو بدی.
6. با `docker run --rm -v vol:/data:ro -v $(pwd):/b alpine tar czf /b/backup.tar.gz -C /data .`
7. چون از بیرون دسترسی به db خطرناکه (brute force، SQL injection). فقط اگه برای dev/debug لازمه و از `127.0.0.1:` استفاده کن.
8. همه volume های بلااستفاده (حتی setup اصلیت که موقتاً متوقفن) رو پاک می‌کنه.
</details>

## چک‌لیست پایان مرحله ۳

قبل از رفتن به مرحله ۴ (Compose)، مطمئن شو:

- [ ] تونستم دیتا رو با volume بین دو container زنده نگه دارم
- [ ] تونستم با اسم container (نه IP) به یه db وصل شم
- [ ] تفاوت bind mount و named volume رو می‌فهمم
- [ ] می‌تونم از یه volume بکاپ بگیرم
- [ ] می‌دونم چرا `docker volume prune` خطره
- [ ] setup اصلیت رو با `docker network inspect` و `docker inspect` تحلیل کردم

---

**قدم بعدی:** مرحله ۴ (Docker Compose) — که همه‌ی اینا (network, volume, depends_on, healthcheck) رو یه جا با YAML به هم وصل می‌کنه. حالا که مفاهیم پایه رو داری، Compose **خیلی منطقی** به نظر می‌رسه.

**آماده‌ای بریم مرحله ۴؟** یا می‌خوای روی یکی از این تمرین‌ها عمیق‌تر کار کنیم؟
