Building on the foundational path, the next stage moves from manual, console-driven administration toward **automation, tuning, and modern deployment patterns**. This phase is where WebLogic administration becomes a discipline of scripting, security hardening, and integration with CI/CD pipelines.

---

### ⚙️ Phase 8: Automate with WLST (WebLogic Scripting Tool)

The console is excellent for learning, but production work demands repeatability. WLST is a Jython-based scripting interface that exposes WebLogic's management model (its MBeans) so you can query state, change configuration, and deploy applications programmatically.

**What to learn:** WLST has two fundamental modes. **Online mode** connects to a running AdminServer to read runtime state and modify live configuration. **Offline mode** works directly on configuration files without a running server, which is ideal for creating or modifying domains in a CI/CD pipeline. Start by launching `wlst.sh` from `WL_HOME/common/bin` and experimenting interactively. Then move to running `.py` script files non-interactively for automation.

**Why it matters:** Scripted changes can be versioned in Git, peer-reviewed, and replayed consistently. This eliminates configuration drift and provides an audit trail—instead of asking "what did we click last April," you can read the repository.

**Phase output:** You can write a WLST script that connects to your domain, deploys a WAR file, and reads the health state of a server—then run the same script in both interactive and non-interactive modes.

### 🔗 Phase 9: Deepen Resource Configuration (JDBC & JMS)

You have already created a basic data source. Now expand into the full resource model that enterprise applications depend on.

**JDBC:** Go beyond a single connection pool. Learn to tune pool sizes, configure **Prepared Statement Cache** settings, and understand how connection backlog buffering affects performance under load. For applications with high transaction volumes, explore **Logging Last Resource (LLR)** optimization, which can improve performance while maintaining transactional integrity.

**JMS:** Messaging resources follow a layered configuration. The typical sequence is: create a JDBC connection pool → create a JDBC data source → create a JMS connection factory → create a persistent store (JDBC Store or File Store) → create a JMS server → create JMS queues or topics. Persistent stores are mandatory for reliable messaging; they determine whether messages survive a server restart.

**Phase output:** You can configure a JMS queue backed by a JDBC persistent store, and you can explain the trade-offs between File Stores and JDBC Stores for different workloads.

---

### 🔐 Phase 10: Security Hardening and SSL

Security in WebLogic centers on **Security Realms**. The default realm (`myrealm`) controls authentication providers, password policies, and user lockout settings. Harden it by enforcing minimum password length, complexity requirements, and periodic rotation.

**SSL configuration** is a two-part task: enable the SSL listen port on the server (separate from the default HTTP port 7001, often 7002 or a custom port), and configure JSSE (Java Secure Socket Extension), which is the only supported SSL implementation in modern WebLogic versions. You will need to generate or import a certificate into a keystore and reference it from the server's SSL configuration.

**Phase output:** You can enable SSL on a Managed Server, configure a custom keystore, and verify that `https://` access works alongside the existing HTTP listener.

### 📊 Phase 11: Performance Tuning Foundations

Tuning is not about applying a magic list of parameters; it is a methodology. The official Oracle tuning guide frames it as a roadmap: **understand your performance objectives → measure baseline metrics → locate bottlenecks → tune the appropriate layer** (application, database, WebLogic, JVM, or operating system).

**Key areas to study:**

| Area | What to focus on |
|---|---|
| **JVM** | Heap sizing, garbage collection scheme selection (G1GC is commonly recommended for modern deployments) |
| **Thread pools** | Work Manager thread constraints; the self-tuning thread pool behavior |
| **HTTP sessions** | Session replication strategies (asynchronous replication to a secondary server or database) to balance availability and performance |
| **Persistent stores** | JDBC Store vs. File Store tuning; block size and direct-write policies |
| **Development vs. Production mode** | Production mode changes default values for many services and disables development-only features |

**Phase output:** You can produce a baseline performance profile of your domain (thread usage, heap trends, JDBC pool wait times) and identify one concrete bottleneck with a proposed tuning change.

### 🚀 Phase 12: DevOps and the Modern WebLogic Toolchain

Oracle now provides a suite of tools that treat WebLogic as a deployable artifact rather than a manually configured server. This is the direction the platform has been moving toward, and it is increasingly relevant for teams running WebLogic alongside cloud-native infrastructure.

**The Oracle WebLogic Kubernetes Toolkit** includes several complementary tools:

- **WebLogic Deploy Tooling (WDT):** Lift-and-shift existing domain configurations into images or Kubernetes. It automates domain provisioning, updates, and application deployment.
- **WebLogic Image Tool:** Automate building, patching, and updating WebLogic Docker images, including custom images, scriptable for CI/CD.
- **WebLogic Kubernetes Operator:** Extends Kubernetes to create, configure, and manage WebLogic domains natively, handling services, ports, and configuration overrides.
- **Monitoring Exporter:** Exports WebLogic metrics to Prometheus, enabling Grafana dashboards and policy-based autoscaling of WebLogic clusters.

Even if your organization is not yet on Kubernetes, **WDT and the Image Tool are useful independently** for standardizing domain creation and reducing manual configuration in traditional VM environments. Jenkins or GitLab CI can invoke WLST or these tools to automate releases, blue-green switches, and rollbacks.

**Phase output:** You can explain the difference between WLST-based automation (imperative scripting) and WDT-based automation (declarative model-driven deployment), and you know which tool to reach for in a containerized versus traditional environment.

### 📚 How to Sequence This Stage

Do not attempt all five phases simultaneously. A practical order is:

1. **WLST first** — it underpins everything else and gives you a scripting habit.
2. **JDBC/JMS depth** — build the resource model your applications actually need.
3. **Security hardening** — apply SSL and password policies before any production-like testing.
4. **Performance tuning** — only after you have a stable, monitored baseline.
5. **DevOps tooling** — when you are ready to treat domains and deployments as versioned artifacts.

Each phase should end with a concrete artifact: a reusable WLST script, a working JMS queue with a persistence store, an SSL-enabled endpoint, a baseline report, or a WDT model file. The goal is to accumulate a personal toolkit of verified, reusable assets rather than just reading documentation.
