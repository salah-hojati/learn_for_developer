Here is a step-by-step WebLogic learning path in English. It is organized by phases, with a clear goal and expected outcome for each phase. The path assumes a Linux environment (CentOS/Ubuntu), which is common in enterprise deployments.

---

## Phase 1: Understand WebLogic’s Core Architecture First

Before installing anything, build a mental model of three key concepts.

**1. Domain is the management boundary.**  
A WebLogic domain is a logical administrative unit containing **one AdminServer** and **zero or more Managed Servers**. The AdminServer holds the main configuration (`config.xml`) and is the control plane for starting/stopping the domain and distributing configuration. Managed Servers carry application traffic. In the beginning, you can use only the AdminServer and deploy applications directly to it. Introduce Managed Servers later when you study clustering.

**2. Node Manager handles process-level control.**  
Node Manager is a daemon running on each host. It allows the AdminServer to remotely start, stop, and restart Managed Servers on that host. It is the foundation for clustering and automated operations.

**3. The Administration Console is your main operating entry point.**  
After installation, access `http://<host>:7001/console` in a browser. Most configuration tasks—deploying applications, creating data sources, configuring clusters, checking status—can be done there. WLST (WebLogic Scripting Tool) is the scripting interface you will gradually adopt for automation and batch operations.

**Phase output:** You can explain in your own words the relationship between Domain, AdminServer, Managed Server, and Node Manager, and you know what the Administration Console is for.

---

## Phase 2: Environment Preparation and Installation (Linux)

### 2.1 System and account preparation

Use CentOS 7/8 or Ubuntu. Allocate at least 4 GB RAM (8 GB+ is recommended for production-like environments). **Do not run WebLogic as root.** Create a dedicated `weblogic` system user and perform installation and startup under that user.

For JDK, WebLogic 12c/14c typically uses JDK 8 or JDK 11. Check with `java -version`. If no suitable JDK exists, install OpenJDK and set `JAVA_HOME`.

### 2.2 Obtain the installer and install

Download the appropriate installation JAR from Oracle, for example `fmw_14.1.1.0.0_wls_lite_generic.jar` for 14c, or the corresponding 12c file. Switch to the `weblogic` user and run:

```bash
java -jar fmw_14.1.1.0.0_wls_lite_generic.jar
```

In the installer, pay attention to two choices: **Middleware Home** (for example `/u01/oracle/middleware`) and installation type (choose **Typical Install** for initial learning). If you later need batch deployment across multiple machines, learn silent installation using a response file (`-silent -responseFile`).

**Phase output:** WebLogic is successfully installed in the target directory, and the `weblogic` user can execute scripts under the installation directory.

---

## Phase 3: Create a Domain and Start It for the First Time

### 3.1 Create a domain with the configuration wizard

Go to `<Middleware Home>/oracle_common/common/bin` and run `./config.sh`. In the wizard:

- Choose **Create a new domain**.
- Select the **Basic WebLogic Server Domain** template.
- Specify the domain path, for example `/u01/oracle/user_projects/domains/base_domain`.
- Set the administrator account (username is usually `weblogic`; the password must meet complexity requirements).

After creation, the `base_domain` directory contains `bin/`, `config/`, `servers/`, etc. `startWebLogic.sh` and `stopWebLogic.sh` are in `bin/`.

### 3.2 Start and access the console

Go to the domain’s `bin` directory and start in the foreground:

```bash
./startWebLogic.sh
```

The first startup is slower. When you see `<Server state changed to RUNNING>`, the AdminServer is ready. To run in the background, use `nohup ./startWebLogic.sh > admin.log 2>&1 &`. Then open `http://<server-IP>:7001/console` and log in with the administrator account.

If you cannot access it, first check whether the firewall allows port 7001: `firewall-cmd --add-port=7001/tcp --permanent` followed by `--reload`.

**Phase output:** You can independently create a domain, start the AdminServer, and log in to the console through a browser.

---

## Phase 4: Deploy Your First Application

Prepare a `.war` file (or package a simple web application). In the console, go to **Deployments → Install**, select the WAR file, set **Target** to **AdminServer**, and complete the wizard to install and start it. Access `http://<IP>:7001/<context-root>` to verify.

The purpose here is not just uploading a WAR. It is to understand the concept of **deployment Target**: an application can be deployed to a single Server or to a Cluster. Later, when you study clustering, the deployment target directly determines whether the application has high availability.

**Phase output:** You can successfully deploy a WAR through the console and access its URL.

---

## Phase 5: Learn a Production-Essential Configuration—Data Sources

Enterprise applications almost always need a database. In the console, go to **Services → Data Sources → New**. Fill in the JNDI name, database driver class, URL, username, and password. After creation, use **Test Configuration** to verify connectivity.

The value of this step is that you encounter **JDBC connection pools** and **JNDI resources** in WebLogic for the first time, and you understand the principle that “resources must be targeted to a server or cluster”—a principle that runs through WebLogic configuration.

**Phase output:** You can create a data source that passes the test and know how an application looks it up via JNDI.

---

## Phase 6 (Advanced): Clustering and High Availability

Move to clustering after you are comfortable operating a single AdminServer. A typical entry-level cluster architecture is: **one AdminServer (not in the cluster, management only) + two or more Managed Servers forming a cluster**, with Nginx/HAProxy in front for load balancing.

Key operations include: creating the domain in cluster mode via `config.sh` or WLST, defining a Cluster object and adding Managed Servers to it; starting Node Manager on each node so the AdminServer can remotely control Managed Server start/stop. For external access, use a **cluster DNS name** mapped to all Managed Server addresses. Clients obtain the member list via DNS, and WebLogic uses them in round-robin fashion and automatically removes unreachable nodes.

For high availability, at minimum understand **HTTP session replication** (so sessions are not lost when one instance fails) and **deploying applications to the Cluster rather than a single Server**.

**Phase output:** You can build a minimal cluster with one AdminServer and two Managed Servers, deploy an application to the cluster, and verify that requests are still handled after stopping one Managed Server.

---

## Phase 7: Monitoring and the Starting Point for Daily Operations

You do not need a full monitoring platform at first, but you should master two basic paths: the console and WLST.

- **Console:** Under `Servers → <Server> → Monitoring`, check runtime state, idle thread count, JVM heap usage, etc.
- **WLST:** In the domain’s `bin` directory, run `./wlst.sh`, then `connect('weblogic','password','t3://localhost:7001')`. Use `serverRuntime()` to get `HealthState`, thread, and JVM runtime information. WLST is the foundation for writing inspection scripts and automation later. At the entry level, just be able to connect and read health status.

**Phase output:** You can obtain a Server’s health status and thread/JVM summary through both the console and WLST.

## Suggested Learning Resources

**Official documentation is the most accurate source of truth.** Oracle’s `Understanding Oracle WebLogic Server` includes a “Roadmap for Administering the WebLogic Server System” table that maps installation, startup/shutdown, resource management, deployment, monitoring, clustering, and troubleshooting tasks to the relevant documentation. Use it as an index for your whole learning process.

**For hands-on introductory operations**, Chinese series notes on Tencent Cloud and yisu.com provide fairly direct step-by-step explanations of installation, domain creation, deployment, and cluster configuration under CentOS/Linux. They are useful for following along.

**For advanced system administration topics** (WLST automation, JDBC/JMS, security, performance tuning, DevOps), consult Cleverence’s WebLogic system administrator guide as needed when you enter the intermediate/advanced stage.

---

## Summary of the Core Logic

Use a single AdminServer to complete the minimum loop: **install → create domain → start → deploy → data source**. This builds basic familiarity with how WebLogic is operated. Then move to the cluster phase—**AdminServer + Managed Servers + Cluster**—to understand the difference in deployment targets for high availability. Finally, gradually introduce WLST and monitoring to prepare for automation and daily operations. After each phase, use “Can I independently reproduce the key operations?” as your test criterion. That is more effective than reading documentation alone.
