# CRD & Operator Control Loop
+------------------------------------------------------------------+
|                   CRD / OPERATOR CONTROL LOOP                     |
|                                                                  |
|  +----------------------------------------------------------------+
|  |  CUSTOM RESOURCE DEFINITION (CRD)                             |
|  |  apiVersion: apiextensions.k8s.io/v1                         |
|  |  kind: CustomResourceDefinition                              |
|  |  metadata.name: crontabs.stable.example.com               |
|  |  spec:                                                    |
|  |  group: stable.example.com                                |
|  |  names: kind: CronTab plural: crontabs singular: crontab  |
|  |  scope: Namespaced                                         |
|  |  versions:                                                 |
|  |  - name: v1                                                 |
|  |  served:true storage:true                                   |
|  |  schema: openAPIV3Schema (validation)  |
|  +----------------------------------------------------------------+
|        |                                                         |
|        |  Custom Resource (instance)                              |
|        |  apiVersion: stable.example.com/v1                      |
|        |  kind: CronTab                                          |
|        |  metadata.name: my-cron                                |
|        |  spec: { schedule:"*/1 * * * *", ... }                |
|        v                                                         |
|  +----------------------------------------------------------------+
|  |  OPERATOR (controller)                                        |
|  |  - Informer watches CronTab CRs + owned resources            |
|  |  - Event -> workqueue (rate-limited)                          |
|  |  - Reconcile(ctx, req{namespace/name}) loop                  |
|  +-----------+--------------------------------------------------+ |
|              |                                                  |
|              |  1. Fetch CronTab instance (GET from cache)       |
|              v                                                  |
|              |  2. Read spec (schedule, image, replicas)         |
|              +--------------------------------------------------+
|              |                                                  |
|              |  3. Compute desired state (cron Job schedule)     |
|              v                                                  |
|              |  4. List owned resources (ownership labels)       |
|              +--------------------------------------------------+
|              |                                                  |
|              |  5. Diff desired vs actual -> create/update/delete|
|              v                                                  |
|              |  6. Set OwnerReferences (GC safety)               |
|              +--------------------------------------------------+
|              |                                                  |
|              |  7. Update Status (conditions, observedGen)       |
+------------------------------------------------------------------+

# Ownership Graph & Finalizers
+------------------------------------------------------------------+
|         OWNED RESOURCES, OWNERREFS & FINALIZERS                   |
|                                                                  |
|  CRON-TAB (CR)                                                   |
|  +----------------------------------------------------------+    |
|  |  spec.schedule: "* * * * *"                            |    |
|  |  metadata:                                               |    |
|  |  finalizers:                                             |    |
|  |  - crontab-cleanup.stable.example.com                  |    |
|  +-----------+----------+----------+                      |    |
|              |          |          |                      |    |
|              v          v          v                      |    |
|  +-----------------+ +----------------+ +----------------+|      |
|  |  Deployment     | |   CronJob     | |  Service       |      |
|  |  (worker)       | |  (scheduled)  | |  (svc)         |      |
|  |  replicas:1     | |               | |                |      |
|  |  ownerRef: CronTab|            | |                |      |
|  +-----------------+ +-------------+ +----------------+ |      |
|                                                                  |
|  FINALIZER FLOW (deletion):                                      |
|  1. DELETE CronTab -> metadata.deletionTimestamp set             |
|  2. Object NOT removed (finalizers present)                     |
|  3. Reconcile sees dt!=nil -> run cleanup (delete jobs/PVCs)     |
|  4. Remove finalizer from list -> API server deletes object     |
|                                                                  |
|  STATUS SUBRESOURCE:                                             |
|  - spec and status updated via SEPARATE API paths:               |
|    /apis/stable.example.com/v1/crontabs/<name> (spec)            |
|    /apis/.../crontabs/<name>/status (status)                     |
|  - status requires a separate RBAC verb:                     |
|    "crontabs/status" resource                                  |
|  - prevents status writes from resetting spec                   |
+------------------------------------------------------------------+

# Operator SDK / Reconcile Best Practices
+------------------------------------------------------------------+
|            RECONCILE BEST PRACTICES & WATCH SETUP                |
|                                                                  |
|  WATCH SETUP (controller-runtime):                                |
|  +----------------------------------------------------------+    |
|  |  mgr.Watch(&source.Kind{Type: &appsv1.Deployment{}},   |    |
|  |  &handler.EnqueueRequestForOwner{...})                |    |
|  |  -> events on Deployments cascade to owning CRs        |    |
|  +----------------------------------------------------------+    |
|                                                                  |
|  RECONCILE PATTERN:                                              |
|  - idempotent (same result no matter how many runs)             |
|  - compare .spec (desired) vs observed (fetched resources)      |
|  - never use == on objects; use equality.Semantic.DeepEqual     |
|  - update status BEFORE returning error                         |
|  - requeue on error (backoff) or requeueAfter for periodic      |
|                                                                  |
|  COMMON PITFALLS:                                                |
|  - infinite reconcile loop (mutating owned resource each time)   |
|  - forgetting to set controller: true (OwnerReferences)         |
|  - writing spec in status subresource (rejected)                |
|  - long-running reconcile (blocks other keys in queue)          |
+------------------------------------------------------------------+
