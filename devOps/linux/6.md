## بخش ۱: Git چیست و چرا برای DevOps حیاتی است؟

Git یک **سیستم کنترل نسخه توزیع‌شده (DVCS)** است. برخلاف SVN، هر کلون کامل تاریخچه را دارد و می‌توانی آفلاین کامیت بزنی.

**چرا DevOps بدون Git معنا ندارد:**

- **CI/CD:** هر Pipeline از یک کامیت در Git trigger می‌شود.
- **IaC:** Ansible Playbook، Terraform و Kubernetes Manifest همه در Git نگه‌داری می‌شوند.
- **همکاری:** چند نفر بدون تداخل روی یک کد کار می‌کنند.
- **Audit Trail:** می‌دانی چه کسی، چه زمانی، چرا تغییری داده.

## بخش ۳: ساختار سه‌گانه Git (مهم‌ترین مفهوم)

Git سه ناحیه دارد:

```
Working Directory  →  Staging Area  →  Repository (.git)
   (فایل‌های واقعی)      (index)          (تاریخچه کامیت‌ها)
```

| ناحیه | چیست | دستور انتقال |
|---|---|---|
| **Working Directory** | فایل‌هایی که ویرایش می‌کنی | — |
| **Staging Area** | تغییراتی که آماده کامیت هستند | `git add` |
| **Repository** | کامیت‌های ثبت‌شده | `git commit` |

**چرا Staging Area؟** می‌توانی از میان ۱۰ فایل تغییرکرده، فقط ۳ فایل مرتبط را در یک کامیت منطقی ثبت کنی.

## بخش ۵: کامیت استاندارد با **Conventional Commits**

پیام کامیت خوب، تاریخچه را به **مستندات زنده** تبدیل می‌کند. استاندارد صنعتی امروز **Conventional Commits** است که با **SemVer** (نسخه‌گذاری معنایی) هماهنگ است.

### ساختار

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### Typeهای اصلی

| Type | معنا | تأثیر SemVer |
|---|---|---|
| `feat` | قابلیت جدید | MINOR |
| `fix` | رفع باگ | PATCH |
| `docs` | فقط مستندات | — |
| `style` | فرمت، بدون تغییر منطق | — |
| `refactor` | بازنویسی بدون feat/fix | — |
| `perf` | بهبود عملکرد | — |
| `test` | تست | — |
| `build` | سیستم build یا dependency | — |
| `ci` | تنظیمات CI | — |
| `chore` | کارهای متفرقه | — |



### قوانین طلایی

- **حالت امری:** `add feature` نه `added feature`
- **خط اول حداکثر ۵۰ تا ۷۲ کاراکتر**
- **Body توضیح می‌دهد «چرا»، نه «چه»** (diff خودش «چه» را نشان می‌دهد)
- **Breaking Change:** `feat!:` یا footer `BREAKING CHANGE:`

### مثال‌ها

```bash
# ✅ خوب
git commit -m "feat(auth): add OAuth2 PKCE flow for mobile clients"
git commit -m "fix(ssh): prevent lockout when AllowUsers is empty"
git commit -m "docs: update session 6 with Conventional Commits"
git commit -m "feat!: remove legacy TLS 1.0 support"

# ❌ بد
git commit -m "updated stuff"
git commit -m "fix bug"
git commit -m "WIP"
```

**چرا مهم است؟** ابزارهایی مثل `commitlint` می‌توانند کامیت غیراستاندارد را رد کنند، و ابزارهایی مثل `semantic-release` می‌توانند نسخه و changelog را خودکار بسازند.

## بخش ۶: **امضای کامیت با SSH** (ویژه ۲۰۲۶)

در DevOps، **Supply Chain Security** حیاتی است. کامیت بدون امضا یعنی هر کسی با ایمیل تو می‌تواند کامیت جعلی بزند. **امضای SSH** راهی ساده و مدرن برای تأیید هویت است (به جای GPG پیچیده).

### پیش‌نیاز: Git 2.34+

```bash
git --version
```

### پیکربندی

```bash
# به Git بگو از SSH برای امضا استفاده کند
git config --global gpg.format ssh

# کلید عمومی SSH را به عنوان کلید امضا معرفی کن
git config --global user.signingkey ~/.ssh/id_ed25519.pub

# همه کامیت‌ها و تگ‌ها به صورت پیش‌فرض امضا شوند
git config --global commit.gpgSign true
git config --global tag.gpgSign true
```



### فعال کردن SSH Agent (تا هر بار passphrase نپرسد)

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
```



### اضافه کردن کلید به GitHub به عنوان **Signing Key**

این مرحله حیاتی است: کلید را به عنوان **Signing Key** اضافه کن، نه فقط Authentication Key.

در GitHub: **Settings → SSH and GPG keys → New SSH key → Key type: Signing Key** → کلید عمومی (`id_ed25519.pub`) را پیست کن.

### تست

```bash
git commit -m "test: verify SSH commit signing"
```

اگر در GitHub کامیت را دیدی و **برچسب سبز “Verified”** داشت، موفق شدی.

### بررسی محلی امضا

```bash
git log --show-signature -1
```

## بخش ۷: برنچ‌ها (Branching)

برنچ یعنی یک خط توسعه موازی. `main` شاخه اصلی است و برای هر قابلیت/فیکس یک برنچ جدید می‌سازی.

### دستورات پایه

```bash
git branch                    # لیست برنچ‌ها
git branch feature-x          # ساخت برنچ
git switch feature-x          # رفتن به برنچ (مدرن)
git checkout -b feature-y     # ساخت + رفتن (کلاسیک)
git switch main               # برگشت به main
git branch -d feature-x       # حذف برنچ (اگر merge شده)
git branch -D feature-x       # حذف اجباری
```

### الگوی نام‌گذاری

```bash
git switch -c feat/add-search
git switch -c fix/ssh-timeout
git switch -c docs/session-7
```

### استراتژی‌های Branching

| استراتژی | کی استفاده کن | معایب |
|---|---|---|
| **Trunk-Based** | تیم کوچک، CI قوی، CD | نیاز به Feature Flag |
| **GitHub Flow** | اکثر تیم‌ها (ساده) | — |
| **GitFlow** | نرم‌افزار نسخه‌دار (موبایل، SDK) | برای web service overkill است |



**برای DevOps و web service:** **GitHub Flow** بهترین انتخاب است. یک `main`، برنچ‌های کوتاه‌عمر، PR و merge سریع.

## بخش ۸: Merge و Rebase

### Merge

```bash
git switch main
git merge feature-x
```

یک **merge commit** می‌سازد و تاریخچه غیرخطی می‌شود.

### Rebase

```bash
git switch feature-x
git rebase main
```

کامیت‌های feature-x را روی نوک main بازپخش می‌کند و تاریخچه **خطی** می‌سازد.

### کدام را انتخاب کنم؟

| سناریو | انتخاب |
|---|---|
| ادغام feature به main | **Merge** (یا Squash Merge) |
| به‌روزرسانی برنچ feature با تغییرات main | **Rebase** |
| تمیز کردن کامیت‌های محلی قبل از PR | **Rebase Interactive** (`git rebase -i`) |

**قانون طلایی:** هرگز برنچی که push شده و دیگران روی آن کار می‌کنند را rebase نکن (تاریخچه را بازنویسی می‌کند).

## بخش ۱۰: `.gitignore` — چه چیزی هرگز نباید کامیت شود

فایل `.gitignore` به Git می‌گوید چه فایل‌هایی را نادیده بگیرد.

```gitignore
# Secrets — هرگز کامیت نکن!
.env
*.pem
*.key
id_rsa
id_ed25519

# Python
__pycache__/
*.pyc
.venv/

# Node

.vscode/
```

**⚠️ هشدار امنیتی:** اگر `.env` یا کلید خصوصی را کامیت کردی، حتی اگر بعداً پاک کنی، در تاریخچه Git می‌ماند. باید از `git filter-repo` یا BFG Repo-Cleaner استفاده کنی و **کلید را فوراً باطل کنی**.

### `.gitkeep` برای پوشه‌های خالی

## بخش ۱۱: دستورات نجات‌بخش (Undo)

| سناریو | دستور |
|---|---|
| تغییرات unstaged را دور بریز | `git restore file` |
| فایل را از Staging خارج کن | `git restore --staged file` |
| آخرین کامیت را اصلاح کن (پیام یا محتوا) | `git commit --amend` |
| کامیت را برگردان (تاریخچه حفظ شود) | `git revert <hash>` |
| به کامیت قبلی برگرد (تاریخچه بازنویسی شود) | `git reset --hard <hash>` ⚠️ |
| تغییرات را موقتاً کنار بگذار | `git stash` / `git stash pop` |

**⚠️ `git reset --hard`** تغییرات uncommitted را برای همیشه پاک می‌کند. با احتیاط.

### `git stash` — کنار گذاشتن موقت

```bash
git stash              # تغییرات را کنار بگذار
git stash list         # لیست stashها
git stash pop          # برگردان
```

## بخش ۱۲: Git Hooks — اتوماسیون قبل از کامیت

Git Hooks اسکریپت‌هایی هستند که در رویدادهای خاص اجرا می‌شوند. نمونه کلاسیک: **جلوگیری از کامیت فایل‌های حاوی Secret**.

### نمونه: `pre-commit` hook

```bash
nano .git/hooks/pre-commit
```

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

# جلوگیری از کامیت فایل‌های حساس
if git diff --cached --name-only | grep -E '\.env$|\.pem$|id_ed25519$'; then
    echo "❌ ERROR: Attempting to commit sensitive files!" >&2
    echo "Remove them from staging: git restore --staged <file>" >&2
    exit 1
fi

# اجرای ShellCheck روی اسکریپت‌ها
for file in $(git diff --cached --name-only -- '*.sh'); do
    if command -v shellcheck &>/dev/null; then
        shellcheck "$file" || exit 1
    fi
done
```

```bash
chmod +x .git/hooks/pre-commit
```

**نکته:** Hooks به صورت پیش‌فرض در Git منتقل نمی‌شوند. برای تیم، از ابزارهایی مثل `pre-commit` framework یا Husky استفاده کن.

## پروژه جلسه ۶

**سناریو:** یک مخزن Git برای اسکریپت‌های DevOps خودت بساز.

1. پوشه `~/devops-scripts` بساز و `git init` کن.
2. فایل `README.md` و `server-health.sh` (از جلسه ۵) را اضافه کن.
3. یک `.gitignore` حرفه‌ای بنویس (شامل `.env`, `*.key`, `*.log`).
4. **SSH Commit Signing** را تنظیم کن و اولین کامیت را با پیام Conventional بزن:
   ```bash
   git commit -m "feat: add server health check script"
   ```
5. یک برنچ `feat/add-backup-script` بساز.
6. اسکریپت `backup.sh` را از جلسه ۵ اضافه کن و کامیت بزن:
   ```bash
   git commit -m "feat: add automated backup script with trap cleanup"
   ```
7. به `main` برگرد و merge کن (با `--no-ff`).
8. یک مخزن در GitHub بساز و push کن.
9. بررسی کن که کامیت‌ها در GitHub **Verified** هستند.
10. یک `pre-commit` hook بنویس که از کامیت فایل‌های `.env` جلوگیری کند.

## ارتباط با جلسات قبل و بعد

- **جلسه ۴ (SSH):** همان کلید `ed25519` که ساختی، حالا برای **امضای کامیت** هم استفاده می‌شود. یک کلید، دو کاربرد (Authentication + Signing).
- **جلسه ۵ (Bash):** اسکریپت‌هایت را در Git نگه می‌داری و `pre-commit` hook با `shellcheck` کیفیت را تضمین می‌کند.
- **جلسه ۷ (CI/CD):** هر Pipeline از یک `git push` trigger می‌شود. Conventional Commits اجازه می‌دهد نسخه و changelog خودکار ساخته شود.
