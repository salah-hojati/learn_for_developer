تا اینجا یاد گرفتی چطور روی سرور کار کنی، امن وصل شوی و اسکریپت بنویسی. اما اگر سرویسی بالا نیاید یا سرور دیگری را نبیند، باید بدانی **کجای مسیر شبکه** مشکل دارد. این جلسه دقیقاً همان مهارتی است که در DevOps هر روز به کار می‌آید: «چرا پورت باز نیست؟ DNS چرا جواب نمی‌دهد؟ فایروال جلوی چه چیزی را گرفته؟»

# جلسه ۷: مبانی شبکه در لینوکس

**هدف:** در پایان این جلسه بتوانی آدرس IP، مسیر (route) و DNS را با ابزارهای مدرن (`ip`, `dig`, `resolvectl`) بررسی کنی، پورت‌های باز را ببینی، با `tcpdump` ترافیک را بگیرد، و فایروال را با `ufw` یا `nftables` طوری تنظیم کنی که سرویس‌ها در دسترس باشند اما سرور امن بماند.

---

## بخش ۱: چهار لایه‌ای که واقعاً لمس می‌کنی

لازم نیست کل مدل OSI را حفظ کنی. در کار روزمره چهار لایه کافی است:

| لایه | ابزار | چه چیزی را چک می‌کند |
|---|---|---|
| **Link** (لینک) | `ip link`, `ip neigh` | اینترفیس و MAC |
| **Network** (شبکه) | `ip addr`, `ip route` | IP و مسیر |
| **Transport** (انتقال) | `ss` | پورت‌ها و اتصال‌ها |
| **Application** (کاربرد) | `curl`, `dig`, `openssl` | HTTP، DNS، TLS |

**قانون طلایی عیب‌یابی:** از پایین به بالا برو. اول ببین اینترفیس IP دارد، بعد route، بعد DNS، بعد پورت، و آخر فایروال.

---

## بخش ۲: ابزارهای مدرن — `ip` جای `ifconfig`

ابزارهای قدیمی `ifconfig`, `netstat`, `route` و `arp` از بسته `net-tools` هستند که دیگر به‌طور پیش‌فرض نصب نمی‌شوند. جایگزین مدرن، بسته `iproute2` است.

### دیدن اینترفیس‌ها و IP

```bash
ip -brief addr
```

خروجی چیزی شبیه:

```
lo    UNKNOWN   127.0.0.1/8 ::1/128
eth0  UP        10.0.3.17/24 fe80::5054:ff:fe12:3456/64
```

`-brief` جدول تمیزی می‌دهد. برای جزئیات بیشتر:

```bash
ip addr show
ip addr show eth0
```

### مدیریت اینترفیس

```bash
ip link show
sudo ip link set dev eth0 up
sudo ip link set dev eth0 down
```

### جدول مسیریابی (Route)

```bash
ip route
```

خروجی معمولی:

```
default via 10.0.3.1 dev eth0 proto dhcp src 10.0.3.17 metric 100
10.0.3.0/24 dev eth0 proto kernel scope link src 10.0.3.17
```

- `default via 10.0.3.1`: ترافیک به بیرون از این gateway می‌رود.
- `10.0.3.0/24`: شبکه محلی؛ بدون gateway.

### `ip neigh` — جدول ARP/NDP

```bash
ip neigh
```

نقشه IP به MAC را نشان می‌دهد. اگر یک IP در این جدول `FAILED` بود، یعنی در لایه ۲ به آن نمی‌رسی.

## بخش ۳: CIDR و آدرس‌دهی — چیزی که اشتباهش همه‌چیز را خراب می‌کند

آدرس `10.0.3.17/24` یعنی ۲۴ بیت اول شبکه را مشخص می‌کند. پس `10.0.3.0` تا `10.0.3.255` محلی هستند و بقیه باید از router رد شوند. اگر این عدد را اشتباه بگذاری، «بعضی مقصدها کار می‌کنند و بعضی نه».

**سه رنج خصوصی (Private):**

| رنج | کاربرد |
|---|---|
| `10.0.0.0/8` | شبکه‌های بزرگ ابری/VPC |
| `172.16.0.0/12` | شبکه‌های متوسط |
| `192.168.0.0/16` | شبکه خانگی/اداری |

`127.0.0.0/8` هم loopback است (کاملاً داخل kernel).

## بخش ۴: DNS — نام چطور به IP تبدیل می‌شود

DNS مثل دفترچه تلفن است: نام قابل‌فهم انسان را به IP تبدیل می‌کند.

### فایل‌های مهم

| فایل | کار |
|---|---|
| `/etc/hostname` | نام ماندگار سیستم |
| `/etc/hosts` | نگاشت ایستا (قبل از DNS چک می‌شود) |
| `/etc/resolv.conf` | سرورهای DNS (معمولاً توسط `systemd-resolved` مدیریت می‌شود) |
| `/etc/nsswitch.conf` | ترتیب جستجو (`hosts: files dns`) |

### ابزار مدرن: `resolvectl`

در Ubuntu 26.04، `systemd-resolved` مدیر DNS است:

```bash
resolvectl status
resolvectl query google.com
```

### ابزار دقیق: `dig`

`dig` خود DNS را بازجویی می‌کند (نه library سیستم) و خروجی ساختاریافته می‌دهد:

```bash
dig google.com
dig +short google.com
dig google.com MX
dig @8.8.8.8 google.com          # مستقیم از یک resolver خارجی
```

اگر `dig +short google.com @8.8.8.8` جواب داد ولی `dig +short google.com` جواب نداد، مشکل از resolver محلی یا `/etc/resolv.conf` است.

## بخش ۵: پورت‌ها و اتصال‌ها — `ss` جای `netstat`

`ss` (Socket Stat) جایگزین سریع‌تر و پرجزئیات‌تر `netstat` است.

```bash
ss -tulpn
```

معنی فلگ‌ها:

| فلگ | معنا |
|---|---|
| `-t` | TCP |
| `-u` | UDP |
| `-l` | Listening (گوش‌دهنده) |
| `-p` | Process (نیاز به sudo برای همه) |
| `-n` | بدون resolve نام (سریع‌تر) |

مثال: اگر سرویسی بالا نیامده، اول `ss -tulpn | grep :8080` بزن. اگر چیزی گوش نمی‌دهد، مشکل از فایروال نیست؛ خود سرویس بالا نیامده.

---

## بخش ۶: عیب‌یابی لایه‌به‌لایه (مهم‌ترین بخش این جلسه)

این گردش‌کار را حفظ کن. در ۹۰٪ مواقع مشکل را پیدا می‌کند:

### مرحله ۱: اینترفیس و IP

```bash
ip -brief addr
```

اگر اینترفیس اصلی `UP` نبود یا IP نداشت، مشکل از لایه ۱/۲ است (کابل، DHCP، Netplan).

### مرحله ۲: مسیر پیش‌فرض

```bash
ip route show
```

باید یک خط `default via ...` ببینی. اگر نبود، سرور به بیرون نمی‌رود.

### مرحله ۳: تست gateway

```bash
ping -c 4 $(ip route | awk '/default/ {print $3}')
```

اگر gateway جواب نداد، مشکل در شبکه محلی است.

### مرحله ۴: DNS

```bash
dig +short google.com @8.8.8.8
resolvectl query google.com
cat /etc/resolv.conf
```

### مرحله ۵: پورت گوش‌دهنده

```bash
ss -tulpn
```

### مرحله ۶: تست پورت مقصد

```bash
nc -zv 10.0.0.5 5432
# یا بدون nc:
timeout 3 bash -c "</dev/tcp/10.0.0.5/5432" && echo open || echo closed
```

### مرحله ۷: مسیر بسته‌ها

```bash
traceroute -n 8.8.8.8
mtr --report 8.8.8.8
```

`mtr` ترکیب traceroute و ping است و آمار هر hop را می‌دهد.

### مرحله ۸: گرفتن ترافیک با `tcpdump`

اگر هیچ‌کدام جواب نداد، ترافیک را ببین:

```bash
sudo tcpdump -i eth0 -n port 53
sudo tcpdump -i eth0 -n host 10.0.0.5 and port 443 -w /tmp/capture.pcap
```

`tcpdump` بهترین ابزار برای دیدن این است که بسته‌ها واقعاً می‌رسند یا نه.

**نکته طلایی:** اگر `ss` نشان می‌دهد پورت گوش می‌دهد ولی از بیرون وصل نمی‌شوی، احتمالاً فایروال (یا Security Group ابری) جلوی آن را گرفته است.

## بخش ۷: فایروال — `ufw` در برابر `nftables`

در Ubuntu 26.04، `nftables` موتور اصلی فایروال در kernel است. `ufw` یک frontend ساده است که قوانین `nftables` تولید می‌کند.

### کدام را انتخاب کنم؟

| سناریو | ابزار |
|---|---|
| سرور ساده، پورت‌های معمولی | **UFW** ✅ |
| NAT، port forwarding، rate limiting دقیق | **nftables** |
| Performance بالا (بیش از 100k pps) | **nftables** |
| اسکریپت‌های قدیمی | iptables (به nftables مهاجرت کن) |

منبع:

### UFW — برای ۹۰٪ کارها

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing

# ⚠️ قبل از enable، SSH را باز کن وگرنه قفل می‌شوی
sudo ufw allow 22/tcp comment 'SSH'

sudo ufw allow 80,443/tcp comment 'Web'
sudo ufw allow from 192.168.1.0/24 to any port 5432 comment 'Postgres internal'

sudo ufw enable
sudo ufw status verbose
```

**قانون طلایی:** همیشه قبل از `ufw enable` پورت SSH را باز کن.

### nftables — برای کنترل دقیق

```bash
sudo nft add table inet my_filter
sudo nft add chain inet my_filter input '{ type filter hook input priority 0; policy drop; }'

sudo nft add rule inet my_filter input ct state established,related accept
sudo nft add rule inet my_filter input iif lo accept
sudo nft add rule inet my_filter input tcp dport { 22, 80, 443 } accept
```

ذخیره ماندگار:

```bash
sudo nft list ruleset > /etc/nftables.conf
sudo systemctl enable --now nftables
```

**⚠️ هشدار:** اگر UFW فعال است، مستقیماً `nftables` را دستکاری نکن. اول `sudo ufw disable`، بعد `nftables` را تنظیم کن.

### مشاهده قوانین فعال

```bash
sudo ufw status verbose
sudo nft list ruleset
```

## بخش ۸: ابزارهای اضافی که در DevOps لازم می‌شوند

| ابزار | کار | نمونه |
|---|---|---|
| `curl -v` | دیباگ کامل HTTP/TLS/DNS در یک خط | `curl -v https://example.com` |
| `nc -zv` | تست پورت TCP | `nc -zv host 443` |
| `nmap -sT` | اسکن پورت | `nmap -p 80,443 host` |
| `mtr` | traceroute + ping | `mtr --report 8.8.8.8` |
| `tcpdump` | گرفتن بسته | `sudo tcpdump -i eth0 -n port 80` |

## پروژه جلسه ۷

**سناریو:** یک سرور Ubuntu 26.04 تازه نصب کرده‌ای. می‌خواهی مطمئن شوی شبکه سالم است، یک وب‌سرور ساده بالا بیاوری، و فایروال را طوری تنظیم کنی که فقط SSH و HTTP در دسترس باشند.

1. با `ip -brief addr` اینترفیس و IP را ببین.
2. با `ip route` gateway را پیدا کن و با `ping` تست کن.
3. با `dig +short google.com @8.8.8.8` و `resolvectl query google.com` DNS را تست کن.
4. یک وب‌سرور ساده بالا بیاور:
   ```bash
   sudo apt install nginx -y
   sudo ss -tulpn | grep :80
   ```
5. فایروال را با UFW تنظیم کن (SSH + HTTP) و تست کن.
6. با `tcpdump` ترافیک DNS را ببین:
   ```bash
   sudo tcpdump -i any -n port 53
   ```
7. (اختیاری) یک قانون `nftables` ساده بنویس و با `nft list ruleset` ببین.

## اشتباهات رایج (این‌ها را نکن!)

| ❌ اشتباه | ✅ درست |
|---|---|
| `ifconfig` و `netstat` | `ip` و `ss` |
| `ufw enable` قبل از باز کردن SSH | اول `ufw allow 22/tcp` |
| `chmod 777` معادل شبکه‌ای: باز کردن همه پورت‌ها | حداقل پورت لازم را باز کن |
| `ping` جواب نداد → «شبکه خراب است» | ICMP ممکن است بلاک شده باشد؛ TCP را تست کن |
| DNS را با `nslookup` چک کردن | `dig` دقیق‌تر است |
| نادیده گرفتن Security Group در ابر | هم فایروال host و هم SG ابری را چک کن |

## ارتباط با جلسات قبل و بعد

- **جلسه ۴ (SSH):** `ufw allow 22/tcp` همان پورتی است که در جلسه ۴ امن کردی. حالا می‌دانی چرا بدون این قانون، SSH قطع می‌شود.
- **جلسه ۵ (Bash):** اسکریپت `server-health.sh` می‌تواند با `ss` و `dig` شبکه را هم چک کند.
- **جلسه ۶ (Git):** کانفیگ‌های فایروال را در Git نگه‌داری کن (IaC).
- **جلسه ۸ (Docker):** هر کانتینر پورت خودش را دارد؛ `ss` و `nftables` همان‌جا هم به کارت می‌آید.
