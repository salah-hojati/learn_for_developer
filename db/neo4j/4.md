Welcome to **Step 3: Master the Core Neo4j Java Driver**. This is where you move from running manual queries to building robust, programmatic data access.

We'll focus on the three core components of the driver: the **Driver**, the **Session**, and the **Transaction**, and how to manage them correctly.

### 📦 The Hierarchy: Driver → Session → Transaction

Understanding this flow is key to using the driver effectively.

| Component | Responsibility | Lifecycle | Thread-Safety |
| :--- | :--- | :--- | :--- |
| **`Driver`** | Manages connection pools and holds database config. | **One per application** (long-lived, expensive to create). | **Thread-safe** |
| **`Session`** | A logical container for a series of transactions. | **Short-lived** (create per unit of work, always close). | **NOT thread-safe** |
| **`Transaction`** | An atomic unit of work (commit or rollback). | **Short-lived** (created within a session). | **NOT thread-safe** |

The recommended pattern is: create **one** `Driver` for your app, then create a **new** `Session` for each specific task or request, and perform your database work inside a **managed transaction** within that session.

### 🔌 1. Connecting: The Driver

The `Driver` is the entry point. You should create a single instance for your entire application and reuse it, as it is thread-safe and expensive to create.

```java
import org.neo4j.driver.*;

public class Neo4jDriverProvider implements AutoCloseable {
    private final Driver driver;

    public Neo4jDriverProvider(String uri, String user, String password) {
        this.driver = GraphDatabase.driver(uri, AuthTokens.basic(user, password));
        // Fail fast if the connection is not valid
        this.driver.verifyConnectivity();
    }

    public Driver getDriver() {
        return driver;
    }

    @Override
    public void close() {
        driver.close();
    }
}
```
Best Practice: Wrap the driver in a class that implements `AutoCloseable` so you can manage its lifecycle cleanly (e.g., with try-with-resources or a framework's shutdown hook).

### 📨 2. Managing Work: Sessions and Managed Transactions

This is the most important section. **Managed transactions** are the recommended way to execute queries. They handle transaction boundaries (begin/commit/rollback) automatically and include **built-in retry logic** for transient errors like network blips or cluster role changes.

#### How Managed Transactions Work
You call `session.executeRead()` or `session.executeWrite()`, passing a **callback function**. The driver supplies a `TransactionContext` to this callback, which you use to run your queries.

**Key Rules:**
*   **Process results inside the callback.** You must consume the `Result` within the transaction function. Returning the raw `Result` object is an error, as the connection is released when the callback ends.
*   **Design for idempotency.** Because the driver may retry the entire transaction function if a transient error occurs, the operations within it should be repeatable without side effects.

#### Example: `executeRead` (for retrieving data)

```java
try (var session = driver.session(SessionConfig.builder().withDatabase("neo4j").build())) {
    // executeRead returns the value produced by the lambda
    List<String> names = session.executeRead(tx -> {
        var result = tx.run(
            "MATCH (p:Person) WHERE p.age > $minAge RETURN p.name AS name",
            Map.of("minAge", 25)
        );
        // Process the result INSIDE the callback and return a simple value
        return result.list(record -> record.get("name").asString());
    });
    names.forEach(System.out::println);
}
```
In this example, `tx -> { ... }` is the transaction function. The driver begins a transaction, runs the lambda, and then commits it automatically. If an exception is thrown, the transaction is rolled back and retried if the error is deemed transient.

#### Example: `executeWrite` (for creating, updating, or deleting data)

```java
try (var session = driver.session(SessionConfig.builder().withDatabase("neo4j").build())) {
    Long nodeId = session.executeWrite(tx -> {
        var result = tx.run(
            "CREATE (p:Person {name: $name, age: $age}) RETURN id(p) AS nodeId",
            Map.of("name", "Alice", "age", 30)
        );
        // Consume the result and return the generated ID
        return result.single().get("nodeId").asLong();
    });
    System.out.println("Created node with ID: " + nodeId);
}
```
`executeWrite` is used for any operation that modifies the graph. The retry logic is crucial here to ensure your writes eventually succeed.

> **Note on Deprecated Methods:** If you see older tutorials using `session.readTransaction()` or `session.writeTransaction()`, know that these are deprecated in favor of `executeRead()` and `executeWrite()` in driver v5 and v6.

### ⚙️ 3. Fine-Grained Control: Explicit Transactions

For advanced use cases where you need to manage the transaction boundary manually across multiple method calls, you can use **explicit (unmanaged) transactions**. However, you lose the automatic retry logic of managed transactions.

You must manually call `commit()` to persist changes; otherwise, the transaction is **rolled back by default** when the try-with-resources block closes.

```java
try (var session = driver.session(SessionConfig.builder().withDatabase("neo4j").build());
     var tx = session.beginTransaction()) {
    try {
        tx.run("CREATE (p:Person {name: $name})", Map.of("name", "Bob")).consume();
        // ... more client logic or queries ...
        tx.commit(); // Persist the changes
    } catch (Exception e) {
        tx.rollback(); // Explicit rollback on error (optional; close() does it too)
        throw e;
    }
}
```
Use explicit transactions sparingly, typically only when you have complex logic that spans multiple methods and you need precise control over commit/rollback.

### 📊 4. Handling Results and Data Types

The `Result` object is a lazy stream of `Record` objects.

| Method | Purpose |
| :--- | :--- |
| `result.list()` | Loads all records into a `List<Record>` (buffers all in memory) |
| `result.single()` | Returns the single record, throws if there are 0 or >1 |
| `result.consume()` | **Consumes the entire result** without reading it and returns a `ResultSummary` |
| `result.stream()` | Returns a Java `Stream<Record>` for functional-style processing |

Each `Record` is a map of keys to `Value` objects. You convert a `Value` to a Java type using the `asX()` methods (e.g., `asString()`, `asLong()`, `asObject()`).

#### Mapping to Java Objects (Records)
The driver can automatically map a query result to a **Java Record**. The record's components must match the query's return keys exactly (case-sensitive).

```java
// Define a Java Record that matches the RETURN clause
public record PersonDTO(String name, int age) {}

// In your transaction:
List<PersonDTO> people = session.executeRead(tx -> {
    var result = tx.run("MATCH (p:Person) RETURN p.name AS name, p.age AS age");
    return result.list(record -> record.as(PersonDTO.class)); // Auto-mapping
});
```
This feature is powerful for keeping your code clean and type-safe.

### 🛡️ 5. Key Best Practices for the Driver

*   **Always Close Sessions:** Sessions are lightweight, but they hold a connection from the pool. Use try-with-resources to ensure they are closed.
*   **Use Managed Transactions by Default:** Rely on `executeRead`/`executeWrite` for automatic retries and simpler code.
*   **Process Results Inside the Callback:** Never return a `Result` object from a transaction function. Extract the data you need within the callback.
*   **Use Parameterized Queries:** Always use `$param` placeholders and pass parameters via a `Map`. This prevents injection and enables query plan caching.
*   **Specify the Database:** If your Neo4j instance has multiple databases, configure the session with `.withDatabase("your-db-name")` to avoid an extra network round-trip for discovery.

### 💎 Summary

You've now learned the core pattern for working with the Neo4j Java Driver:

1.  Create **one `Driver`** for your application.
2.  Open a **new `Session`** for each unit of work.
3.  Perform all database operations inside a **managed transaction** (`executeRead` or `executeWrite`).
4.  **Process the `Result`** within the transaction callback and return simple Java values or mapped objects.

This foundation will serve you well, whether you continue with the raw driver or move on to **Step 4: Spring Data Neo4j**, which builds on these concepts with even higher-level abstractions.
