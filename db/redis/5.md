Based on your existing `StringRedisTemplate` setup, the two most valuable next steps are **declarative caching (`@Cacheable`)** and **distributed locking**. The first solves "repeated queries slow down responses"; the second solves "multiple instances modifying the same resource concurrently." Both are extremely common in Spring Boot interviews and real projects.

---

## Route 1: Declarative Caching (`@Cacheable`) — Let Method Results Flow Into Redis Automatically

Your `RedisController` so far does manual `SET`/`GET`. The value of `@Cacheable` is that **the method's return value is automatically written to Redis, and subsequent calls with the same arguments hit the cache directly — the method body never executes**.

### 1. Add the dependency and enable caching

You already have `spring-boot-starter-data-redis` in `pom.xml`. Add `spring-boot-starter-cache`:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
```

Add `@EnableCaching` on the main class:

```java
@SpringBootApplication
@EnableCaching
public class RedisLearnApplication { ... }
```

### 2. Configure a Redis cache with a TTL (avoid the "never expires" default trap)

Spring Boot's Redis cache **has no TTL by default** — entries stay in Redis forever. It also uses JDK serialization by default, so keys/values look like binary garbage in `redis-cli`. Fix both in `application.yml` at once:

```yaml
spring:
  cache:
    type: redis
    redis:
      time-to-live: 5m          # global default TTL, adjust as needed
      cache-null-values: true   # helps prevent cache penetration; usually keep on
      key-prefix: "myapp:"
      use-key-prefix: true
```

> ⚠️ **Critical trap**: Once you declare your own `RedisCacheConfiguration` bean in code, the yml properties like `time-to-live` and `key-prefix` **silently stop working**. If you later need JSON serialization and must define a custom bean, you'll have to re-set every option inside that bean manually.

### 3. A full CRUD example using the three annotations

Below, an in-memory `Map` simulates a "database" so you can clearly see cache hits vs. misses:

```java
@Service
public class BookService {

    // Simulated database
    private final Map<String, Book> db = new ConcurrentHashMap<>();

    @Cacheable(value = "books", key = "#isbn")
    public Book findByIsbn(String isbn) {
        simulateSlowDb();
        return db.get(isbn); // only runs on cache miss
    }

    @CachePut(value = "books", key = "#book.isbn")
    public Book saveOrUpdate(Book book) {
        db.put(book.getIsbn(), book);
        return book; // method body always runs; return value written/overwritten into cache
    }

    @CacheEvict(value = "books", key = "#isbn")
    public void delete(String isbn) {
        db.remove(isbn); // remove from DB and evict from cache
    }

    private void simulateSlowDb() {
        try { Thread.sleep(2000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public record Book(String isbn, String title) {}
}
```

**Controller**:

```java
@RestController
@RequestMapping("/books")
public class BookController {

    private final BookService service;
    public BookController(BookService service) { this.service = service; }

    @GetMapping("/{isbn}")
    public BookService.Book get(@PathVariable String isbn) {
        return service.findByIsbn(isbn);
    }

    @PostMapping
    public BookService.Book save(@RequestBody BookService.Book book) {
        return service.saveOrUpdate(book);
    }

    @DeleteMapping("/{isbn}")
    public String delete(@PathVariable String isbn) {
        service.delete(isbn);
        return "deleted";
    }
}
```

### 4. Verify the cache is actually working

1. **First** `GET /books/123` → takes ~2 seconds (`simulateSlowDb` runs).
2. **Second** `GET /books/123` → returns in **milliseconds**, method body not executed.
3. In IntelliJ's Redis console or `redis-cli` on Linux, run `KEYS myapp:books*` — you'll see something like `myapp:books::123`.
4. **Update** with `POST /books` (same isbn) → `@CachePut` overwrites the cache entry; next GET returns the new value immediately.
5. **Delete** with `DELETE /books/123` → next GET is back to ~2 seconds, because `@CacheEvict` removed the entry.

> `@Cacheable(sync = true)` makes concurrent requests execute the method body only once on a miss — this prevents cache stampede/breakdown. Advanced usage; you can revisit it later.

## Route 2: Distributed Locking — Protect Critical Sections From Concurrent Writes

A distributed lock answers this question: **when multiple app instances (or threads) modify the same shared resource simultaneously, how do we guarantee only one executes at a time?** Classic cases: stock deduction, flash sales, preventing duplicate submissions.

Recommended path: **first hand-write a "imperfect" version** to understand the principles and pitfalls, **then switch to Redisson** for the production-grade solution.

### Step 1: Hand-write `SET NX PX` + Lua release (to understand the principle)

Redis's `SET key value NX PX ttl` is an atomic "set only if not exists, with expiry" command. Implement it with `StringRedisTemplate`:

```java
@Component
public class SimpleRedisLock {

    private final StringRedisTemplate redis;
    private static final String UNLOCK_LUA =
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('del', KEYS[1]) " +
            "else return 0 end";

    public SimpleRedisLock(StringRedisTemplate redis) {
        this.redis = redis;
    }

    /** Returns a token if lock acquired; null if failed */
    public String tryLock(String key, Duration ttl) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redis.opsForValue().setIfAbsent(key, token, ttl);
        return Boolean.TRUE.equals(ok) ? token : null;
    }

    /** Only the caller holding the matching token can release — avoids deleting someone else's lock */
    public boolean unlock(String key, String token) {
        Long result = redis.execute(
                new DefaultRedisScript<>(UNLOCK_LUA, Long.class),
                List.of(key), token);
        return result != null && result > 0;
    }
}
```

**Why must release be in Lua?** If you did `GET` to check the token then `DEL`, the lock could expire between the two steps and get re-acquired by another thread — your `DEL` would then delete someone else's lock. A Lua script executes atomically inside Redis, avoiding this race.

**Limitations of the hand-written version** (exactly what Redisson solves): no reentrancy, no watchdog auto-renewal, no fair locking, complex behavior in cluster mode.

### Step 2: Redisson `RLock` (production-grade)

Add the dependency (`redisson-spring-boot-starter` auto-configures `RedissonClient`):

```xml
<dependency>
    <groupId>org.redisson</groupId>
    <artifactId>redisson-spring-boot-starter</artifactId>
    <version>3.23.4</version>
</dependency>
```

If auto-config doesn't pick up your `spring.data.redis` properties, declare a `RedissonClient` bean manually:

```java
@Configuration
public class RedissonConfig {
    @Bean(destroyMethod = "shutdown")
    public RedissonClient redissonClient() {
        Config config = new Config();
        config.useSingleServer()
              .setAddress("redis://192.168.1.100:6379")
              .setPassword("YourStrongPassword123");
        return Redisson.create(config);
    }
}
```

Use `RLock` in a service:

```java
@Service
public class StockService {

    private final RedissonClient redisson;
    private final StringRedisTemplate redis;

    public StockService(RedissonClient redisson, StringRedisTemplate redis) {
        this.redisson = redisson;
        this.redis = redis;
    }

    public String deduct(String goodsId, int count) {
        RLock lock = redisson.getLock("lock:stock:" + goodsId);
        try {
            // Wait up to 3s for the lock; auto-release after 10s (watchdog renews if business is still running)
            boolean locked = lock.tryLock(3, 10, TimeUnit.SECONDS);
            if (!locked) {
                return "System busy, please retry";
            }
            String raw = redis.opsForValue().get("stock:" + goodsId);
            int stock = raw == null ? 0 : Integer.parseInt(raw);
            if (stock < count) return "Insufficient stock";
            redis.opsForValue().set("stock:" + goodsId, String.valueOf(stock - count));
            return "Deducted, remaining " + (stock - count);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return "Thread interrupted";
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock(); // only releases the lock held by the current thread
            }
        }
    }
}
```

**What Redisson takes care of for you**:
- **Reentrancy**: the same thread can acquire the same lock multiple times; a counter is maintained automatically.
- **Watchdog**: if business logic runs longer than the initial lock TTL, Redisson auto-renews so the lock doesn't expire mid-execution.
- **Atomic release**: a Lua script guarantees "check owner + delete" happen atomically.

### Step 3: Verify with a concurrency test

```java
@GetMapping("/stock/concurrent-test")
public String concurrentTest() throws InterruptedException {
    redis.opsForValue().set("stock:A100", "100");
    int threads = 20;
    ExecutorService pool = Executors.newFixedThreadPool(threads);
    CountDownLatch latch = new CountDownLatch(threads);
    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            try {
                stockService.deduct("A100", 1);
            } finally {
                latch.countDown();
            }
        });
    }
    latch.await();
    pool.shutdown();
    return "Final stock: " + redis.opsForValue().get("stock:A100");
}
```

20 concurrent threads each deducting 1 — **the final stock must be `80`**. If it ends up as `81` or lower, the lock is broken. Add `Thread.sleep(100)` inside `deduct` to widen the concurrency window and make the effect more obvious.

### Which route to prioritize

| | Declarative Caching | Distributed Locking |
|---|---|---|
| **Why start here** | Tiny code change, one annotation and you see results, immediately useful on any query endpoint | Requires understanding concurrency, but unavoidable in interviews and real problems |
| **Suggested entry** | Run `@Cacheable` → `@CachePut` → `@CacheEvict` on `BookService` first | Hand-write `SETNX` + Lua to understand pitfalls, then switch to Redisson |
| **Observation tool** | IntelliJ Redis console watching `myapp:books::*` keys appear/disappear | Concurrency test endpoint + `redis-cli` watching `lock:stock:*` keys |

If time is limited, **do Route 1 first** — it's the least invasive and gives the fastest feedback. Route 2 can come later once you're comfortable with concurrency topics.
