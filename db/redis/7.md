Here is a deeper, hands-on guide for **Phase 1**. The goal is to move beyond simply memorizing commands and instead build a mental model of *how Redis thinks* — so that when you later use Java or Spring Boot, you understand exactly what the abstractions are doing underneath.

---

### 🔌 Step 0: Connect and Confirm You Are Talking to Redis

You already have Redis running in Docker on your Linux machine. Instead of running `redis-cli` inside the container, connect from your Windows terminal if you have `redis-cli` installed, or continue using `docker exec`. From your Linux host:

```bash
docker exec -it redis-server redis-cli -a YourStrongPassword123
```

Once you see the prompt `127.0.0.1:6379>`, type:

```
PING
```

The reply must be `PONG`. If it is not, stop and fix the connection before continuing. Every command below assumes you are at this interactive prompt.

> **Habit to build now:** Redis commands are **case-insensitive** (`set` and `SET` are identical), but keys are **case-sensitive** (`user:1` and `User:1` are different keys). Use lowercase for commands and a consistent naming convention (like `object:id:field`) for your keys.

### 🧱 Step 1: Master the Five Core Data Structures (with Real Use Cases)

Redis is not just a key-value store — each key can hold a *specialized data structure*, and choosing the right one is the single most important design decision you will make. For each structure below, run the commands yourself, then pause and ask: *"What real problem does this solve?"*

#### 1. String — The Swiss Army Knife

A String can hold text, numbers, or binary data (up to 512 MB). This is your go-to for caching, counters, and simple values.

```bash
SET username "alice"
GET username
INCR page_views
INCR page_views
GET page_views          # "2"
SET session:123 "user_data" EX 3600   # expires in 1 hour
```

**Why it matters:** `INCR` is **atomic** — even if 1,000 application instances run `INCR` at the same time, no increments are lost. This is the foundation for rate limiting, page-view counters, and even simple distributed locks (`SET key value NX`).

**Use when:** caching HTML/JSON, counters, session tokens, distributed locks.

#### 2. Hash — A Mini-Dictionary Inside One Key

A Hash stores field-value pairs, perfect for representing an object without serializing the entire thing every time you update one field.

```bash
HSET user:42 name "Alice" email "alice@example.com" age 30
HGET user:42 name         # "Alice"
HGETALL user:42
HINCRBY user:42 age 1
```

**Why it matters:** If you stored the user as a single JSON String, updating `age` would require reading, parsing, modifying, and rewriting the entire blob. With a Hash, `HINCRBY` changes only that field — efficient and atomic.

**Use when:** user profiles, product data, configuration objects — anything with multiple attributes.

#### 3. List — Ordered, Fast at Both Ends

A List is an ordered sequence. Push to the left (head) or right (tail); pop from either end. This makes it a natural queue *or* stack.

```bash
RPUSH jobs "send_email" "resize_image" "send_sms"
LPOP jobs                 # "send_email" (FIFO queue behavior)
RPOP jobs                 # "send_sms"   (LIFO stack behavior)
LRANGE jobs 0 -1
BLPOP jobs 0              # blocks until an item arrives
```

**Why it matters:** `BLPOP` (blocking pop) is how you build a **reliable worker queue** without polling — the worker sleeps until a job appears.

**Use when:** job queues, activity feeds, chat history, undo stacks.

#### 4. Set — Unique Collections with Fast Membership Checks

A Set is an *unordered* collection of unique strings. Adding a duplicate is a no-op.

```bash
SADD tags "redis" "nosql" "cache"
SADD tags "redis"         # no-op, already present
SISMEMBER tags "nosql"    # 1 (exists)
SMEMBERS tags
SCARD tags                # 3
SINTER set1 set2          # members in both
SUNION set1 set2          # all members from both
SDIFF set1 set2           # in set1 but not set2
```

**Why it matters:** Set operations like `SINTER` run server-side, so "find mutual friends" or "which users have both permission A and permission B" becomes a single fast command instead of fetching and intersecting in application code.

**Use when:** tracking unique visitors, tags, online users, mutual friends, permission sets.

#### 5. Sorted Set — The Leaderboard Powerhouse

A Sorted Set is like a Set, but every member has a numeric **score**, and members are automatically kept sorted by that score.

```bash
ZADD scores 9500 "alice" 8200 "bob" 11000 "carol"
ZREVRANGE scores 0 -1 WITHSCORES   # highest score first
ZREVRANK scores "alice"            # rank (0 = top)
ZSCORE scores "alice"              # 9500
ZINCRBY scores 500 "alice"         # add to score
```

**Why it matters:** Getting the top 10 players from a million-entry leaderboard is `O(log N)` — you never sort the whole set. The same structure powers rate limiter windows and priority queues.

**Use when:** leaderboards, priority queues, time-series data, rate limiter windows, autocomplete.

### ⏳ Step 2: Key Management and TTL — The Heart of Caching

Expiration is what makes Redis a *cache* rather than just a database. Understand it deeply now, and `@Cacheable` later will feel obvious.

```bash
SET cache:homepage "<html>..." EX 300   # expires in 5 minutes
TTL cache:homepage                      # remaining seconds
EXPIRE cache:homepage 600               # reset TTL to 10 minutes
PERSIST cache:homepage                  # remove expiration (permanent)
```

**Interpreting `TTL`:** `-1` means the key exists but has **no expiration**; `-2` means the key **does not exist**. This distinction matters enormously in production — a cache key with `TTL -1` is a memory leak waiting to happen.

**Practice exercise:** Set a key with `EX 10`, then run `TTL` immediately, wait 5 seconds, and run it again. Watch the number decrease. When it reaches zero, `GET` returns `nil` — the key is gone. This is the exact lifecycle that happens behind every Spring `@Cacheable` annotation.

### 📡 Step 3: Pub/Sub — Your First Taste of Messaging

Publish/Subscribe is a lightweight messaging pattern: publishers send messages to a **channel** without knowing who is listening; subscribers receive every message on channels they have subscribed to.

**Hands-on requires two separate `redis-cli` terminals.**

**Terminal 1 (subscriber):**
```bash
SUBSCRIBE temperature
```
The prompt enters **subscribed mode** and waits. In this mode, `redis-cli` will not accept normal commands — only `SUBSCRIBE`, `PSUBSCRIBE`, `UNSUBSCRIBE`, `PING`, and `QUIT`.

**Terminal 2 (publisher):**
```bash
PUBLISH temperature "22.5"
```

**Back in Terminal 1**, you will see a message array containing the channel name and the payload.

**Why it matters:** This is the simplest form of event-driven communication. Later, in Spring Boot, you will use `RedisMessageListenerContainer` to consume these messages. Understanding the *raw* pattern first — channel, publisher, subscriber — makes the Spring abstraction trivial to learn.

> **Important limitation to remember:** Pub/Sub is **fire-and-forget**. If no subscriber is listening when a message is published, the message is lost forever. Redis **Streams** (which you can explore later) solve this with persistence and consumer groups.

### 💾 Step 4: Persistence — How Redis Survives a Restart

You already configured `--save 60 1` in your `docker-compose.yml`. Now understand what that actually does.

Redis has two main persistence strategies:

| | **RDB (Snapshot)** | **AOF (Append-Only File)** |
|---|---|---|
| **What it does** | Periodically forks a child and writes a point-in-time snapshot of the dataset to disk | Logs every write command; on restart, replays the log |
| **Durability** | You may lose the last few seconds/minutes of writes | Much stronger (configurable fsync policy) |
| **File size / restart speed** | Compact, fast restart | Larger, slower restart |
| **Your current setup** | `--save 60 1` = snapshot if at least 1 key changed in 60 seconds | **Not enabled** |

**Manual snapshot commands to try:**
```bash
BGSAVE       # background (non-blocking) snapshot — the one you should use
LASTSAVE     # Unix timestamp of the last successful save
```

`SAVE` also exists but **blocks the entire Redis server** while it writes — avoid it in production.

**Why this matters for your learning:** RDB is why your `redis_data` Docker volume exists. Restart the container (`docker compose restart redis`) and check whether your keys are still there. They will be, because the RDB snapshot was written to the volume. When you later use Redis purely as a *cache*, you may deliberately choose **not** to persist — because cached data can always be recomputed.

### 🎯 Step 5: A Progressive Exercise Plan (Do These in Order)

Reading commands is not learning. These exercises force you to *combine* structures and think about design.

**Exercise A — Session Store (String + TTL)**
1. Create `session:token:abc123` with value `user:42` and a TTL of 30 minutes.
2. Verify the TTL decreases over time.
3. Simulate "logout" by deleting the key.
4. Confirm `GET` returns `nil`.

**Exercise B — User Profile Updates (Hash)**
1. Create a Hash `user:100` with `name`, `email`, and `login_count`.
2. Increment `login_count` three times.
3. Retrieve only the `name` and `email` in one command (`HMGET`).
4. Delete only the `email` field and confirm the rest of the Hash survives.

**Exercise C — A Simple Job Queue (List)**
1. Push three "jobs" onto a List.
2. Pop one from the front (`LPOP`) and one from the back (`RPOP`). Explain the difference in behavior.
3. Use `BLPOP` with a 5-second timeout on an empty list. Observe what happens when the timeout expires.

**Exercise D — Leaderboard (Sorted Set)**
1. Add five players with scores.
2. Get the top three (`ZREVRANGE ... 0 2 WITHSCORES`).
3. Find one player's rank (`ZREVRANK`).
4. Increase a player's score by 500 (`ZINCRBY`) and verify their rank changed.

**Exercise E — Pub/Sub (Two Terminals)**
1. Subscribe to `news` in one terminal.
2. Publish three messages from the other terminal.
3. Unsubscribe (or `Ctrl-C`) and publish again. Confirm the message is lost — this is the fire-and-forget behavior you need to internalize.

**Exercise F — Persistence Observation**
1. Set a few keys.
2. Run `BGSAVE`.
3. Restart the Redis container.
4. Check whether your keys survived. If they did, you have just observed RDB persistence working through your Docker volume.

### 🧠 The Mental Model to Carry Into Phase 2

When you move to Java, you will not be learning new Redis concepts — you will be learning **how to express these exact same operations in code**. The mapping will be direct:

- `SET` / `GET` → `jedis.set()` / `jedis.get()` or `redisTemplate.opsForValue().set()`
- `HSET` → `opsForHash().put()`
- `EXPIRE` → passing a `Duration` to `set()`
- `SUBSCRIBE` → `RedisMessageListenerContainer`

The developers who struggle with Spring Data Redis are usually the ones who never built this CLI-level intuition. Spending real time in Phase 1 pays for itself many times over in Phase 2 and 3.
