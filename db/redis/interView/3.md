# **Cache-Aside، Write-Through و TTL / Eviction در Redis**

این سه مفهوم از مباحث مهم طراحی سیستم‌های Java، Spring Boot، Redis و Microservice هستند.

برای درک آن‌ها، ابتدا فرض کن Oracle دیتابیس اصلی ما است و Redis به‌عنوان Cache استفاده می‌شود:

**Java Application / Spring Boot**

**Redis Cache**

Fast access

**Oracle DB**

Persistent source of truth

هدف این معماری:

- کاهش فشار روی Database
- کاهش Latency
- پاسخ سریع به درخواست‌ها
- افزایش Scalability

# **1. Cache-Aside (Lazy Loading)**

## **مفهوم**

در الگوی Cache-Aside، خود Application مسئول مدیریت Cache است.

وقتی برنامه می‌خواهد اطلاعاتی را بخواند:

1. ابتدا Redis را بررسی می‌کند.
2. اگر داده وجود داشت، آن را از Redis برمی‌گرداند (Cache Hit).
3. اگر داده وجود نداشت، از Database می‌خواند (Cache Miss).
4. داده را در Redis ذخیره می‌کند.
5. نتیجه را به کاربر برمی‌گرداند.

## **جریان Cache-Aside**

**1. Client Request**

**2. Application → Redis**

**3. Cache Hit?**

**YES**

Return cached data

**NO**

Read from Oracle

**4. Read Oracle → Save in Redis → Return**

## **مثال واقعی**

فرض کن اطلاعات محصول شماره 1001 را می‌خواهیم.

### **مرحله اول: بررسی Redis**

```
GET product:1001
```

اگر موجود باشد:

```
{
  "id": 1001,
  "name": "Laptop",
  "price": 1200
}
```

Application مستقیم نتیجه را برمی‌گرداند و Oracle درگیر نمی‌شود.

### **مرحله دوم: Cache Miss**

اگر Redis پاسخ ندهد:

```
Redis → Key Not Found
```

Application از Oracle Query می‌زند:

```
SELECT ID, NAME, PRICE
FROM PRODUCTS
WHERE ID = 1001;
```

سپس نتیجه را در Redis ذخیره می‌کند:

```
SET product:1001 '{"id":1001,"name":"Laptop","price":1200}' EX 600
```

TTL این Cache برابر 600 ثانیه است.

## **مزایا و معایب**

| مزایا                                  | معایب                              |
| -------------------------------------- | ---------------------------------- |
| فقط داده‌های موردنیاز Cache می‌شوند    | اولین درخواست Cache Miss کندتر است |
| Application کنترل Cache را دارد        | Cache ممکن است Stale شود           |
| Redis و DB وابستگی مستقیم به هم ندارند | Cache Stampede ممکن است رخ دهد     |
| مناسب Read-heavy systems               | مدیریت Cache Invalidation لازم است |

### **چه زمانی استفاده می‌کنیم؟**

- Product Catalog
- User Profile
- تنظیمات
- اطلاعاتی که زیاد خوانده می‌شوند و کمتر تغییر می‌کنند
- سیستم‌هایی که Read بسیار بیشتر از Write دارند

# **2. Write-Through Cache**

## **مفهوم**

در Write-Through، هنگام نوشتن داده، Application داده را در Cache و Database به‌روزرسانی می‌کند.

هدف این است که Cache پس از عملیات Write، اطلاعات جدید را داشته باشد و درخواست‌های Read بعدی تا حد امکان به داده قدیمی برخورد نکنند.

## **جریان عملیات**

فرض کن قیمت یک محصول تغییر می‌کند.

```
Client
  |
  v
Application
  |
  +----> Oracle DB (Update)
  |
  +----> Redis (Update Cache)
```

مثلاً:

### **1. تغییر در Oracle**

```
UPDATE PRODUCTS
SET PRICE = 1500
WHERE ID = 1001;
```

### **2. تغییر در Redis**

```
SET product:1001 '{"id":1001,"name":"Laptop","price":1500}' EX 600
```

از این به بعد Readها می‌توانند قیمت جدید را از Redis دریافت کنند.

## **مزایا**

- Cache بعد از Write موفق به‌روز می‌شود.
- احتمال خواندن داده قدیمی کاهش می‌یابد.
- برای داده‌هایی که Read زیادی دارند مناسب است.

## **معایب**

- Write Latency بیشتر می‌شود.
- هر Write نیاز به هماهنگی Cache و DB دارد.
- احتمال Failure بین دو عملیات وجود دارد.
- مدیریت Transaction بین Redis و Oracle پیچیده است.

نکته مهم معماری:

Redis و Oracle معمولاً در یک Transaction اتمیک مشترک قرار ندارند.

ممکن است:

1. Update در Oracle موفق شود.
2. Application قبل از Update Redis Crash کند.
3. Redis همچنان مقدار قبلی را داشته باشد.

بنابراین Write-Through به‌تنهایی تضمین Consistency کامل بین Redis و Oracle نمی‌دهد.

برای کاهش این مشکل، می‌توان از Cache Invalidation، Retry، Transactional Outbox، CDC یا راهکارهای هماهنگ‌سازی استفاده کرد.

# **3. TTL (Time To Live)**

## **TTL چیست؟**

TTL مشخص می‌کند یک Key چه مدت در Redis معتبر بماند.

پس از پایان TTL، Key منقضی می‌شود و دیگر قابل استفاده به‌عنوان Cache نیست؛ Redis آن را در زمان مناسب پاک‌سازی می‌کند.

مثلاً:

```
SET product:1001 '{"id":1001,"price":1500}' EX 300
```

این Cache به مدت 300 ثانیه (5 دقیقه) اعتبار دارد.

### **دستورات TTL**

| دستور               | کاربرد                                      |
| ------------------- | ------------------------------------------- |
| `EXPIRE key 60`     | تعیین TTL به ثانیه                          |
| `PEXPIRE key 60000` | تعیین TTL به میلی‌ثانیه                     |
| `TTL key`           | مشاهده زمان باقی‌مانده به ثانیه             |
| `PTTL key`          | مشاهده زمان باقی‌مانده به میلی‌ثانیه        |
| `PERSIST key`       | حذف TTL و دائمی‌کردن Key تا حذف یا Eviction |
| `EX`                | تعیین TTL هنگام SET، برحسب ثانیه            |
| `PX`                | تعیین TTL هنگام SET، برحسب میلی‌ثانیه       |

مثال:

```
SET session:1001 "logged-in" EX 1800
```

Session تا 30 دقیقه معتبر است.

مشاهده TTL:

```
TTL session:1001
```

ممکن است خروجی:

```
(integer) 1200
```

یعنی 1200 ثانیه باقی مانده است.

## **چرا TTL مهم است؟**

فرض کن اطلاعات محصول را Cache کرده‌ای:

```
Redis:
Product 1001 → Price = 1200
```

اما در Oracle قیمت به 1500 تغییر می‌کند.

اگر Cache را Update یا Invalidate نکنیم، کاربر همچنان ممکن است قیمت 1200 را دریافت کند.

TTL کمک می‌کند داده Cache شده بعد از مدت مشخصی منقضی شود و در درخواست بعدی مجدداً از Database خوانده شود.

اما:

> TTL به‌تنهایی تضمین نمی‌کند Cache همیشه تازه باشد؛ فقط حداکثر زمان ماندن آن را محدود می‌کند.

# **4. Eviction چیست؟**

TTL و Eviction با هم تفاوت دارند.

### **TTL**

می‌گوید:

> این Key بعد از چه مدت باید منقضی شود؟

### **Eviction**

می‌گوید:

> وقتی حافظه Redis پر شده است، کدام Key را حذف کنم تا فضای جدید ایجاد شود؟

Redis می‌تواند با تنظیم `maxmemory` محدودیت حافظه داشته باشد. هنگامی که Redis به سقف حافظه برسد، بسته به `maxmemory-policy`، ممکن است Keyها را حذف کند یا Writeهای جدید را رد کند.&#x20;

## **5. انواع Eviction Policy**

Policyهای مهم Redis

| Policy            | عملکرد                                                                   |
| ----------------- | ------------------------------------------------------------------------ |
| `noeviction`      | Key حذف نمی‌شود؛ در صورت پرشدن حافظه، Writeهای جدید ممکن است Error بدهند |
| `allkeys-lru`     | Keyهایی که مدت بیشتری از آخرین دسترسیشان گذشته حذف می‌شوند               |
| `allkeys-lfu`     | Keyهایی که کمتر استفاده شده‌اند حذف می‌شوند                              |
| `allkeys-random`  | Keyهای تصادفی حذف می‌شوند                                                |
| `volatile-lru`    | LRU فقط روی Keyهایی که TTL دارند                                         |
| `volatile-lfu`    | LFU فقط روی Keyهایی که TTL دارند                                         |
| `volatile-random` | حذف تصادفی از Keyهای دارای TTL                                           |
| `volatile-ttl`    | Keyهایی با TTL باقی‌مانده کمتر، کاندید حذف می‌شوند                       |

این Policyها در مستندات Redis توضیح داده شده‌اند.&#x20;

## **6. تفاوت LRU و LFU**

این سؤال در مصاحبه بسیار رایج است.

### **LRU — Least Recently Used**

Keyهایی حذف می‌شوند که مدت بیشتری از آخرین استفاده‌شان گذشته است.

مثال:

| Key | آخرین استفاده |
| --- | ------------- |
| A   | 1 ثانیه پیش   |
| B   | 2 دقیقه پیش   |
| C   | 10 ساعت پیش   |

اگر Redis نیاز به حذف داشته باشد، C احتمالاً کاندید حذف مناسب‌تری است.

```
LRU → چه چیزی اخیراً استفاده نشده؟
```

### **LFU — Least Frequently Used**

Keyهایی حذف می‌شوند که تعداد دفعات استفاده کمتری داشته‌اند.

| Key | تعداد استفاده |
| --- | ------------- |
| A   | 1000          |
| B   | 20            |
| C   | 2             |

در این مثال C احتمالاً کاندید حذف است.

```
LFU → چه چیزی کمتر استفاده شده؟
```

### **چه زمانی LRU و چه زمانی LFU؟**

- `LRU`: زمانی که الگوی دسترسی متغیر است و داده‌های اخیراً استفاده‌شده احتمالاً دوباره استفاده می‌شوند.
- `LFU`: زمانی که تعدادی Key دائماً محبوب هستند و می‌خواهیم Keyهای پرمصرف در Cache باقی بمانند، حتی اگر لحظه‌ای کمتر استفاده شوند.

Redis در پیاده‌سازی LRU و LFU از الگوریتم‌های تقریبی استفاده می‌کند، نه لزوماً پیاده‌سازی کامل و دقیق این الگوریتم‌ها.&#x20;

# **7. تنظیم Eviction در Redis**

مثلاً در `redis.conf`:

```
maxmemory 512mb
maxmemory-policy allkeys-lru
```

معنی:

- Redis حداکثر 512MB برای Memory Limit در نظر می‌گیرد.
- وقتی به محدودیت حافظه برسد، Keyهایی که کمتر اخیراً استفاده شده‌اند، کاندید حذف می‌شوند.

یا برای Cacheهایی که TTL دارند:

```
maxmemory 512mb
maxmemory-policy volatile-lru
```

در این حالت Redis فقط Keyهای دارای TTL را برای Eviction انتخاب می‌کند. اگر هیچ Key دارای TTL وجود نداشته باشد، رفتار `volatile-*` مشابه `noeviction` خواهد بود.&#x20;

اگر Redis فقط برای Cache استفاده می‌شود، معمولاً انتخاب‌هایی مانند:

# **8. مقایسه Cache-Aside و Write-Through**

| ویژگی         | Cache-Aside                        | Write-Through                                     |
| ------------- | ---------------------------------- | ------------------------------------------------- |
| Cache در Read | در صورت Miss پر می‌شود             | معمولاً Cache از قبل یا هنگام Write به‌روز می‌شود |
| Read          | Redis، سپس DB در Miss              | معمولاً Redis                                     |
| Write         | DB و سپس Cache Invalidation/Update | DB و Cache هر دو به‌روز می‌شوند                   |
| مدیریت Cache  | Application                        | Application یا Cache Layer                        |
| اولین Read    | ممکن است کند باشد                  | در صورت موجود بودن Cache سریع                     |
| Consistency   | احتمال Stale Data                  | احتمال Stale Data در صورت Failure بین دو Write    |
| کاربرد        | Read-heavy سیستم‌ها                | سیستم‌هایی که Cache باید هنگام Write به‌روز شود   |

# **11. پیاده‌سازی در Spring Boot**

Spring Cache امکان پیاده‌سازی Cache-Aside را با کدنویسی بسیار کم فراهم می‌کند.

### **Dependency**

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

### **فعال کردن Cache**

```
@SpringBootApplication
@EnableCaching
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

### **Cache-Aside با&#x20;**`@Cacheable`

```
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Cacheable(value = "products", key = "#id")
    public Product findById(Long id) {
        return productRepository.findById(id)
                .orElseThrow(() ->
                        new RuntimeException("Product not found"));
    }
}
```

وقتی `findById(1001)` فراخوانی شود:

1. Spring ابتدا Cache را بررسی می‌کند.
2. اگر Key موجود باشد، Method اجرا نمی‌شود و مقدار Cache برگردانده می‌شود.
3. اگر Key موجود نباشد، Method اجرا می‌شود.
4. نتیجه Method در Cache ذخیره می‌شود.

یعنی در حالت Cache Hit، حتی Repository هم فراخوانی نمی‌شود.

### **Update و Invalidate**

```
@CacheEvict(value = "products", key = "#product.id")
public Product update(Product product) {
    return productRepository.save(product);
}
```

پس از Update موفق، Cache مربوط به محصول حذف می‌شود تا درخواست بعدی داده جدید را از DB خوانده و دوباره Cache کند.

### **حذف تمام Cacheها**

```
@CacheEvict(value = "products", allEntries = true)
public void clearProductCache() {
}
```

### **به‌روزرسانی Cache به‌جای حذف**

```
@CachePut(value = "products", key = "#product.id")
public Product update(Product product) {
    return productRepository.save(product);
}
```

`@CachePut` همیشه Method را اجرا می‌کند و نتیجه آن را در Cache قرار می‌دهد؛ برخلاف `@Cacheable` که در Cache Hit، Method را اجرا نمی‌کند.

نکته: `@CacheEvict` و `@CachePut` به‌تنهایی مشکل هماهنگی بین Commit دیتابیس و Redis را حل نمی‌کنند. در سیستم‌های حساس، ترتیب عملیات، Transaction، Failure و Retry را باید در معماری در نظر گرفت.

# **12. TTL در Spring Boot**

مثلاً می‌خواهیم TTL پیش‌فرض Cacheها 10 دقیقه باشد.

در `application.yml`:

```
spring:
  cache:
    type: redis
    redis:
      time-to-live: 600000
```

توجه: تنظیم TTL به نسخه Spring Boot وابسته است و این Property در برخی نسخه‌ها به‌صورت استاندارد وجود ندارد یا متفاوت است. در بسیاری از نسخه‌ها، تنظیم TTL از طریق `RedisCacheConfiguration` روش مطمئن‌تر و قابل‌کنترل‌تری است.

مثال برنامه‌نویسی:

```
@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager cacheManager(
            RedisConnectionFactory connectionFactory) {

        RedisCacheConfiguration config =
                RedisCacheConfiguration.defaultCacheConfig()
                    .entryTtl(Duration.ofMinutes(10))
                    .disableCachingNullValues();

        return RedisCacheManager.builder(connectionFactory)
                .cacheDefaults(config)
                .build();
    }
}
```

در این مثال Cacheها به‌صورت پیش‌فرض 10 دقیقه TTL دارند.

# **13. اگر در مصاحبه Senior بپرسند کدام الگو را انتخاب می‌کنی؟**

مثلاً:

> We have a Spring Boot application with Oracle as the main database and Redis as a cache. How would you implement caching?

پاسخ پیشنهادی:

> I would typically use the Cache-Aside pattern for read-heavy data. The application first checks Redis, and if the data is missing, it retrieves it from Oracle and stores it in Redis with an appropriate TTL.
>
> For write operations, I would update the database first and then invalidate or update the corresponding cache entry. I would also consider cache consistency, TTL, eviction policies, cache stampede, and failure scenarios.
>
> For Redis memory management, I would configure maxmemory and choose an appropriate eviction policy, such as LRU or LFU, based on the actual access pattern.
>
> I would monitor cache hit ratio, misses, evictions, memory usage, latency, and database load to evaluate whether the caching strategy is effective.

## **5 مفهوم کلیدی**

**Cache-Aside**

Read Cache → Miss → Read DB → Populate Cache

**Write-Through**

Write operation updates DB and Cache

**TTL**

مدت اعتبار هر Key

**Eviction**

حذف Keyها وقتی حافظه به محدودیت می‌رسد

**Cache Invalidation**

حذف یا به‌روزرسانی Cache پس از تغییر داده اصلی
