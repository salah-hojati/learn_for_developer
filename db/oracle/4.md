# 🔬 Phase 3 Deep Dive — PL/SQL at the Next Level

## 1. Block Structure, Scope & Nested Blocks

- Blocks can be **nested**. Inner blocks see outer variables; outer blocks **cannot** see inner variables.
- You can **label** blocks to qualify ambiguous names: `<<outer>>`.
- Variables declared in `DECLARE` are initialized to `NULL` unless you assign a value.

```sql
<<outer_block>>
DECLARE
   v_x NUMBER := 10;
BEGIN
   DECLARE
      v_x NUMBER := 20;   -- shadows outer v_x
   BEGIN
      DBMS_OUTPUT.PUT_LINE('inner v_x = ' || v_x);          -- 20
      DBMS_OUTPUT.PUT_LINE('outer v_x = ' || outer_block.v_x); -- 10
   END;
   DBMS_OUTPUT.PUT_LINE('outer v_x = ' || v_x);             -- 10
END;
/
```

**Common mistake:** assuming a variable declared in a nested block survives after `END;` — it doesn't.

## 2. Variables, Records & Collections

You already know `%TYPE` and `%ROWTYPE`. Now add:

- **`CONSTANT`** — value cannot change.
- **`RECORD`** — your own composite type.
- **Collections** — three kinds: associative arrays (index-by tables), nested tables, VARRAYs.

```sql
DECLARE
   TYPE t_emp_rec IS RECORD (
      id   employees.employee_id%TYPE,
      name employees.first_name%TYPE,
      sal  employees.salary%TYPE
   );
   v_emp t_emp_rec;

   TYPE t_names IS TABLE OF employees.first_name%TYPE
      INDEX BY PLS_INTEGER;
   v_names t_names;
BEGIN
   v_emp.id := 100; v_emp.name := 'Steven'; v_emp.sal := 24000;
   v_names(1) := 'Steven';
   v_names(2) := 'Neena';
   DBMS_OUTPUT.PUT_LINE(v_emp.name || ' / ' || v_names(2));
END;
/
```

## 3. Control Structures — the Full Set

| Structure | Notes |
|---|---|
| `IF ... ELSIF ... ELSE` | `ELSIF` — **not** `ELSE IF` |
| `CASE` (simple) | compares one expression to values |
| `CASE` (searched) | each `WHEN` has its own condition |
| `LOOP ... EXIT WHEN` | basic loop |
| `WHILE cond LOOP` | checks condition first |
| `FOR i IN [REVERSE] a..b LOOP` | counter is read-only |
| `CONTINUE [WHEN cond]` | skip to next iteration (11g+) |
| `GOTO` / `<<label>>` | avoid — hurts readability |

```sql
BEGIN
   FOR i IN REVERSE 1..3 LOOP
      CONTINUE WHEN i = 2;
      DBMS_OUTPUT.PUT_LINE('i = ' || i);   -- prints 3, then 1
   END LOOP;
END;
/
```

## 4. Cursors — Attributes, Parameters, and `FOR UPDATE`

**Explicit cursor attributes** (also work as `SQL%...` for implicit cursors):

| Attribute | Meaning |
|---|---|
| `%ISOPEN` | TRUE if cursor is open |
| `%FOUND` | last FETCH returned a row |
| `%NOTFOUND` | last FETCH returned no row |
| `%ROWCOUNT` | rows fetched (or affected by DML) so far |

**Parameterized cursor:**

```sql
DECLARE
   CURSOR c_emp (p_dept NUMBER) IS
      SELECT first_name, salary FROM employees WHERE department_id = p_dept;
BEGIN
   FOR r IN c_emp(50) LOOP
      DBMS_OUTPUT.PUT_LINE(r.first_name || ' — ' || r.salary);
   END LOOP;
END;
/
```

**`FOR UPDATE` + `WHERE CURRENT OF`** — row locking for read-modify-write:

```sql
DECLARE
   CURSOR c_emp IS
      SELECT employee_id, salary FROM employees
      WHERE department_id = 50
      FOR UPDATE OF salary;
BEGIN
   FOR r IN c_emp LOOP
      UPDATE employees SET salary = r.salary * 1.05
      WHERE CURRENT OF c_emp;    -- updates the row just fetched
   END LOOP;
   COMMIT;
END;
/
```

**`SYS_REFCURSOR`** — pass a result set between programs (very common in APIs):

```sql
CREATE OR REPLACE PROCEDURE get_emps (p_dept IN NUMBER, p_rc OUT SYS_REFCURSOR) IS
BEGIN
   OPEN p_rc FOR
      SELECT employee_id, first_name FROM employees WHERE department_id = p_dept;
END;
/
```

## 5. Exception Handling — Beyond `WHEN OTHERS`

**Three exception types:**

1. **Predefined** — `NO_DATA_FOUND`, `TOO_MANY_ROWS`, `ZERO_DIVIDE`, `DUP_VAL_ON_INDEX`, `VALUE_ERROR` …
2. **Non-predefined** — Oracle error with a number but no name; bind it with `PRAGMA EXCEPTION_INIT`.
3. **User-defined** — you declare it and `RAISE` it.

```sql
DECLARE
   e_bad_salary EXCEPTION;
   PRAGMA EXCEPTION_INIT(e_bad_salary, -20001);   -- bind to ORA-20001
   v_sal NUMBER := 10;
BEGIN
   IF v_sal < 1000 THEN
      RAISE_APPLICATION_ERROR(-20001, 'Salary below minimum');
   END IF;
EXCEPTION
   WHEN e_bad_salary THEN
      DBMS_OUTPUT.PUT_LINE('Caught: ' || SQLERRM);   -- SQLERRM = message
   WHEN OTHERS THEN
      DBMS_OUTPUT.PUT_LINE('Code ' || SQLCODE || ': ' || SQLERRM);
      RAISE;   -- re-raise so the caller also sees it
END;
/
```

**Key rules:**
- An unhandled exception **propagates to the caller**. If nobody handles it, it reaches the client.
- **Savepoints** let you roll back *part* of a transaction inside a handler:

```sql
SAVEPOINT before_update;
UPDATE ...;
ROLLBACK TO before_update;
```

- `SQLCODE` / `SQLERRM` give you the numeric code and message.
- **Never** write `WHEN OTHERS THEN NULL;` — it silently hides bugs.

## 6. Procedures & Functions — Parameters and Purity

**Parameter modes:**

| Mode | Inside the subprogram | Caller sees change? |
|---|---|---|
| `IN` (default) | read-only | no |
| `OUT` | write-only (initial value NULL) | yes |
| `IN OUT` | read + write | yes |

**`NOCOPY`** — hint for large `OUT`/`IN OUT` collections to pass by reference (avoid copying):

```sql
PROCEDURE p (p_data IN OUT NOCOPY t_big_table) IS ...
```

**Defaults + overloading:**

```sql
CREATE OR REPLACE PROCEDURE greet (p_name IN VARCHAR2 DEFAULT 'World') IS
BEGIN
   DBMS_OUTPUT.PUT_LINE('Hello, ' || p_name);
END;
/

-- Overloading in a package: same name, different parameter signatures
PROCEDURE log_msg (p_msg IN VARCHAR2);
PROCEDURE log_msg (p_code IN NUMBER);
```

**Function purity** — to call a function **inside SQL**, it must not modify database state (no DML/COMMIT). Declare it `DETERMINISTIC` if it always returns the same output for the same input, or use `RESULT_CACHE` to cache results:

```sql
CREATE OR REPLACE FUNCTION get_dept_name (p_id IN NUMBER)
RETURN VARCHAR2 DETERMINISTIC IS ...
```

## 7. Packages — State, Privacy, Initialization

- **Spec** = public API. **Body** = implementation + private helpers.
- Anything declared only in the body is **private** — invisible to callers.
- **Package state**: package-level variables persist for the **session**. This is powerful and dangerous.
- **One-time initialization**: code in the body's `BEGIN ... END` runs **once per session** on first use.

```sql
CREATE OR REPLACE PACKAGE emp_pkg IS
   g_call_count NUMBER := 0;                 -- public variable
   PROCEDURE bump;                            -- public proc
END emp_pkg;
/

CREATE OR REPLACE PACKAGE BODY emp_pkg IS
   PROCEDURE private_helper IS BEGIN NULL; END;  -- private

   PROCEDURE bump IS
   BEGIN
      g_call_count := g_call_count + 1;
      private_helper;
   END bump;

BEGIN
   DBMS_OUTPUT.PUT_LINE('emp_pkg initialized');   -- runs once per session
END emp_pkg;
/
```

**Pitfall:** package state is per session. Two users see different `g_call_count`. If you need cross-session state, use a table.

## 8. Triggers — Types and the Mutating-Table Trap

**Types:**

| Fires on | Level |
|---|---|
| `INSERT` / `UPDATE` / `DELETE` | `FOR EACH ROW` (row) or statement-level |
| `BEFORE` / `AFTER` | timing |
| `INSTEAD OF` | on **views** only |
| System events (`LOGON`, `DDL`, …) | `ON DATABASE` / `ON SCHEMA` |

**`WHEN` clause** filters rows; **`FOLLOWS`** (11g+) orders triggers on the same table.

```sql
CREATE OR REPLACE TRIGGER trg_sal_check
BEFORE INSERT OR UPDATE OF salary ON employees
FOR EACH ROW
WHEN (NEW.salary < 0)
BEGIN
   RAISE_APPLICATION_ERROR(-20002, 'Salary cannot be negative');
END;
/
```

**Mutating-table error (ORA-04091):** a row trigger cannot `SELECT`/`UPDATE` the table that fired it. Solutions:
1. **Statement-level trigger** + `:NEW`/`:OLD` (not available at statement level — so no).
2. **Compound trigger** (11g+): collect row values in `AFTER EACH ROW`, act in `AFTER STATEMENT`.
3. **Package-based** staging (classic workaround).

```sql
CREATE OR REPLACE TRIGGER trg_compound
FOR UPDATE OF salary ON employees
COMPOUND TRIGGER
   TYPE t_ids IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
   v_ids t_ids;
   AFTER EACH ROW IS
   BEGIN
      v_ids(v_ids.COUNT + 1) := :NEW.employee_id;
   END AFTER EACH ROW;

   AFTER STATEMENT IS
   BEGIN
      FORALL i IN 1..v_ids.COUNT
         INSERT INTO salary_audit(emp_id) VALUES (v_ids(i));
   END AFTER STATEMENT;
END trg_compound;
/
```

## 9. Bulk Processing — `BULK COLLECT` & `FORALL`

Row-by-row loops are slow. Bulk operations cut context switches between PL/SQL and SQL.

```sql
DECLARE
   TYPE t_ids IS TABLE OF employees.employee_id%TYPE;
   v_ids t_ids;
BEGIN
   -- Fetch many rows at once
   SELECT employee_id BULK COLLECT INTO v_ids
   FROM employees WHERE department_id = 50;

   -- Update many rows at once
   FORALL i IN 1..v_ids.COUNT
      UPDATE employees SET salary = salary * 1.05
      WHERE employee_id = v_ids(i);

   DBMS_OUTPUT.PUT_LINE(v_ids.COUNT || ' rows updated');
   COMMIT;
END;
/
```

Use **`LIMIT`** with `BULK COLLECT` on huge result sets to control memory:

```sql
LOOP
   FETCH c_emp BULK COLLECT INTO v_rows LIMIT 500;
   EXIT WHEN v_rows.COUNT = 0;
   -- process v_rows
END LOOP;
```

## 10. Dynamic SQL — `EXECUTE IMMEDIATE`

When the SQL text isn't known until runtime (table names from a variable, DDL, etc.).

```sql
DECLARE
   v_table VARCHAR2(30) := 'EMPLOYEES';
   v_cnt   NUMBER;
BEGIN
   EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM ' || v_table INTO v_cnt;
   DBMS_OUTPUT.PUT_LINE('Rows: ' || v_cnt);
END;
/
```

**Use bind variables** (`USING`) — never concatenate user input (SQL injection):

```sql
EXECUTE IMMEDIATE
   'UPDATE employees SET salary = salary * :pct WHERE employee_id = :id'
   USING 1.05, 100;
```

> DDL (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`) **must** go through `EXECUTE IMMEDIATE` — you can't put DDL directly in PL/SQL.

## 11. Best Practices & Debugging

- **Naming**: prefix parameters `p_`, locals `v_`, globals `g_`, exceptions `e_`, cursors `c_`.
- **`AUTHID`**: default `DEFINER` (runs with owner's privileges). Use `AUTHID CURRENT_USER` for code that must respect the caller's privileges (e.g., in schemas that expose APIs).
- **Autonomous transactions** (`PRAGMA AUTONOMOUS_TRANSACTION`) — commit independently of the caller. Use for logging/auditing so the log survives a caller rollback.
- **Logging**: write errors to a table, not just `DBMS_OUTPUT` (users don't see it).
- **`DBMS_OUTPUT`** is for debugging only — it buffers and needs enabling in the client.

```sql
CREATE OR REPLACE PROCEDURE log_error (p_msg IN VARCHAR2) IS
   PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
   INSERT INTO error_log(msg, logged_at) VALUES (p_msg, SYSDATE);
   COMMIT;
END;
/
```
