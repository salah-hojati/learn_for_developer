تحلیل **Execution Plan** در Oracle یکی از مهم‌ترین مهارت‌های Database Performance Tuning است. وقتی یک Query کند اجرا می‌شود، من فقط به SQL نگاه نمی‌کنم؛ بررسی می‌کنم Oracle چگونه آن را اجرا کرده، از چه Indexهایی استفاده کرده، چه Joinهایی انجام داده و چه مقدار داده در هر مرحله پردازش کرده است.

Execution Plan نشان می‌دهد Oracle برای اجرای SQL چه مسیر و عملیات‌هایی را انتخاب کرده است. صرفاً دیدن یک Index Scan یا Full Table Scan به‌تنهایی نمی‌گوید Plan خوب است یا بد.&#x20;

# **۲. چگونه Execution Plan را نمایش می‌دهم؟**

## **روش اول: EXPLAIN PLAN**

ابتدا Plan تخمینی را بررسی می‌کنم:

```
EXPLAIN PLAN FOR
SELECT *
FROM ORDERS
WHERE CUSTOMER_ID = 100
  AND STATUS = 'ACTIVE';
```

سپس:

```
SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
```

خروجی ممکن است چیزی شبیه این باشد:

```
--------------------------------------------------------------------------------
| Id | Operation                    | Name              | Rows | Cost |
--------------------------------------------------------------------------------
|  0 | SELECT STATEMENT             |                   |  100 |   50 |
|  1 | TABLE ACCESS BY INDEX ROWID | ORDERS            |  100 |   50 |
|* 2 | INDEX RANGE SCAN            | IDX_ORD_CUSTOMER  |  100 |    5 |
--------------------------------------------------------------------------------
```

اما این Plan تخمینی است و ممکن است با Plan واقعی اجرای Query تفاوت داشته باشد.

## **روش دوم: بررسی Execution Plan واقعی (روش مهم‌تر)**

در Performance Tuning، من ترجیح می‌دهم Actual Execution Plan را بررسی کنم؛ چون فقط تخمین Optimizer کافی نیست.

ابتدا Query را با جمع‌آوری آمار واقعی اجرا می‌کنم:

```
SELECT /*+ GATHER_PLAN_STATISTICS */
       *
FROM ORDERS
WHERE CUSTOMER_ID = 100
  AND STATUS = 'ACTIVE';
```

سپس Plan آخرین اجرای Cursor را مشاهده می‌کنم:

```
SELECT *
FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(
        NULL,
        NULL,
        'ALLSTATS LAST +PREDICATE'
    )
);
```

در این خروجی، اطلاعاتی مثل موارد زیر اهمیت زیادی دارند:

- `E-Rows` : تعداد ردیف‌های تخمینی
- `A-Rows` : تعداد ردیف‌های واقعی
- `Buffers` : تعداد Bufferهای مصرف‌شده
- `Reads` : میزان Readهای انجام‌شده
- `Starts` : تعداد دفعات شروع یک Operation
- `Predicate Information` : شرط‌های Access و Filter

این اطلاعات کمک می‌کنند بفهمم مشکل از تخمین Optimizer است یا از حجم واقعی داده و روش اجرای Query.

توجه: برای دیدن Actual Statistics باید آمار اجرای Query جمع‌آوری شده باشد؛ Hint بالا یکی از روش‌هاست. DISPLAY_CURSOR نیز نیازمند دسترسی مناسب به اطلاعات Cursor و Plan است.

# **۳. مهم‌ترین بخش: چگونه Plan را بخوانم؟**

Execution Plan را باید به شکل یک **Tree (درخت)** تحلیل کنیم.

قاعده مهم:

> معمولاً عملیات از پایین به بالا اجرا می‌شوند؛ خروجی هر Operation به Parent Operation بالاتر منتقل می‌شود.

مثلاً:

```
SELECT STATEMENT
       |
       NESTED LOOPS
       /          \
      /            \
 INDEX SCAN      TABLE SCAN
```

یعنی ابتدا عملیات پایین‌تر داده تولید می‌کنند و سپس عملیات بالاتر روی آن داده‌ها کار می‌کند.

در Oracle، ستون `Id` به‌تنهایی ترتیب اجرای عملیات را مشخص نمی‌کند. باید ساختار درخت، Parent/Childها و عملیات مرتبط را بررسی کرد.&#x20;

```

```

اگر ۴ میلیون رکورد `ACTIVE` باشند، استفاده از Index ممکن است باعث شود Oracle:

**اصل مهم در Performance Tuning**

Full Table Scan را صرفاً به خاطر نام آن حذف نکن. اگر Query بخش بزرگی از جدول را می‌خواند، Full Scan می‌تواند بهترین Execution Plan باشد.

# **۵. تحلیل Join در Execution Plan**

در Queryهای چندجدولی، من به نوع Join و ترتیب اجرای جدول‌ها توجه زیادی می‌کنم.

Oracle معمولاً از سه روش اصلی Join استفاده می‌کند.

## **الف) Nested Loops Join**

```
NESTED LOOPS
   |
   |--- TABLE ACCESS (Outer)
   |
   |--- INDEX LOOKUP (Inner)
```

مفهوم:

برای هر رکورد جدول Outer، Oracle رکوردهای مرتبط در جدول Inner را پیدا می‌کند.

مثلاً:

```
SELECT *
FROM CUSTOMERS C
JOIN ORDERS O
    ON O.CUSTOMER_ID = C.ID
WHERE C.ID = 100;
```

اگر تعداد Customers خروجی کم باشد و روی `ORDERS.CUSTOMER_ID` Index داشته باشیم، Nested Loops می‌تواند بسیار مناسب باشد.

[데이널  『데이터 널리지』::SQL Nested Loop Join(조인) - Outer table, Inner table, Driving Table, Driven Table](https://images.openai.com/static-rsc-4/i9I80G63geYzcNth3rWnJbq00JH24rk7gZKPRoq3M0iTpmeT8Jehe_BYOd0t05XoB2SwQDr6Y7npj2Epc_nXOOjdxjb3O6ChHfmBa7Q8ztJGeh9BbBOSjPnxF53B-ncHseVLhYhfAtZJ92Ivl5LDnfoZOR1trVV-mcwnOdjg7Eg?purpose=inline)

مناسب برای:

- تعداد کم رکوردهای Outer.
- دسترسی سریع به Inner Table.
- Index مناسب روی Join Key.

ممکن است مشکل‌ساز شود:

- Outer Row Count بسیار زیاد باشد.
- برای هر رکورد تعداد زیادی Lookup انجام شود.
- Index مناسب نداشته باشیم.

## **ب) Hash Join**

```
HASH JOIN
   |
   |--- TABLE ACCESS FULL (Table A)
   |
   |--- TABLE ACCESS FULL (Table B)
```

در Hash Join، Oracle معمولاً از یک ورودی Hash Table می‌سازد و ورودی دیگر را برای پیدا کردن Matchها بررسی می‌کند.

Hash Join معمولاً برای Join مجموعه‌های بزرگ مناسب است؛ به‌خصوص وقتی تعداد زیادی رکورد باید با هم Join شوند و Index Lookup برای هر رکورد به‌صرفه نیست.

اما اگر حافظه کافی نباشد، ممکن است عملیات به TEMP و Disk Spill منجر شود و عملکرد افت کند.

## **مقایسه روش‌های Join**

| Join         | مناسب برای                     | مشکل احتمالی      |
| ------------ | ------------------------------ | ----------------- |
| Nested Loops | داده کم و Lookup سریع          | تعداد زیاد Lookup |
| Hash Join    | مجموعه داده بزرگ               | مصرف RAM و TEMP   |
| Sort Merge   | داده مرتب یا شرایط مناسب Merge | Sort پرهزینه      |

من هنگام تحلیل Join، صرفاً به اسم Join توجه نمی‌کنم؛ تعداد رکوردهای ورودی و خروجی، Indexها و هزینه واقعی اجرا مهم‌تر هستند.

# **۶. مهم‌ترین ستون‌های Execution Plan**

وقتی خروجی `DBMS_XPLAN` را می‌بینم، این ستون‌ها را به ترتیب بررسی می‌کنم.

## **Execution Plan Columns**

| **Column**    | **مفهوم**                                             |
| ------------- | ----------------------------------------------------- |
| Operation     | نوع عملیات Oracle                                     |
| Rows / E-Rows | تعداد رکوردهای تخمینی                                 |
| A-Rows        | تعداد رکوردهای واقعی خروجی Operation                  |
| Cost          | هزینه تخمینی Optimizer                                |
| Buffers       | Logical Reads (Buffer Gets)                           |
| Reads         | Physical Readهای ثبت‌شده                              |
| Starts        | تعداد دفعات اجرای Operation                           |
| Time          | زمان تخمینی یا اطلاعات زمان اجرا، بسته به Plan Format |

## **۶.۱. بررسی Estimated Rows و Actual Rows**

یکی از مهم‌ترین کارها، مقایسه `E-Rows` با `A-Rows` است.

فرض کن Plan چنین باشد:

| Operation        | E-Rows | A-Rows |
| ---------------- | ------ | ------ |
| Index Range Scan | 100    | 95,000 |
| Table Access     | 100    | 95,000 |
| Nested Loops     | 100    | 95,000 |

Oracle انتظار داشته 100 رکورد دریافت کند، اما در واقع 95,000 رکورد دریافت کرده است.

این اختلاف بزرگ می‌تواند نشان‌دهنده یکی از موارد زیر باشد:

- Statistics قدیمی یا نامناسب.
- Data Skew؛ یعنی توزیع نامتوازن داده.
- Cardinality Estimation نامناسب.
- Predicateهای پیچیده.
- Bind Variable و تفاوت مقادیر ورودی.
- مشکلات Histogram یا تخمین Selectivity.

چنین اختلافی ممکن است باعث شود Optimizer یک Nested Loops انتخاب کند، در حالی که Hash Join مناسب‌تر باشد.

**نکته Performance**

اگر Estimated Rows و Actual Rows اختلاف زیادی داشته باشند، قبل از تغییر Index یا اجبار Join، ابتدا علت تخمین اشتباه را بررسی کن.

## **۶.۲. بررسی Cost**

مثلاً:

```
Operation                  Cost
--------------------------------
TABLE ACCESS FULL          5000
INDEX RANGE SCAN            100
```

در ظاهر Index Range Scan بهتر به نظر می‌رسد.

اما Cost:

- زمان واقعی اجرا نیست.
- واحد میلی‌ثانیه نیست.
- برای مقایسه Planها در شرایط Optimizer استفاده می‌شود.
- تحت تأثیر Statistics، تنظیمات و محیط دیتابیس است.

بنابراین اگر Cost یک Query از 500 به 100 کاهش پیدا کند، لزوماً اجرای آن پنج برابر سریع‌تر نشده است.

## **۶.۳. بررسی Buffers**

`Buffers` یکی از معیارهای بسیار مفید برای تحلیل SQL است.

Logical Read یا Buffer Get یعنی Oracle برای دسترسی به Block، آن را از Buffer Cache درخواست کرده است؛ این الزاماً به معنی خواندن از Disk نیست.

مثلاً:

| Query   | Buffers | نتیجه                     |
| ------- | ------- | ------------------------- |
| Query A | 2,000   | بهتر                      |
| Query B | 800,000 | احتمالاً مصرف منابع بیشتر |

اگر Query در هر بار اجرا Buffer زیادی مصرف کند و پرتکرار باشد، می‌تواند فشار زیادی روی Database ایجاد کند حتی اگر بخشی از داده در Cache باشد.

برای بررسی Performance، Bufferها را همراه با زمان اجرا، Physical Reads و تعداد Rows بررسی می‌کنم.

# **۷. Access Predicate و Filter Predicate چه تفاوتی دارند؟**

این موضوع در تحلیل Index بسیار مهم است.

فرض کن:

```
SELECT *
FROM ORDERS
WHERE CUSTOMER_ID = 100
  AND STATUS = 'ACTIVE';
```

روی `CUSTOMER_ID` Index داریم، اما `STATUS` داخل Index نیست.

ممکن است Plan به شکل زیر باشد:

```
TABLE ACCESS BY INDEX ROWID ORDERS
   |
   INDEX RANGE SCAN IDX_ORD_CUSTOMER
```

در Predicate Information ممکن است ببینیم:

```
access("CUSTOMER_ID" = 100)

filter("STATUS" = 'ACTIVE')
```

### **Access Predicate**

شرطی است که Oracle با استفاده از آن محدوده دسترسی یا Scan را تعیین می‌کند.

### **Filter Predicate**

شرطی است که روی رکوردهای حاصل از Operation بررسی می‌شود تا رکوردهای نامناسب حذف شوند.

اگر Index فقط `CUSTOMER_ID` را پوشش دهد، Oracle ابتدا رکوردهای مربوط به Customer را پیدا می‌کند و سپس `STATUS` را روی رکوردهای حاصل بررسی می‌کند.

اگر Customer موردنظر 200 هزار سفارش داشته باشد، ممکن است حجم زیادی از رکوردها بررسی و حذف شوند.

در این شرایط شاید Index Composite مناسب باشد:

```
CREATE INDEX IDX_ORD_CUSTOMER_STATUS
ON ORDERS(CUSTOMER_ID, STATUS);
```

اما ایجاد Index جدید باید با توجه به Queryهای واقعی، Selectivity و هزینه Write انجام شود، نه صرفاً بر اساس مشاهده Filter Predicate.

# **۸. مثال واقعی تحلیل Execution Plan**

فرض کن این Query کند است:

```
SELECT O.ID,
       O.ORDER_DATE,
       C.NAME
FROM ORDERS O
JOIN CUSTOMERS C
    ON C.ID = O.CUSTOMER_ID
WHERE O.STATUS = 'ACTIVE'
  AND O.ORDER_DATE >= DATE '2026-01-01';
```

Execution Plan:

```
--------------------------------------------------------------------------------
| Id | Operation                     | Name              | E-Rows | Cost |
--------------------------------------------------------------------------------
|  0 | SELECT STATEMENT              |                   |        | 2500 |
|  1 | HASH JOIN                    |                   |  50000 | 2500 |
|  2 | TABLE ACCESS FULL             | CUSTOMERS         | 10000  |  200 |
|  3 | TABLE ACCESS FULL             | ORDERS            | 50000  | 1800 |
--------------------------------------------------------------------------------
```

### **تحلیل من**

**Step 1 — بررسی Full Table Scan**

```
TABLE ACCESS FULL ORDERS
```

آیا این مشکل است؟

نه لزوماً. ابتدا بررسی می‌کنم چند درصد Orders با شرایط Query مطابقت دارند.

اگر ۷۰ درصد Orders از سال 2026 به بعد Active باشند، Full Scan ممکن است منطقی باشد.

اگر فقط ۰.۵ درصد رکوردها Match شوند، احتمالاً Access Path بهتری وجود دارد.

**Step 2 — بررسی Join Method**

```
HASH JOIN
```

چون تعداد رکوردها نسبتاً زیاد است، Hash Join ممکن است انتخاب مناسبی باشد.

اگر Query فقط یک Customer را انتخاب می‌کرد و تعداد Orderها کم بود، Nested Loops با Index Lookup ممکن بود بهتر باشد.

**Step 3 — بررسی Estimated Rows**

```
E-Rows = 50000
```

این عدد را با `A-Rows` مقایسه می‌کنم.

اگر تعداد واقعی 5 میلیون باشد، تخمین Optimizer بسیار اشتباه بوده و باید Statistics، Data Distribution و Predicateها بررسی شوند.

**Step 4 — بررسی Index مناسب**

برای این Query ممکن است Index زیر را بررسی کنم:

```
CREATE INDEX IDX_ORD_STATUS_DATE_CUSTOMER
ON ORDERS(STATUS, ORDER_DATE, CUSTOMER_ID);
```

یا بسته به Queryهای دیگر:

```
CREATE INDEX IDX_ORD_DATE_STATUS
ON ORDERS(ORDER_DATE, STATUS);
```

من ترتیب ستون‌ها را بر اساس Queryهای واقعی، Selectivity، Equality و Range Conditions انتخاب می‌کنم؛ صرفاً یک ترتیب ثابت برای همه Queryها وجود ندارد.

**Step 5 — بررسی SELECT**

در Query فقط سه ستون استفاده شده‌اند:

```
O.ID,
O.ORDER_DATE,
C.NAME
```

پس استفاده از `SELECT *` ضرورت ندارد.

کاهش ستون‌های خروجی می‌تواند:

- میزان انتقال داده را کاهش دهد.
- مصرف Memory را کاهش دهد.
- امکان استفاده از Covering Index را در بعضی Queryها فراهم کند.
- از خواندن Columnهای غیرضروری جلوگیری کند.

## **۱۰. Cheat Sheet برای تحلیل Execution Plan**

وقتی Plan را باز می‌کنی، این چک‌لیست را به ترتیب بررسی کن:

آیا Full Table Scan منطقی است یا حجم زیادی از داده غیرضروری خوانده می‌شود؟

آیا Index مناسب برای WHERE و JOIN وجود دارد؟

آیا Estimated Rows با Actual Rows اختلاف زیادی دارد؟

آیا Nested Loops تعداد زیادی Lookup انجام می‌دهد؟

آیا Hash Join به Memory و TEMP زیادی نیاز دارد؟

آیا Sort عملیات پرهزینه‌ای انجام می‌دهد؟

آیا Filter Predicate تعداد زیادی رکورد را حذف می‌کند؟

آیا Logical Reads یا Physical Reads زیاد هستند؟

آیا Statistics به‌روز و مناسب هستند؟

آیا Performance بعد از تغییر واقعاً بهتر شده است؟

## **پاسخ مناسب برای مصاحبه (English)**

> When analyzing an Oracle execution plan, I start by examining the actual execution plan rather than relying only on the estimated plan.
>
> I look at the access paths, join methods, estimated versus actual row counts, buffer gets, physical reads, and predicate information.
>
> I pay particular attention to cardinality estimation errors, expensive table scans, excessive nested loop lookups, unnecessary sorting, and inefficient join operations.
>
> I don't automatically consider a full table scan or a hash join to be bad. The optimizer may choose them because they are more efficient for the data volume and query conditions.
>
> After identifying the bottleneck, I consider SQL rewriting, indexing, statistics gathering, or changing the query structure. Finally, I compare the actual execution metrics before and after the change to verify that the optimization improved performance.
