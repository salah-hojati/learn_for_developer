# **Isolation Levelها و Lock در Oracle**

این دو مفهوم از مهم‌ترین مباحث دیتابیس در سیستم‌های چندکاربره هستند؛ مخصوصاً زمانی که چند کاربر هم‌زمان روی یک رکورد کار می‌کنند، مثلاً موجودی حساب، سفارش، پرداخت یا موجودی انبار.

برای درک درست، باید دو موضوع را از هم جدا کنیم:

- **Isolation Level:** یک Transaction چه داده‌ای را می‌بیند و تا چه حد باید در برابر تغییرات Transactionهای دیگر مستقل باشد؟
- **Lock:** وقتی چند Transaction بخواهند هم‌زمان یک داده را تغییر دهند، Oracle چگونه از تداخل و خراب‌شدن داده جلوگیری می‌کند؟

# **1. Isolation Level چیست؟**

فرض کن دو کاربر هم‌زمان روی جدول حساب بانکی کار می‌کنند.

```
CREATE TABLE ACCOUNTS (
    ID NUMBER PRIMARY KEY,
    BALANCE NUMBER
);

INSERT INTO ACCOUNTS VALUES (1, 1000);
COMMIT;
```

حالا دو Transaction داریم:

- Transaction A
- Transaction B

هر دو می‌خواهند حساب شماره 1 را تغییر دهند یا بخوانند.

Isolation Level تعیین می‌کند هر Transaction چه تصویری از داده‌ها داشته باشد و تغییرات Transactionهای دیگر را چه زمانی ببیند.

# **2. انواع Isolation Problem**

قبل از Isolation Level، باید سه مشکل اصلی را بشناسیم.

## **Dirty Read**

Transaction A مقداری را تغییر می‌دهد ولی هنوز Commit نکرده است.

Transaction B همان مقدار تغییر یافته را می‌خواند.

اگر A در نهایت Rollback کند، B داده‌ای را خوانده که هرگز واقعاً Commit نشده است.

#### **مثال**

Transaction A

Transaction B

UPDATE BALANCE = 500

SELECT BALANCE → 500

ROLLBACK

B قبلاً مقدار 500 را خوانده!

در این مثال B اطلاعاتی را دیده که هیچ‌وقت Commit نشده است.

Oracle از Dirty Read جلوگیری می‌کند.

Oracle حتی در `READ COMMITTED` نیز Dirty Read را اجازه نمی‌دهد.

## **Non-repeatable Read**

Transaction A یک رکورد را می‌خواند.

Transaction B همان رکورد را تغییر می‌دهد و Commit می‌کند.

Transaction A دوباره همان رکورد را می‌خواند و مقدار متفاوتی می‌بیند.

```
-- Transaction A
SELECT BALANCE FROM ACCOUNTS WHERE ID = 1;
-- 1000
```

```
-- Transaction B
UPDATE ACCOUNTS
SET BALANCE = 2000
WHERE ID = 1;

COMMIT;
```

حالا Transaction A دوباره:

```
SELECT BALANCE FROM ACCOUNTS WHERE ID = 1;
-- 2000
```

Transaction A در یک Transaction، برای یک رکورد، دو مقدار متفاوت مشاهده کرده است.

## **Phantom Read**

Transaction A یک Query با شرط اجرا می‌کند.

Transaction B رکورد جدیدی Insert می‌کند که با شرط Query مطابقت دارد و Commit می‌کند.

Transaction A دوباره همان Query را اجرا می‌کند و رکورد جدید را می‌بیند.

```
-- Transaction A
SELECT *
FROM ACCOUNTS
WHERE BALANCE > 500;
```

فرض کن 5 رکورد دریافت شود.

Transaction B:

```
INSERT INTO ACCOUNTS (ID, BALANCE)
VALUES (10, 900);

COMMIT;
```

Transaction A دوباره همان Query را اجرا می‌کند و این بار 6 رکورد می‌بیند.

رکورد جدیدی که وارد نتیجه Query شده، Phantom Row نام دارد.

# **3. Isolation Levelهای Oracle**

Oracle به‌صورت اصلی دو Isolation Level در اختیار ما قرار می‌دهد:

## **READ COMMITTED**

پیش‌فرض Oracle

Snapshot در سطح هر Statement

## **SERIALIZABLE**

Snapshot در سطح Transaction

Consistency قوی‌تر برای مجموعه عملیات

Oracle همچنین `READ ONLY` Transaction دارد که برای Transactionهای فقط خواندنی استفاده می‌شود، اما به‌عنوان یک Isolation Level استاندارد چهارگانه با نام `READ UNCOMMITTED` یا `REPEATABLE READ` در Oracle ارائه نمی‌شود.

## **3.1 READ COMMITTED**

در Oracle، `READ COMMITTED` Isolation Level پیش‌فرض است.

در این حالت:

> هر SQL Statement یک Snapshot از داده‌های Commit شده در زمان شروع همان Statement می‌بیند.

یعنی اگر داخل یک Transaction چند SELECT اجرا کنی، هر SELECT ممکن است Snapshot متفاوتی داشته باشد.

### **مثال**

```
-- Transaction A
SELECT BALANCE
FROM ACCOUNTS
WHERE ID = 1;
-- 1000
```

Transaction B:

```
UPDATE ACCOUNTS
SET BALANCE = 2000
WHERE ID = 1;

COMMIT;
```

Transaction A:

```
SELECT BALANCE
FROM ACCOUNTS
WHERE ID = 1;
-- 2000
```

در `READ COMMITTED`، Transaction A مقدار جدید Commit شده را می‌بیند، چون Statement دوم Snapshot جدیدی دریافت می‌کند.

### **ویژگی‌ها**

- Dirty Read ندارد.
- Non-repeatable Read ممکن است.
- Phantom Read ممکن است.
- Readها معمولاً Writerها را Block نمی‌کنند.
- Writerها معمولاً Readerها را Block نمی‌کنند.
- برای اکثر اپلیکیشن‌های OLTP انتخاب مناسب و پیش‌فرض است.

## **3.2 SERIALIZABLE**

در این Isolation Level، Transaction یک Snapshot از دیتابیس در زمان شروع Transaction در اختیار دارد.

تمام Queryهای آن Transaction بر اساس همان Snapshot اجرا می‌شوند.

```
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

این دستور باید قبل از اولین Statementهای Transaction اجرا شود.

### **مثال**

Transaction A:

```
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT BALANCE
FROM ACCOUNTS
WHERE ID = 1;
-- 1000
```

Transaction B:

```
UPDATE ACCOUNTS
SET BALANCE = 2000
WHERE ID = 1;

COMMIT;
```

Transaction A:

```
SELECT BALANCE
FROM ACCOUNTS
WHERE ID = 1;
-- همچنان 1000
```

Transaction A تغییر Commit شده Transaction B را در Queryهای عادی خودش نمی‌بیند؛ چون Snapshot آن از ابتدای Transaction ثابت است.

### **مزایا**

- خواندن‌های Transaction از یک Snapshot ثابت انجام می‌شوند.
- Non-repeatable Read در خواندن‌های عادی Transaction رخ نمی‌دهد.
- Phantom Read در خواندن‌های عادی Transaction رخ نمی‌دهد.

### **محدودیت مهم**

در صورت تداخل تغییرات، Oracle ممکن است خطای زیر بدهد:

```
ORA-08177: can't serialize access for this transaction
```

بنابراین استفاده از `SERIALIZABLE` ممکن است نیازمند Retry کردن Transaction باشد.

این Isolation Level لزوماً بهترین انتخاب برای همه Transactionها نیست، چون در workloadهای concurrent می‌تواند Conflict و Retry بیشتری ایجاد کند.

## **3.3 READ ONLY Transaction**

اگر Transaction فقط قرار است داده‌ها را بخواند و یک Snapshot ثابت داشته باشد:

```
SET TRANSACTION READ ONLY;
```

مثلاً:

```
SET TRANSACTION READ ONLY;

SELECT SUM(BALANCE)
FROM ACCOUNTS;

SELECT COUNT(*)
FROM ACCOUNTS;

COMMIT;
```

در این Transaction:

- تغییر داده مجاز نیست.
- Queryها Snapshot یکسانی را می‌بینند.
- برای گزارش‌گیری چند Query که باید از یک تصویر ثابت داده استفاده کنند مفید است.

# **4. مقایسه Isolation Levelها**

مقایسه بر اساس رفتار Oracle Database

| ویژگی               | READ COMMITTED | SERIALIZABLE                | READ ONLY      |
| ------------------- | -------------- | --------------------------- | -------------- |
| Snapshot            | هر Statement   | کل Transaction              | کل Transaction |
| Dirty Read          | ندارد          | ندارد                       | ندارد          |
| Non-repeatable Read | ممکن           | جلوگیری می‌شود              | جلوگیری می‌شود |
| Phantom Read        | ممکن           | جلوگیری می‌شود              | جلوگیری می‌شود |
| امکان DML           | بله            | بله                         | خیر            |
| Concurrency         | بالا           | ممکن است Conflict ایجاد شود | مناسب خواندن   |
| کاربرد              | اکثر سیستم‌ها  | عملیات با Consistency بیشتر | گزارش‌گیری     |

نکته: Oracle با استفاده از MVCC و Undo Data، خواندن نسخه قبلی داده را بدون نیاز به Block کردن Writer انجام می‌دهد. این موضوع یکی از تفاوت‌های مهم Oracle با دیتابیس‌هایی است که برای خواندن از Shared Lock استفاده می‌کنند.

# **5. Lock چیست؟**

Lock مکانیزمی است که Oracle برای کنترل دسترسی هم‌زمان به منابع دیتابیس استفاده می‌کند.

هدف Lock:

- جلوگیری از تغییر هم‌زمان ناسازگار
- جلوگیری از تداخل Transactionها
- حفظ Integrity داده‌ها
- کنترل دسترسی به Row یا Object

در Oracle دو نوع Lock مهم داریم:

- Row-level Lock
- Table-level Lock

# **6. Row-level Lock**

وقتی یک رکورد را Update یا Delete می‌کنی، Oracle آن Row را Lock می‌کند.

مثلاً:

```
UPDATE ACCOUNTS
SET BALANCE = 1500
WHERE ID = 1;
```

Oracle رکورد مربوط به `ID = 1` را Lock می‌کند.

در این حالت:

- Transaction دیگر نمی‌تواند همان Row را به شکل ناسازگار تغییر دهد.
- Transactionهای دیگر می‌توانند Rowهای دیگر همان جدول را تغییر دهند.
- Lock معمولاً تا `COMMIT` یا `ROLLBACK` باقی می‌ماند.

### **مثال هم‌زمان**

#### **سناریوی Row Lock**

Transaction A

UPDATE Row 1

Lock Row 1

Transaction B

UPDATE Row 2

موفق

Transaction B → UPDATE Row 1

منتظر آزاد شدن Lock می‌ماند

اگر Transaction B بخواهد Row 1 را تغییر دهد، باید منتظر پایان Transaction A بماند.

```
-- Transaction A
UPDATE ACCOUNTS
SET BALANCE = 1500
WHERE ID = 1;

-- هنوز COMMIT نکرده است
```

```
-- Transaction B
UPDATE ACCOUNTS
SET BALANCE = 2000
WHERE ID = 1;
```

Transaction B در این مرحله Wait می‌کند.

اگر A:

```
COMMIT;
```

کند، B ادامه پیدا می‌کند.

اگر A:

```
ROLLBACK;
```

کند، B نیز می‌تواند ادامه دهد و تغییر خودش را انجام دهد.

# **7. Table-level Lock**

Oracle علاوه بر Row Lock، روی Table نیز Lockهایی برای کنترل عملیات مختلف دارد.

یکی از انواع مهم Table Lock، TM Lock است.

TM Lock برای کنترل عملیات DML و سازگاری دسترسی به ساختار Table استفاده می‌شود.

مثلاً در اجرای:

```
UPDATE ACCOUNTS
SET BALANCE = BALANCE + 100
WHERE ID = 1;
```

Oracle علاوه بر Lock روی Rowهای مورد تغییر، روی خود Table نیز یک Lock در سطح DML می‌گیرد.

این Lock به معنای قفل شدن کامل Table و جلوگیری از تمام عملیات دیگر نیست.

در بسیاری از حالت‌ها Transactionهای دیگر می‌توانند هم‌زمان روی همان Table کار کنند.

### **انواع مهم Table Lock Mode**

| Lock Mode | نام                       | توضیح                     |
| --------- | ------------------------- | ------------------------- |
| 1         | Null                      | کمترین سطح Lock           |
| 2         | Row Share (RS)            | اجازه برخی عملیات هم‌زمان |
| 3         | Row Exclusive (RX)        | معمولاً برای DML          |
| 4         | Share (S)                 | محدودیت بیشتر در DML      |
| 5         | Share Row Exclusive (SRX) | محدودیت شدیدتر            |
| 6         | Exclusive (X)             | بیشترین محدودیت           |

این Modeها با هم سازگاری‌های متفاوتی دارند؛ به همین دلیل وجود TM Lock لزوماً به معنای Block شدن همه Transactionها نیست.

# **8. SELECT FOR UPDATE**

یکی از مهم‌ترین ابزارهای Lock در Oracle.

در حالت معمول:

```
SELECT *
FROM ACCOUNTS
WHERE ID = 1;
```

این SELECT، Row Lock معمولی برای جلوگیری از Update توسط دیگر Transactionها ایجاد نمی‌کند.

اما:

```
SELECT *
FROM ACCOUNTS
WHERE ID = 1
FOR UPDATE;
```

Row موردنظر را برای Update Lock می‌کند.

یعنی می‌خواهیم بگوییم:

> این رکورد را می‌خوانم و قصد دارم آن را تغییر دهم؛ تا زمانی که Transaction من تمام نشده، اجازه نده تغییر ناسازگار روی این رکورد انجام شود.

## **مثال کاربردی: برداشت از حساب**

فرض کن موجودی حساب 1000 دلار است و کاربر می‌خواهد 700 دلار برداشت کند.

```
SELECT BALANCE
FROM ACCOUNTS
WHERE ID = 1
FOR UPDATE;
```

بعد:

```
UPDATE ACCOUNTS
SET BALANCE = BALANCE - 700
WHERE ID = 1;

COMMIT;
```

با `FOR UPDATE` می‌توان از تداخل برخی عملیات هم‌زمان روی همان Row جلوگیری کرد.

البته برای طراحی صحیح عملیات مالی، باید علاوه بر Lock، شرط‌های اعتبارسنجی و محدودیت‌های دیتابیس هم داشته باشیم.

## **8.1 NOWAIT**

اگر Row از قبل Lock شده باشد، به‌جای انتظار می‌توان فوراً خطا دریافت کرد.

```
SELECT *
FROM ACCOUNTS
WHERE ID = 1
FOR UPDATE NOWAIT;
```

اگر Lock در اختیار Transaction دیگری باشد، Oracle به‌جای Wait کردن، خطای Lock می‌دهد، معمولاً:

```
ORA-00054: resource busy and acquire with NOWAIT specified
```

مناسب زمانی است که نمی‌خواهیم کاربر منتظر بماند.

## **8.2 WAIT**

می‌توان مدت مشخصی منتظر Lock ماند:

```
SELECT *
FROM ACCOUNTS
WHERE ID = 1
FOR UPDATE WAIT 5;
```

یعنی حداکثر 5 ثانیه انتظار برای آزاد شدن Lock.

اگر Lock در این مدت آزاد نشود، Query با خطا تمام می‌شود.

## **8.3 SKIP LOCKED**

این گزینه بسیار کاربردی برای Queueها و پردازش Jobهای هم‌زمان است.

```
SELECT *
FROM JOBS
WHERE STATUS = 'READY'
FOR UPDATE SKIP LOCKED;
```

اگر رکوردی توسط Transaction دیگری Lock شده باشد، Oracle آن را نادیده می‌گیرد و سراغ Rowهای دیگر می‌رود.

### **کاربرد**

فرض کن 100 Job داریم و 5 Worker هم‌زمان می‌خواهند Job بردارند.

اگر همه Workerها بخواهند اولین رکورد را Lock کنند، ممکن است منتظر یکدیگر بمانند.

با `SKIP LOCKED`:

- Worker 1 رکورد اول را Lock می‌کند.
- Worker 2 رکورد Lock شده را رد می‌کند و رکورد بعدی را می‌گیرد.
- Worker 3 نیز رکوردهای در اختیار دیگران را رد می‌کند.

این روش برای پیاده‌سازی Queueهای دیتابیس بسیار مفید است.

# **9. Deadlock چیست؟**

Deadlock زمانی اتفاق می‌افتد که دو Transaction منتظر Lock یکدیگر باشند و هیچ‌کدام نتوانند ادامه دهند.

### **مثال**

Transaction A:

```
UPDATE ACCOUNTS
SET BALANCE = BALANCE - 100
WHERE ID = 1;

-- حالا تلاش برای Lock حساب 2
UPDATE ACCOUNTS
SET BALANCE = BALANCE + 100
WHERE ID = 2;
```

Transaction B:

```
UPDATE ACCOUNTS
SET BALANCE = BALANCE - 100
WHERE ID = 2;

-- حالا تلاش برای Lock حساب 1
UPDATE ACCOUNTS
SET BALANCE = BALANCE + 100
WHERE ID = 1;
```

#### **ساختار Deadlock**

Transaction A

Lock روی Row 1 دارد

منتظر Row 2 است

Transaction B

Lock روی Row 2 دارد

منتظر Row 1 است

در نتیجه:

- A منتظر B است.
- B منتظر A است.
- هیچ‌کدام نمی‌توانند ادامه دهند.

Oracle این وضعیت را تشخیص می‌دهد و معمولاً یکی از Statementهای دخیل را با خطای زیر متوقف می‌کند:

```
ORA-00060: deadlock detected while waiting for resource
```

Oracle لزوماً کل Transaction را Rollback نمی‌کند؛ معمولاً Statement ایجادکننده Deadlock را Rollback می‌کند و برنامه باید وضعیت Transaction را مدیریت کند.

## **چگونه از Deadlock جلوگیری کنیم؟**

### **1. ترتیب Lock یکسان**

همه Transactionها Rowها را با یک ترتیب ثابت Lock کنند.

مثلاً همیشه:

```
Account 1 → Account 2
```

و هیچ Transaction دیگری:

```
Account 2 → Account 1
```

نباشد.

### **2. Transaction کوتاه باشد**

از باز نگه داشتن Transaction هنگام انجام کارهای زیر اجتناب کن:

- HTTP Call
- ارسال Email
- پردازش طولانی
- دریافت ورودی کاربر
- عملیات سنگین

### **3. Lockهای غیرضروری نگیری**

فقط Rowهایی را Lock کن که واقعاً نیاز داری.

### **4. Retry هوشمند**

برای برخی خطاهای concurrency می‌توان Retry در نظر گرفت، اما باید کنترل‌شده باشد؛ مخصوصاً عملیات مالی که نباید دوباره اجرا شدن آن باعث Duplicate Transaction شود.

# **10. MVCC در Oracle چیست؟**

یکی از ویژگی‌های بسیار مهم Oracle، **MVCC (Multi-Version Concurrency Control)** است.

Oracle برای خواندن داده‌ها معمولاً نیازی ندارد Reader را منتظر Writer نگه دارد یا Writer را منتظر Reader.

فرض کن یک Transaction در حال Update است:

```
WHERE ID = 1;
```

Oracle می‌تواند مقدار قبلی و Commit شده را از طریق سازوکار Consistent Read برگرداند.

بنابراین:

- Reader معمولی منتظر Writer نمی‌ماند.
- Writer معمولی منتظر Reader نمی‌ماند.
- Writerهایی که روی یک Row مشترک تغییر ناسازگار انجام می‌دهند، ممکن است منتظر یکدیگر بمانند.

این ویژگی یکی از دلایل مهم Concurrency بالا در Oracle است.

البته در شرایط خاص، به‌خصوص کمبود Undo یا طولانی شدن Query، ممکن است خطاهایی مانند ORA-01555 (Snapshot Too Old) رخ دهد.

# **11. تفاوت Lock و Isolation Level**

این دو مفهوم به هم مرتبط‌اند، ولی یکسان نیستند.

| Isolation Level                           | Lock                                            |
| ----------------------------------------- | ----------------------------------------------- |
| تعیین می‌کند Transaction چه داده‌ای ببیند | تعیین می‌کند دسترسی هم‌زمان چگونه کنترل شود     |
| مربوط به Consistency                      | مربوط به Concurrency Control                    |
| مثل `READ COMMITTED`                      | مثل `SELECT FOR UPDATE`                         |
| می‌تواند رفتار Snapshot را تغییر دهد      | می‌تواند باعث Wait یا Block شدن Transaction شود |

مثلاً در Oracle، حتی در `SERIALIZABLE` نیز Readerها معمولاً Writerها را Block نمی‌کنند؛ Oracle با MVCC سازگاری خواندن را فراهم می‌کند.

# **12. چگونه Lockهای Oracle را بررسی کنیم؟**

وقتی یک Query کند شده و احتمال می‌دهیم به دلیل Lock باشد، می‌توان Sessionهای Blocking و Waiting را بررسی کرد.

## **Sessionهای Block شده**

```
SELECT
    SID,
    SERIAL#,
    USERNAME,
    BLOCKING_SESSION,
    WAIT_CLASS,
    EVENT,
    SECONDS_IN_WAIT,
    SQL_ID
FROM V$SESSION
WHERE BLOCKING_SESSION IS NOT NULL;
```

این Query Sessionهایی را نشان می‌دهد که توسط Session دیگری Block شده‌اند.

## **بررسی Lockها**

```
SELECT
    SESSION_ID,
    LOCK_TYPE,
    MODE_HELD,
    MODE_REQUESTED,
    LOCK_ID1,
    LOCK_ID2
FROM DBA_LOCK;
```

این View به دسترسی مناسب نیاز دارد.

## **پیدا کردن Session مسدودکننده و مسدودشده**

```
SELECT
    s1.sid AS blocker_sid,
    s1.serial# AS blocker_serial,
    s1.username AS blocker_user,
    s2.sid AS waiter_sid,
    s2.serial# AS waiter_serial,
    s2.username AS waiter_user,
    s2.event,
    s2.seconds_in_wait
FROM v$session s1
JOIN v$session s2
    ON s2.blocking_session = s1.sid;
```

این اطلاعات برای DBA و Developer هنگام بررسی Lockهای طولانی مفید است.

# **13. ارتباط با Spring Boot و JPA**

در Spring، اگر یک متد را `@Transactional` کنیم، Transaction معمولاً تا پایان متد و خروج از محدوده Transaction باقی می‌ماند.

```
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {

    Account from = accountRepository.findById(fromId)
            .orElseThrow();

    Account to = accountRepository.findById(toId)
            .orElseThrow();

    from.withdraw(amount);
    to.deposit(amount);

    accountRepository.save(from);
    accountRepository.save(to);
}
```

اگر این متد Transaction داشته باشد، تغییرات تا Commit شدن Transaction در محدوده آن قرار دارند.

اما اگر دو کاربر هم‌زمان روی یک حساب کار کنند، صرفاً `@Transactional` به تنهایی تمام Race Conditionهای منطقی را حل نمی‌کند.

برای مثال، موجودی 100 است و دو درخواست هم‌زمان هرکدام 80 برداشت می‌کنند.

اگر هر دو ابتدا موجودی 100 را بخوانند و سپس برداشت انجام دهند، ممکن است منطق کسب‌وکار دچار مشکل شود.

## **راهکار اول: Pessimistic Lock**

با JPA می‌توان از Lock صریح استفاده کرد.

```
public interface AccountRepository
        extends JpaRepository<Account, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT a FROM Account a WHERE a.id = :id")
    Optional<Account> findByIdForUpdate(Long id);
}
```

استفاده:

```
@Transactional
public void withdraw(Long accountId, BigDecimal amount) {

    Account account = accountRepository
            .findByIdForUpdate(accountId)
            .orElseThrow();

    if (account.getBalance().compareTo(amount) < 0) {
        throw new IllegalStateException("Insufficient balance");
    }

    account.setBalance(account.getBalance().subtract(amount));
}
```

در این روش، Transaction برای Update کردن حساب، Lock مناسب می‌گیرد تا Transactionهای متعارض نتوانند هم‌زمان همان حساب را به شکل ناسازگار تغییر دهند.

## **راهکار دوم: Optimistic Lock**

با استفاده از `@Version`:

```
@Entity
public class Account {

    @Id
    private Long id;

    private BigDecimal balance;

    @Version
    private Long version;
}
```

در این روش، معمولاً Lock طولانی برای خواندن ایجاد نمی‌کنیم.

هنگام Update، Hibernate نسخه رکورد را بررسی می‌کند. اگر Transaction دیگری رکورد را تغییر داده باشد، ممکن است Update شکست بخورد و Exception مربوط به Optimistic Lock رخ دهد.

## **Optimistic**

- فرض می‌کند Conflict کم است
- Lock طولانی ندارد
- مناسب سیستم‌های پرتراکنش با Conflict کم

## **Pessimistic**

- از ابتدا Lock می‌گیرد
- از تغییر هم‌زمان ناسازگار جلوگیری می‌کند
- مناسب منابع پرConflict

# **14. چه زمانی از کدام روش استفاده کنیم؟**

| سناریو                                   | پیشنهاد                                |
| ---------------------------------------- | -------------------------------------- |
| سیستم CRUD معمولی                        | `READ COMMITTED`                       |
| گزارش‌گیری با چند Query و Snapshot یکسان | `READ ONLY`                            |
| نیاز به Consistency در کل Transaction    | `SERIALIZABLE` با مدیریت Retry         |
| برداشت از حساب یا تخصیص منابع            | Lock یا Atomic Update                  |
| ویرایش رکورد توسط کاربران با Conflict کم | Optimistic Lock                        |
| Job Queue چند Worker                     | `FOR UPDATE SKIP LOCKED`               |
| انتقال پول بین دو حساب                   | Lock با ترتیب ثابت و Transaction کوتاه |

# **15. نکات مهم Senior Developer**

## **اشتباهات رایج در Concurrency**

- فکر کنیم `SELECT` معمولی در Oracle باعث Row Lock می‌شود.
- تصور کنیم `@Transactional` به‌تنهایی Race Condition را حل می‌کند.
- Transaction را در زمان HTTP Call باز نگه داریم.
- در عملیات چند رکوردی ترتیب Lock متفاوت داشته باشیم و Deadlock ایجاد کنیم.
- برای هر عملیات از `SERIALIZABLE` استفاده کنیم و باعث افزایش Conflict شویم.
- تصور کنیم `SELECT FOR UPDATE` کل Table را قفل می‌کند؛ در حالت معمول Rowهای انتخاب‌شده Lock می‌شوند، نه همه Rowهای Table.
- فراموش کنیم Transaction باید Commit یا Rollback شود تا Lockها آزاد شوند.

# **16. پاسخ آماده برای مصاحبه انگلیسی**

Oracle supports READ COMMITTED and SERIALIZABLE isolation levels, with READ COMMITTED being the default.

In READ COMMITTED, each SQL statement sees a consistent snapshot of committed data at the beginning of that statement. Therefore, non-repeatable reads and phantom reads can occur across multiple statements within the same transaction.

In SERIALIZABLE isolation, all statements within a transaction see a consistent snapshot from the beginning of the transaction. However, concurrent conflicting transactions may result in ORA-08177, so the application may need to retry the transaction.

Oracle uses MVCC and undo data to provide consistent reads without blocking writers. It also uses TX row locks and TM table locks to protect concurrent modifications.

For explicit locking, we can use SELECT FOR UPDATE, including NOWAIT, WAIT, and SKIP LOCKED options.

To prevent deadlocks, I keep transactions short, acquire locks in a consistent order, avoid unnecessary locking, and implement safe retry mechanisms when appropriate.

## **سؤال تمرینی مصاحبه**

فرض کن دو Transaction در Oracle داریم:

- Transaction A یک `SELECT` معمولی روی یک Row انجام می‌دهد.
- Transaction B همان Row را `UPDATE` می‌کند ولی Commit نمی‌کند.
- Transaction A دوباره همان `SELECT` را اجرا می‌کند.

در Oracle با Isolation Level پیش‌فرض `READ COMMITTED`:

**آیا Transaction A منتظر Transaction B می‌ماند؟ مقدار قبلی را می‌بیند یا مقدار جدید را؟ چرا؟**

این سؤال، در واقع میزان درک تو از MVCC، Undo و READ COMMITTED را مشخص می‌کند.
