### ✅ Model Answer — Q1

**Procedure vs Function**

| | Procedure | Function |
|---|---|---|
| Returns a value? | No — returns results via `OUT`/`IN OUT` parameters | **Must** `RETURN` exactly one value |
| Callable from SQL (`SELECT`, `WHERE`, …)? | **No** | **Yes** (with purity restrictions) |
| Typical use | Perform an action (DML, side effects) | Compute/return a value |

**Why "callable from SQL" matters:** A function used in a SQL statement is executed **once per row** by the SQL engine, possibly many times, possibly out of the order you'd expect, possibly inside a parallel query. That means it must be **side-effect free** — the SQL engine assumes it only reads data.

**The restriction this imposes:** a function called from SQL must **not** modify database state:
- ❌ no `INSERT` / `UPDATE` / `DELETE` / `MERGE`
- ❌ no `COMMIT` / `ROLLBACK` / `SAVEPOINT`
- ❌ no DDL (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`)
- ✅ only `SELECT` and computation

**Related modifiers:**
- `DETERMINISTIC` — promise that the same inputs always return the same output, letting Oracle cache/skip calls.
- `RESULT_CACHE` — cache return values across calls.
- `AUTHID CURRENT_USER` — run with the caller's privileges rather than the owner's (relevant to security, not purity).

**One-liner to remember:** *"A function called from SQL may only look, never touch."*
