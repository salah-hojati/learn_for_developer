تفاوت اصلی در **استفاده از ایندکس (Index) و حجم داده‌هایی است که باید پردازش شوند**。 قرار دادن `$match` **قبل از** `$group` به طور کلی بسیار کارآمدتر است، زیرا از ایندکس‌ها استفاده می‌کند و حجم داده ورودی به مرحله سنگین `$group` را به شدت کاهش می‌دهد. در مقابل، `$match` **بعد از** `$group` روی نتایج محاسبه‌شده و در حافظه اجرا می‌شود و نمی‌تواند از ایندکس‌های اصلی مجموعه بهره ببرد.

### 🆚 مقایسه مستقیم

| ویژگی | `$match` قبل از `$group` (رویکرد بهینه) | `$match` بعد از `$group` (رویکرد غیربهینه) |
| :--- | :--- | :--- |
| **استفاده از ایندکس** | **بله**. `$match` در ابتدای پایپ‌لاین مانند یک `find()` عمل می‌کند و می‌تواند از ایندکس‌های مجموعه استفاده کند. | **خیر**. `$group` ساختار داده را تغییر می‌دهد و `$match` بعد از آن روی اسناد محاسبه‌شده در حافظه اجرا می‌شود و ایندکس اصلی دیگر قابل استفاده نیست. |
| **حجم داده ورودی به `$group`** | **کم**. فقط اسناد فیلترشده وارد مرحله `$group` می‌شوند که باعث افزایش چشمگیر سرعت می‌شود. | **زیاد**. `$group` باید **تمام** اسناد مجموعه (یا تمام اسناد باقی‌مانده از مراحل قبلی) را پردازش کند، حتی اگر در نهایت بسیاری از آن‌ها فیلتر شوند. |
| **مصرف حافظه و ریسک خطا** | کمتر. با کاهش تعداد اسناد، احتمال رسیدن به محدودیت ۱۰۰ مگابایتی حافظه در هر مرحله بسیار کمتر می‌شود. | بیشتر. `$group` باید تمام اسناد را قبل از تولید خروجی در حافظه نگه دارد (عملیات blocking) که می‌تواند منجر به مصرف بالای حافظه و خطا شود. |

### 📌 `$match` قبل از `$group`: رویکرد بهینه
این الگوی استاندارد و توصیه‌شده در MongoDB است. با قرار دادن `$match` در ابتدای پایپ‌لاین، دو مزیت کلیدی نصیب شما می‌شود:

1.  **استفاده از ایندکس**: مرحله `$match` در ابتدای کار دقیقاً معادل فیلتر `find()` است و می‌تواند از ایندکس‌های تعریف‌شده روی فیلدهای فیلتر بهره ببرد. این کار اسناد مرتبط را با سرعت بسیار بالاتری پیدا می‌کند.
2.  **کاهش زودهنگام حجم داده**: با فیلتر کردن اسناد در همان ابتدا، تعداد بسیار کمتری سند به مرحله سنگین و مسدودکننده `$group` وارد می‌شود. `$group` برای کار با حجم کمتری از داده باید تلاش کند که مستقیماً زمان اجرا و مصرف حافظه را کاهش می‌دهد.

**مثال بهینه:**
```javascript
db.orders.aggregate([
  // 1. فیلتر کردن اولیه با استفاده از ایندکس
  { $match: { status: "completed", createdAt: { $gte: new Date("2024-01-01") } } },
  // 2. گروه‌بندی فقط روی داده‌های فیلترشده
  { $group: { _id: "$userId", totalAmount: { $sum: "$amount" } } }
])
```

### 📌 `$match` بعد از `$group`: رویکرد غیربهینه
وقتی `$match` را بعد از `$group` قرار می‌دهید، در واقع نتایج تجمیع‌شده را فیلتر می‌کنید. مشکل اینجاست که تا زمانی که `$group` تمام نشود، هیچ خروجی‌ای تولید نمی‌شود. به عبارت دیگر، `$group` یک مرحله **مسدودکننده (blocking)** است و باید **تمام** اسناد ورودی را پردازش کند تا بتواند اولین سند خروجی خود را تولید کند.

بنابراین، اگر `$match` بعد از `$group` قرار گیرد، `$group` مجبور است تمام اسناد مجموعه (مثلاً ۱۰ میلیون سند) را پردازش کند، صرف‌نظر از اینکه در نهایت فقط تعداد کمی از گروه‌ها در `$match` باقی بمانند. این اتلاف منابع عظیمی است.

**مثال غیربهینه:**
```javascript
db.orders.aggregate([
  // 1. گروه‌بندی روی تمام اسناد مجموعه
  { $group: { _id: "$userId", count: { $sum: 1 } } },
  // 2. فیلتر کردن نتایج گروه‌بندی‌شده (دیر شده است!)
  { $match: { count: { $gt: 100 } } }
])
```

### 💡 استثنای مهم
گاهی اوقات ممکن است به `$match` بعد از `$group` نیاز داشته باشید، اما این باید برای فیلتر کردن **نتایج تجمیع** باشد، نه برای کاهش حجم داده اولیه. برای مثال، در پایپ‌لاین زیر، `$match` دوم برای فیلتر کردن گروه‌هایی است که بیش از ۱۰۰ سفارش دارند. این یک عملیات تحلیلی معتبر است، اما همچنان باید بدانید که `$group` اولیه تمام اسناد را پردازش می‌کند.

```javascript
db.orders.aggregate([
  // فیلتر اولیه برای کاهش داده (بهینه)
  { $match: { status: "completed" } }, 
  // گروه‌بندی روی داده‌های فیلترشده
  { $group: { _id: "$userId", count: { $sum: 1 } } },
  // فیلتر کردن نتایج تجمیع (این بار برای هدف تحلیلی، نه کاهش داده اولیه)
  { $match: { count: { $gt: 100 } } } 
])
```

### 💎 جمع‌بندی
- **`$match` را تا حد امکان زودتر در پایپ‌لاین قرار دهید** تا از ایندکس‌ها استفاده کنید و حجم داده ورودی به مراحل سنگین بعدی را کاهش دهید.
- `$group` یک عملیات مسدودکننده است که از ایندکس استفاده نمی‌کند. هر چه داده کمتری به آن وارد شود، عملکرد کل پایپ‌لاین بهتر خواهد بود.
- `$match` بعد از `$group` فقط برای فیلتر کردن **نتایج محاسبه‌شده** منطقی است و نمی‌تواند جایگزین فیلتر اولیه برای بهبود عملکرد شود.
