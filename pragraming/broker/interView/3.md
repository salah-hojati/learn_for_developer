# **سؤال ۱: معماری RabbitMQ را توضیح دهید**

RabbitMQ یک Message Broker است که Producerها و Consumerها را از یکدیگر جدا می‌کند.

اجزای اصلی آن:

- **Producer:** تولیدکننده پیام
- **Exchange:** دریافت پیام از Producer و تصمیم‌گیری برای Routing
- **Queue:** نگهداری پیام تا زمان مصرف
- **Binding:** قانون اتصال Exchange به Queue
- **Routing Key:** کلیدی برای تعیین مسیر پیام
- **Consumer:** دریافت و پردازش پیام

# **سؤال ۴: Topic Exchange چگونه کار می‌کند؟**

# **سؤال ۵: تفاوت Direct، Fanout و Topic را توضیح دهید**

[RabbitMQ Cluster using AWS Peer Discovery | by Sugandh Pasricha | Medium](https://images.openai.com/static-rsc-4/lo1gAWePJK5z2o3HkAEwYeUjaAhXPXOejK1giAuJqepCAKqRz4TB5BYQTzpb4-XH-CqeyMtau1-MUfHv3jPJLGY3a4plM2XloYkiKRjIRgGWN1B791fRIqCLOtVaOzh4JPw8ZK4bMFEOwgj-zOGh-FdAYkPFSfVHURFxXaGdti0?purpose=inline)

| Exchange | روش Routing           | کاربرد                  |
| -------- | --------------------- | ----------------------- |
| Direct   | Exact Match           | Routing دقیق            |
| Fanout   | ارسال به تمام Queueها | Broadcast               |
| Topic    | Pattern Matching      | Routing منعطف           |
| Headers  | Match براساس Header   | Routing براساس Metadata |

### **جواب مصاحبه‌ای انگلیسی**

> A Direct Exchange routes messages based on an exact match between the routing key and binding key. A Fanout Exchange broadcasts messages to all bound queues, ignoring the routing key. A Topic Exchange uses wildcard patterns to route messages based on routing keys. I use Direct for exact routing, Fanout for broadcasting, and Topic when I need flexible routing patterns.

# **سؤال ۶: Headers Exchange چیست؟**

Headers Exchange پیام را براساس Headerهای پیام Route می‌کند، نه Routing Key.

مثلاً:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
{
  "headers": {
    "region": "EU",
    "type": "ORDER",
    "priority": "HIGH
  }
}
```

</div>


Binding می‌تواند تعیین کند پیام‌هایی با Headerهای مشخص به Queue خاصی ارسال شوند.

دو حالت Matching مهم:

- `x-match = all` → همه شرط‌ها باید Match شوند.
- `x-match = any` → حداقل یک شرط باید Match شود.

### **چه زمانی استفاده می‌شود؟**

وقتی Routing براساس Metadata پیام باشد و استفاده از Routing Key ساختاریافته مناسب نباشد.

با این حال، در بسیاری از پروژه‌ها Direct و Topic Exchange ساده‌تر و قابل‌فهم‌تر هستند.

# **سؤال ۷: اگر یک پیام به چند Queue متصل به Exchange ارسال شود، چه اتفاقی می‌افتد؟**

بسته به نوع Exchange و Binding، ممکن است پیام به چند Queue Route شود.

مثلاً در Fanout:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
                 Producer
                    |
                    v
               Fanout Exchange
             /       |        \
            /        |         \
           v         v          v
       Queue A   Queue B    Queue C
           |         |          |
           v         v          v
       Consumer A Consumer B Consumer C
```

</div>


در این حالت هر Queue نسخه‌ای مستقل از پیام را دریافت می‌کند.

اگر چند Consumer روی یک Queue باشند، آن‌ها معمولاً پیام‌ها را بین خود تقسیم می‌کنند؛ نه اینکه هر Consumer یک نسخه از تمام پیام‌ها را دریافت کند.

این تفاوت بسیار مهم است:

- **چند Queue متصل به Exchange:** امکان دریافت یک Event توسط چند سرویس مستقل.
- **چند Consumer روی یک Queue:** تقسیم کار بین Workerها.

### **تعریف Exchange، Queue و Binding**

```
@Configuration
public class RabbitMQConfig {

    public static final String ORDER_EXCHANGE = "order.exchange";
    public static final String ORDER_QUEUE = "order.created.queue";
    public static final String ORDER_ROUTING_KEY = "order.created";

    @Bean
    public DirectExchange orderExchange() {
        return new DirectExchange(ORDER_EXCHANGE, true, false);
    }

    @Bean
    public Queue orderQueue() {
        return QueueBuilder
                .durable(ORDER_QUEUE)
                .build();
    }

    @Bean
    public Binding orderBinding() {
        return BindingBuilder
                .bind(orderQueue())
                .to(orderExchange())
                .with(ORDER_ROUTING_KEY);
    }
}
```

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
@Service
@RequiredArgsConstructor
public class OrderProducer {

    private final RabbitTemplate rabbitTemplate;

    public void publish(OrderCreatedEvent event) {
```

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
public class OrderService {

    private final OrderRepository orderRepository;
    private final OrderProducer orderProducer;

    public void createOrder(Order order) {

        Order savedOrder = orderRepository.save(order);

        OrderCreatedEvent event = new OrderCreatedEvent(
                savedOrder.getId(),
                savedOrder.getCustomerId(),
                savedOrder.getAmount()

        orderProducer.publish(event);

}
```

### **سؤال مصاحبه**

`RabbitTemplate` چه وظیفه‌ای دارد؟

**جواب:**

`RabbitTemplate` کلاس Spring AMQP برای ارسال و دریافت پیام از RabbitMQ است. این کلاس عملیات‌هایی مانند `convertAndSend` را فراهم می‌کند تا بتوانیم پیام را با Exchange و Routing Key مشخص ارسال کنیم. همچنین با Message Converter می‌توان Objectهای Java را به قالب مناسب پیام تبدیل کرد.

# **سؤال ۱۱: چگونه Object را به JSON تبدیل می‌کنیم؟**

برای ارسال Java Object به RabbitMQ معمولاً از `Jackson2JsonMessageConverter` استفاده می‌کنیم.

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
@Configuration
public class RabbitConverterConfig {

    @Bean
    public MessageConverter jacksonMessageConverter() {
        return new Jackson2JsonMessageConverter();
    }

    @Bean
    public RabbitTemplate rabbitTemplate(
            ConnectionFactory connectionFactory,
            MessageConverter messageConverter) {

        RabbitTemplate template =
                new RabbitTemplate(connectionFactory);

        template.setMessageConverter(messageConverter);

        return template;
    }
}
```

</div>


در این حالت، Event به JSON تبدیل می‌شود.

مثلاً:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
OrderCreatedEvent event =
        new OrderCreatedEvent(100L, 20L, new BigDecimal("250"));
```

</div>


Payload:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
{
  "orderId": 100,
  "customerId": 20,
  "amount": 250
}
```

</div>


Consumer می‌تواند JSON را مجدداً به Object Java تبدیل کند.

# **سؤال ۱۲: ACK خودکار و ACK دستی در Spring RabbitMQ چه تفاوتی دارند؟**

در RabbitMQ، ACK مشخص می‌کند پیام به‌صورت موفق پردازش شده و Broker می‌تواند آن را حذف کند.

### **Auto ACK**

در حالت Auto ACK، رفتار تأیید پیام توسط Listener Container مدیریت می‌شود. در Spring RabbitMQ، حالت پیش‌فرض معمولاً `AUTO` است؛ یعنی Spring بعد از اجرای موفق Listener پیام را ACK می‌کند و اگر Listener Exception بدهد، براساس تنظیمات Error Handling و Requeue تصمیم‌گیری می‌شود.

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto
```

</div>


### **Manual ACK**

در حالت Manual، خود Consumer باید پیام را ACK یا Reject کند.

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
```

</div>


مثال:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
@Component
public class ManualAckConsumer {

    @RabbitListener(queues = "order.queue")
    public void consume(
            OrderCreatedEvent event,
            Channel channel,
            @Header(AmqpHeaders.DELIVERY_TAG) long tag
    ) throws IOException {

        try {
            process(event);

            channel.basicAck(tag, false);

        } catch (Exception e) {

            channel.basicNack(tag, false, false);
        }
    }

    private void process(OrderCreatedEvent event) {
        // Business logic
    }
}
```

</div>


در این مثال:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
channel.basicAck(tag, false);
```

</div>


یعنی پیام با موفقیت پردازش شده است.

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
channel.basicNack(tag, false, false);
```

</div>


یعنی پیام Reject شده و Requeue هم نمی‌شود.

اگر پیام به Dead Letter Exchange متصل باشد و شرایط Dead Letter شدن برقرار باشد، می‌تواند به DLQ منتقل شود.

نکته مصاحبه:

ACK را نباید قبل از انجام عملیات اصلی Business صادر کرد. اگر قبل از ذخیره اطلاعات در دیتابیس ACK کنیم و سپس برنامه Crash شود، پیام از RabbitMQ حذف شده ولی عملیات Business انجام نشده است.

# **سؤال ۱۳: اگر Consumer Exception بدهد، چه اتفاقی می‌افتد؟**

در Spring RabbitMQ، رفتار دقیق به تنظیمات Listener Container، Retry، Requeue و Error Handler بستگی دارد.

اگر Retry را تنظیم نکرده باشیم، باید رفتار پیش‌فرض را بشناسیم و به آن اکتفا نکنیم؛ چون ممکن است پیام مجدداً تحویل داده شود و باعث Retry مداوم شود.

برای Production بهتر است سیاست مشخص داشته باشیم:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
Message Received
      |
      v
Processing
      |
  +---+---+
  |       |
Success  Failure
  |       |
 ACK    Retry
          |
      Retry Limit
          |
          v
         DLQ
```

</div>


در Spring Boot می‌توان Retry را با تنظیمات Listener یا استفاده از `MessageRecoverer` و Error Handler پیاده‌سازی کرد.

# **سؤال ۱۴: آیا RabbitMQ تضمین می‌کند که پیام گم نشود؟**

**جواب مناسب مصاحبه:**

> RabbitMQ provides several mechanisms to improve message reliability, such as durable queues, persistent messages, publisher confirms, manual acknowledgments, and replicated queues. However, reliable delivery requires correct configuration and handling on both producer and consumer sides.

یعنی:

- Queue باید Durable باشد.
- پیام باید Persistent باشد.
- Producer بهتر است Publisher Confirm دریافت کند.
- Consumer باید ACK را بعد از پردازش موفق ارسال کند.
- برای HA باید از Queueهای Replicated مانند Quorum Queue استفاده شود.
- Duplicate Processing باید مدیریت شود.
