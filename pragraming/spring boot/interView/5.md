در Spring Boot، ابزار **Spring Boot Actuator** برای مانیتورینگ، بررسی سلامت (Health Check)، مشاهده وضعیت داخلی برنامه و جمع‌آوری اطلاعات عملیاتی استفاده می‌شود.

به زبان ساده، Actuator به ما کمک می‌کند بفهمیم:

- آیا برنامه سالم است؟
- آیا دیتابیس در دسترس است؟
- چقدر حافظه مصرف شده است؟
- چند درخواست HTTP دریافت شده است؟
- کدام Beanها در برنامه ساخته شده‌اند؟
- چه تنظیماتی در محیط اجرا فعال هستند؟

اما نکته مهم این است که بعضی Endpointهای Actuator اطلاعات حساسی از داخل برنامه افشا می‌کنند؛ بنابراین باید دسترسی به آن‌ها را کنترل کنیم.

# **۱. چگونه Spring Actuator را فعال کنیم؟**

ابتدا Dependency زیر را به پروژه اضافه می‌کنیم:

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

بعد از اجرای برنامه، Endpointهای Actuator در مسیر زیر قرار می‌گیرند:

```
http://localhost:8080/actuator
```

به‌صورت پیش‌فرض همه Endpointها از طریق HTTP در دسترس نیستند؛ معمولاً فقط `health` و `info` به‌صورت پیش‌فرض در معرض دسترسی HTTP قرار می‌گیرند.

# **۲. مهم‌ترین Endpointهای Actuator**

| Endpoint                | اطلاعاتی که ارائه می‌دهد             |
| ----------------------- | ------------------------------------ |
| `/actuator/health`      | وضعیت سلامت برنامه                   |
| `/actuator/info`        | اطلاعات عمومی برنامه                 |
| `/actuator/metrics`     | معیارهای عملکردی                     |
| `/actuator/env`         | Environment و تنظیمات                |
| `/actuator/beans`       | Beanهای ساخته‌شده                    |
| `/actuator/mappings`    | مسیرهای HTTP ثبت‌شده                 |
| `/actuator/loggers`     | تنظیمات Loggerها                     |
| `/actuator/threaddump`  | اطلاعات Threadها                     |
| `/actuator/heapdump`    | Heap Dump حافظه                      |
| `/actuator/configprops` | مقادیر Configuration Properties      |
| `/actuator/prometheus`  | معیارهای قابل دریافت توسط Prometheus |

برای درک بهتر، چند مورد مهم را بررسی کنیم.

# **۳. Health Endpoint**

یکی از کاربردی‌ترین Endpointها:

```
GET /actuator/health
```

خروجی نمونه:

```
{
  "status": "UP"
}
```

یعنی برنامه از نظر Health Indicatorهای فعال، سالم است.

اما اگر دیتابیس مشکل داشته باشد، ممکن است خروجی به شکل زیر باشد:

```
{
  "status": "DOWN",
  "components": {
    "db": {
      "status": "DOWN",
      "details": {
        "error": "Connection refused"
      }
    }
  }
}
```

Health می‌تواند وضعیت وابستگی‌هایی مانند موارد زیر را بررسی کند:

- Database
- Disk Space
- Redis
- RabbitMQ
- Elasticsearch

البته وجود هر Health Indicator به Dependencyهای موجود و تنظیمات پروژه بستگی دارد.

### **Liveness و Readiness**

در محیط Kubernetes این دو مفهوم بسیار مهم هستند.

```
/actuator/health/liveness
/actuator/health/readiness
```

| نوع       | مفهوم                                       |
| --------- | ------------------------------------------- |
| Liveness  | آیا برنامه هنوز زنده است و باید اجرا بماند؟ |
| Readiness | آیا برنامه آماده دریافت درخواست است؟        |

مثلاً اگر دیتابیس موقتاً قطع شود، ممکن است برنامه هنوز زنده باشد، اما آماده پاسخ‌گویی به درخواست‌های وابسته به دیتابیس نباشد.

# **۴. Metrics Endpoint**

با استفاده از:

```
GET /actuator/metrics
```

می‌توانیم معیارهای عملکردی برنامه را مشاهده کنیم.

مثلاً:

```
GET /actuator/metrics/jvm.memory.used
```

اطلاعات مصرف حافظه JVM را نمایش می‌دهد.

نمونه معیارهای مهم:

| Metric                 | کاربرد                   |
| ---------------------- | ------------------------ |
| `jvm.memory.used`      | میزان حافظه مصرف‌شده JVM |
| `jvm.threads.live`     | تعداد Threadهای فعال     |
| `process.cpu.usage`    | مصرف CPU پردازش          |
| `http.server.requests` | آمار درخواست‌های HTTP    |
| `system.cpu.usage`     | مصرف CPU سیستم           |

برای مانیتورینگ حرفه‌ای معمولاً Actuator را به Micrometer و Prometheus متصل می‌کنیم.

**Spring Boot Application**

Actuator + Micrometer

**Prometheus**

جمع‌آوری Metrics

**Grafana**

نمایش Dashboard و نمودارها

# **۵. Info Endpoint**

با استفاده از:

```
GET /actuator/info
```

می‌توانیم اطلاعات عمومی برنامه را نمایش دهیم.

مثلاً در `application.yml`:

```
info:
  app:
    name: User Management
    version: 2.0.0
    description: User Management System
```

خروجی:

```
{
  "app": {
    "name": "User Management",
    "version": "2.0.0",
    "description": "User Management System"
  }
}
```

این اطلاعات برای تشخیص نسخه برنامه در محیط Production مفید است.

# **۶. ریسک‌های امنیتی Spring Actuator چیست؟**

این بخش برای مصاحبه بسیار مهم است.

اگر Endpointهای Actuator بدون محدودیت در اینترنت منتشر شوند، ممکن است اطلاعات حساس برنامه افشا شوند یا حتی امکان تغییر رفتار برنامه به وجود بیاید.

مهم‌ترین ریسک‌ها:

## **ریسک اول: افشای اطلاعات محیط اجرا**

Endpoint:

```
/actuator/env
```

می‌تواند اطلاعات مربوط به Environment و Property Sourceها را نمایش دهد.

اطلاعات حساس احتمالی:

- Database URL
- نام کاربری دیتابیس
- API Key
- اطلاعات اتصال به سرویس‌های خارجی
- تنظیمات امنیتی

Spring Boot در بسیاری از نسخه‌ها مقادیر حساس را Mask می‌کند، اما نباید به این قابلیت به‌عنوان تنها لایه امنیتی اعتماد کرد.

## **ریسک دوم: افشای اطلاعات داخلی برنامه**

Endpointهایی مانند:

```
/actuator/beans
/actuator/mappings
/actuator/configprops
```

ممکن است ساختار داخلی برنامه را آشکار کنند.

برای مثال مهاجم می‌تواند اطلاعاتی درباره این موارد به دست بیاورد:

- Beanهای ثبت‌شده
- APIهای موجود
- تنظیمات داخلی
- ساختار سرویس‌ها

این اطلاعات می‌توانند به مهاجم برای شناسایی سطح حمله کمک کنند.

## **ریسک سوم: تغییر تنظیمات Logging**

Endpoint زیر:

```
/actuator/loggers
```

در صورت فعال‌بودن قابلیت تغییر، می‌تواند سطح Logging را در زمان اجرا تغییر دهد.

مثلاً:

```
POST /actuator/loggers/com.example
```

با ارسال درخواست مناسب می‌توان سطح Logging را تغییر داد.

این قابلیت برای Debug کردن مفید است، اما اگر دسترسی آن کنترل نشود، ممکن است باعث افشای اطلاعات حساس در Logها یا مصرف بیش از حد منابع شود.

## **ریسک چهارم: Heap Dump**

Endpoint:

```
/actuator/heapdump
```

می‌تواند Snapshot حافظه JVM را در اختیار درخواست‌کننده قرار دهد.

این اطلاعات ممکن است شامل مواردی مانند موارد زیر باشد:

- اطلاعات کاربران
- Tokenهای احراز هویت
- داده‌های حساس موجود در حافظه
- اطلاعات اتصال به سرویس‌ها

ریسک امنیتی بالا

به همین دلیل Heap Dump نباید برای کاربران عمومی قابل دسترسی باشد.

## **ریسک پنجم: Shutdown Endpoint**

Endpoint زیر در صورت فعال‌سازی:

```
POST /actuator/shutdown
```

می‌تواند برنامه را خاموش کند.

اگر این Endpoint بدون کنترل دسترسی منتشر شود، مهاجم ممکن است بتواند سرویس را متوقف کند.

نکته: این Endpoint به‌صورت پیش‌فرض فعال نیست.

# **۷. چگونه Spring Actuator را امن کنیم؟**

من برای Production چند اقدام مشخص انجام می‌دهم.

### **اقدام اول: فقط Endpointهای ضروری را فعال می‌کنم**

در `application-prod.yml`:

```
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
```

در این حالت فقط Endpointهای مشخص‌شده از طریق HTTP در دسترس قرار می‌گیرند.

توجه کن که `include` تعیین می‌کند کدام Endpointها در معرض HTTP باشند؛ این به‌تنهایی احراز هویت یا Authorization ایجاد نمی‌کند.

### **اقدام دوم: اطلاعات حساس Health را مخفی می‌کنم**

```
management:
  endpoint:
    health:
      show-details: never
```

در صورت نیاز، می‌توانیم جزئیات را فقط برای کاربران مجاز نمایش دهیم:

```
management:
  endpoint:
    health:
      show-details: when-authorized
```

### **اقدام سوم: از Spring Security استفاده می‌کنم**

مثلاً می‌توانیم دسترسی به Endpointهای مدیریتی را محدود کنیم:

```
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http) throws Exception {

        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health")
                    .permitAll()
                .requestMatchers("/actuator/**")
                    .hasRole("ADMIN")
                .anyRequest()
                    .authenticated()
            )
            .httpBasic(Customizer.withDefaults());

        return http.build();
    }
}
```

در این مثال:

- Health عمومی است.
- سایر Endpointهای Actuator فقط برای کاربران دارای Role برابر `ADMIN` قابل دسترسی هستند.
- سایر درخواست‌ها نیز نیاز به احراز هویت دارند.

در پروژه واقعی باید Authentication و Authorization مناسب سازمان را پیاده‌سازی کنیم و دسترسی مدیریتی را به شبکه یا کاربران مجاز محدود کنیم.

### **اقدام چهارم: استفاده از پورت مدیریتی جداگانه**

می‌توانیم Endpointهای مدیریتی را روی پورت جداگانه اجرا کنیم:

```
management:
  server:
    port: 9090
```

در این حالت:

```
Application: http://localhost:8080
Actuator:    http://localhost:9090
```

این کار به جداسازی سطح دسترسی کمک می‌کند؛ البته به‌تنهایی امنیت ایجاد نمی‌کند. باید Firewall، Network Policy یا محدودیت شبکه نیز اعمال شود.

## **پاسخ حرفه‌ای برای مصاحبه**

اگر بپرسند:

**What information does Spring Boot Actuator provide, and what are its security risks?**

می‌توانی این‌طور پاسخ بدهی:

> Spring Boot Actuator provides production-ready monitoring and management endpoints.
>
> It exposes useful information such as application health, JVM metrics, HTTP request statistics, environment properties, registered beans, and application mappings.
>
> I usually integrate Actuator with Micrometer and Prometheus for monitoring and Grafana for visualization.
>
> However, exposing sensitive endpoints such as env, beans, mappings, heapdump, and loggers can create security risks.
>
> To secure Actuator, I expose only the necessary endpoints, apply Spring Security authorization, hide sensitive health details, and preferably isolate management endpoints on a separate network or port.

## **سؤال تمرینی مصاحبه**

فرض کن در Production این تنظیم را داریم:

```
management:
  endpoints:
    web:
      exposure:
        include: "*"
```

**سه ریسک امنیتی این تنظیم چیست و برای اصلاح آن چه پیشنهادی می‌دهی؟**

نکته کلیدی: `exposure.include: "*"` به معنی عمومی‌شدن خودکار تمام Endpointها بدون هیچ محدودیت دیگری نیست، اما تمام Endpointهای قابل‌دسترسی از طریق Web را در معرض انتشار قرار می‌دهد و باید حتماً با کنترل دسترسی مناسب همراه باشد.
