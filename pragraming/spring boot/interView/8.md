اگر بخواهم یک اپلیکیشن قدیمی Java EE یا Struts را به Spring Boot مهاجرت بدهم، **هیچ‌وقت در قدم اول کل سیستم را بازنویسی نمی‌کنم.** استراتژی من مهاجرت تدریجی، کاهش ریسک و حفظ عملکرد سیستم در طول مهاجرت است.

معمولاً از ترکیب سه رویکرد استفاده می‌کنم:

1. **Incremental Migration:** مهاجرت مرحله‌به‌مرحله.
2. **Strangler Fig Pattern:** جایگزینی تدریجی بخش‌های قدیمی با بخش‌های جدید.
3. **Clean Architecture / Layered Architecture:** جداسازی منطق کسب‌وکار از Framework و لایه نمایش.

بیایید این استراتژی را با جزئیات بررسی کنیم.

# **۱. مرحله اول: بررسی و شناخت سیستم موجود (Assessment)**

قبل از هر تغییری باید معماری فعلی را بشناسم.

در یک پروژه قدیمی Java EE یا Struts ممکن است چنین ساختاری داشته باشیم:

## **Legacy Architecture**

**Struts Action / JSP**

Presentation Layer

**Business Logic / EJB**

Business Layer

**DAO / JDBC / JPA**

Persistence Layer

**Oracle / SQL Server**

Database

در این مرحله موارد زیر را بررسی می‌کنم:

- نسخه Java و Java EE مورد استفاده.
- استفاده از Struts 1 یا Struts 2.
- استفاده از EJB، JMS، JTA و JNDI.
- نحوه مدیریت Transactionها.
- وابستگی به Application Server مثل WebLogic، WebSphere یا JBoss.
- نحوه مدیریت Session و Authentication.
- وابستگی‌های خارجی و کتابخانه‌های قدیمی.
- ارتباط بین ماژول‌ها و میزان Coupling.
- تست‌های موجود و پوشش تست.

**خروجی این مرحله:** یک نقشه معماری و فهرست وابستگی‌ها و ریسک‌های مهاجرت.

# **۲. مرحله دوم: ایجاد تست برای سیستم قدیمی**

قبل از تغییر رفتار سیستم باید مطمئن شویم که عملکرد فعلی را می‌شناسیم.

در پروژه‌های Legacy معمولاً مستندات کامل نیستند؛ بنابراین از تست برای استخراج رفتار واقعی سیستم استفاده می‌کنم.

مثلاً:

```
@Test
void shouldCalculateOrderTotal() {

    Order order = createSampleOrder();

    BigDecimal total = legacyOrderService.calculateTotal(order);

    assertEquals(
        new BigDecimal("150.00"),
        total
    );
}
```

این نوع تست‌ها را Characterization Tests می‌نامیم.

هدف آن‌ها لزوماً اثبات درست بودن منطق قدیمی نیست؛ بلکه ثبت رفتار فعلی است تا هنگام مهاجرت ناخواسته آن را تغییر ندهیم.

همچنین برای APIهای مهم تست Integration و تست Regression ایجاد می‌کنم.

# **۴. مرحله چهارم: جایگزینی فناوری‌های قدیمی**

یکی از مهم‌ترین قسمت‌های مهاجرت، جایگزینی تکنولوژی‌های Java EE و Struts با معادل‌های Spring Boot است.

| تکنولوژی قدیمی    | جایگزین پیشنهادی                               |
| ----------------- | ---------------------------------------------- |
| Struts Action     | Spring MVC Controller                          |
| JSP               | Thymeleaf یا React/Angular                     |
| EJB Session Bean  | Spring `@Service`                              |
| EJB MDB           | `@JmsListener`                                 |
| JPA EntityManager | Spring Data JPA یا EntityManager               |
| JTA               | Spring `@Transactional`                        |
| JNDI DataSource   | Spring DataSource Configuration                |
| Servlet Filter    | Spring Security Filter / Servlet Filter        |
| `web.xml`         | Java Configuration / Spring Boot Configuration |
| EJB Timer         | Spring Scheduling یا ابزار زمان‌بندی مناسب     |
| JAX-RS            | Spring MVC REST Controller                     |

البته این جایگزینی‌ها همیشه یک‌به‌یک نیستند.

مثلاً EJB فقط یک Service ساده نیست؛ ممکن است قابلیت‌هایی مثل Security، Transaction، Concurrency و Timer داشته باشد. بنابراین قبل از جایگزینی باید مشخص کنیم کدام قابلیت‌ها واقعاً استفاده شده‌اند.

## **مثال: مهاجرت از EJB به Spring Service**

کد قدیمی:

```
@Stateless
public class OrderServiceBean {

    @PersistenceContext
    private EntityManager entityManager;

    public void createOrder(Order order) {

        entityManager.persist(order);
    }
}
```

نسخه جدید:

```
@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public void createOrder(Order order) {

        orderRepository.save(order);
    }
}
```

در این مثال:

- `@Stateless` با `@Service` جایگزین شده است.
- مدیریت Transaction به Spring سپرده شده است.
- دسترسی به دیتابیس از طریق Repository انجام می‌شود.

اما باید رفتار Transaction قبلی، خصوصاً Propagation و Rollback، با رفتار جدید تطبیق داده شود.

# **۵. مرحله پنجم: مهاجرت تدریجی با Strangler Fig Pattern**

**مرحله دوم: مهاجرت User Management**

# **۶. مرحله ششم: مدیریت Database و Transaction**

این قسمت معمولاً یکی از پیچیده‌ترین بخش‌های مهاجرت است.

اگر اپلیکیشن قدیمی و جدید هم‌زمان از یک دیتابیس استفاده کنند، باید مراقب موارد زیر باشیم:

- سازگاری Schema.
- تغییرات هم‌زمان داده‌ها.
- Transactionهای توزیع‌شده.
- Foreign Key و Constraintها.
- مدیریت Migration با Flyway یا Liquibase.
- جلوگیری از اجرای دوباره عملیات (Duplicate Processing).

پیشنهاد من:

1. در شروع، در صورت امکان Schema دیتابیس را حفظ می‌کنم.
2. تغییرات ساختاری را با Flyway یا Liquibase مدیریت می‌کنم.
3. از اجرای هم‌زمان دو منطق برای نوشتن یک داده جلوگیری می‌کنم.
4. برای عملیات بین چند سرویس از Saga یا Outbox Pattern استفاده می‌کنم، نه اینکه فرض کنم یک Transaction دیتابیس می‌تواند همه سیستم‌ها را Rollback کند.

نکته: استفاده موقت از دیتابیس مشترک می‌تواند مهاجرت را آسان‌تر کند، اما باید یک وضعیت انتقالی کنترل‌شده باشد، نه معماری نهایی بدون برنامه.

# **۷. مرحله هفتم: Security و Session Management**

در پروژه‌های قدیمی ممکن است از موارد زیر استفاده شده باشد:

- `HttpSession`
- JAAS
- Container-managed Security
- Custom Authentication Filter
- LDAP
- JNDI Security Realm

در Spring Boot معمولاً از Spring Security استفاده می‌کنم.

برای مثال:

```
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http) throws Exception {

        return http
                .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/api/public/**").permitAll()
                    .anyRequest().authenticated()
                )
                .httpBasic(Customizer.withDefaults())
                .build();
    }
}
```

این فقط یک مثال ساده است؛ در Production معمولاً Authentication مناسب مثل OAuth2/OIDC یا روش متناسب با زیرساخت سازمان را انتخاب می‌کنم.

همچنین اگر سیستم قدیمی و جدید هم‌زمان فعال باشند، باید تکلیف Session، Cookie، SSO و انتقال هویت کاربر مشخص شود.

# **۸. مرحله هشتم: تست، مانیتورینگ و Deployment**

قبل از انتقال هر ماژول به Production موارد زیر را بررسی می‌کنم:

| نوع تست          | هدف                             |
| ---------------- | ------------------------------- |
| Unit Test        | تست Business Logic              |
| Integration Test | تست ارتباط Service و Repository |
| API Test         | تست قراردادهای REST             |

همچنین برای هر مرحله برنامه Rollback دارم؛ یعنی اگر نسخه جدید مشکل داشت، بتوانیم Routing را به نسخه قدیمی برگردانیم.

# **۹. نقشه راه پیشنهادی مهاجرت**

1. **Assessment**

   شناخت معماری، وابستگی‌ها، فناوری‌ها و ریسک‌ها.
2. **Characterization Testing**

   ثبت رفتار فعلی با تست‌های Regression.
3. **Target Architecture**

   طراحی معماری Spring Boot و جداسازی لایه‌ها.
4. **Infrastructure Preparation**

   مهاجرت ماژول به ماژول با Strangler Pattern.

7. **Legacy Decommissioning**

   حذف تدریجی بخش‌های قدیمی پس از اطمینان از جایگزینی کامل.

# **۱۰. پاسخ حرفه‌ای برای مصاحبه (English)**

اگر در مصاحبه از من بپرسند چطور یک اپلیکیشن Java EE یا Struts را به Spring Boot مهاجرت می‌دهم، این‌طور پاسخ می‌دهم:

> I would avoid a big-bang rewrite because it introduces significant technical and business risks.
>
> First, I would assess the existing application, identify its dependencies, business workflows, transaction boundaries, security mechanisms, and integration points.
>
> Then, I would create characterization and regression tests to capture the existing behavior.
>
> Next, I would design the target Spring Boot architecture, separating controllers, services, and repositories, and replacing legacy technologies such as Struts Actions, EJBs, and JTA with appropriate Spring alternatives.
>
> I would use the Strangler Fig Pattern to migrate the application incrementally, module by module, while keeping the legacy system operational.
>
> Finally, I would validate data consistency, security, performance, and business behavior before decommissioning the legacy components.
>
> My main goals would be minimizing business disruption, reducing migration risk, and ensuring a maintainable architecture.

## **یک نکته مهم برای سطح Senior Developer**

مصاحبه‌کننده ممکن است سؤال را عمیق‌تر کند:

**فرض کن اپلیکیشن قدیمی Struts و اپلیکیشن جدید Spring Boot هر دو به یک دیتابیس متصل هستند. کاربر یک سفارش ثبت می‌کند و در هر دو سیستم امکان ثبت سفارش وجود دارد. چطور از ثبت سفارش تکراری یا ناسازگاری داده جلوگیری می‌کنی؟**

پاسخ حرفه‌ای باید به Idempotency، مالکیت داده (Data Ownership)، Transaction Boundary و کنترل هم‌زمانی (Concurrency Control) اشاره کند.

این سؤال یکی از بهترین راه‌ها برای سنجش تجربه واقعی مهاجرت سیستم‌های Legacy است.
