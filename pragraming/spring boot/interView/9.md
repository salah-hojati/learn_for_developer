در Spring Security، من پیاده‌سازی امنیت را بر اساس دو مفهوم اصلی طراحی می‌کنم:

1. **Authentication (احراز هویت):** کاربر چه کسی است؟
2. **Authorization (مجوز دسترسی):** این کاربر اجازه انجام چه کاری را دارد؟

برای مثال، فرض کن یک سیستم فروشگاهی داریم:

- کاربر با Username و Password وارد سیستم می‌شود.
- سرور اطلاعات کاربر را بررسی می‌کند.
- اگر اطلاعات معتبر بود، یک JWT صادر می‌کند.
- کاربر در درخواست‌های بعدی JWT را ارسال می‌کند.
- Spring Security توکن را اعتبارسنجی می‌کند و بررسی می‌کند آیا کاربر مجوز دسترسی به API موردنظر را دارد یا خیر.

## **۱. معماری Spring Security و Filter Chain**

یکی از مهم‌ترین مفاهیم Spring Security، **Security Filter Chain** است.

Spring Security درخواست HTTP را قبل از رسیدن به Controller از یک زنجیره Filter عبور می‌دهد.

## **Spring Security Request Flow**

**HTTP Request**

Authorization: Bearer JWT

**DelegatingFilterProxy**

Bridge between Servlet Container and Spring Security

**FilterChainProxy**

Selects the matching SecurityFilterChain

**Security Filter Chain**

SecurityContextHolderFilter

BearerTokenAuthenticationFilter (JWT Resource Server)

AnonymousAuthenticationFilter

ExceptionTranslationFilter

AuthorizationFilter

**Controller**

Business Logic

این تصویر مفهومی است؛ ترتیب دقیق Filterها به Configuration و نسخه Spring Security بستگی دارد.

### **نقش Filterها چیست؟**

| Filter                                 | وظیفه                                                |
| -------------------------------------- | ---------------------------------------------------- |
| `SecurityContextHolderFilter`          | مدیریت Security Context درخواست                      |
| `BearerTokenAuthenticationFilter`      | استخراج و اعتبارسنجی Bearer Token در Resource Server |
| `UsernamePasswordAuthenticationFilter` | پردازش احراز هویت Username/Password در فرم لاگین     |
| `AnonymousAuthenticationFilter`        | ایجاد Authentication ناشناس در صورت نبود هویت        |
| `ExceptionTranslationFilter`           | تبدیل خطاهای امنیتی به پاسخ مناسب مثل 401 و 403      |
| `AuthorizationFilter`                  | بررسی مجوز دسترسی به درخواست                         |

نکته مهم: همه این Filterها الزاماً در هر پروژه یا هر درخواست فعال نیستند.

## **۲. Authentication چگونه انجام می‌شود؟**

فرض کن کاربر اطلاعات زیر را ارسال می‌کند:

```
{
  "username": "ali",
  "password": "123456"
}
```

در Spring Security معمولاً فرآیند احراز هویت از این اجزا استفاده می‌کند:

- `Authentication`: اطلاعات مربوط به هویت و اعتبارنامه کاربر.
- `AuthenticationManager`: نقطه ورود برای انجام Authentication.
- `AuthenticationProvider`: منطق بررسی اعتبار اطلاعات.
- `UserDetailsService`: بارگذاری اطلاعات کاربر.
- `PasswordEncoder`: بررسی Password Hash.

جریان معمول:

**Username + Password**

**AuthenticationManager**

**AuthenticationProvider**

**UserDetailsService**

**PasswordEncoder**

**Authenticated Authentication**

مثلاً `UserDetailsService` اطلاعات کاربر را از دیتابیس می‌خواند و `PasswordEncoder` رمز واردشده را با Hash ذخیره‌شده مقایسه می‌کند.

در حالت موفق، یک Authentication معتبر ایجاد می‌شود.

## **۳. JWT چیست و چرا استفاده می‌کنیم؟**

JWT مخفف JSON Web Token است.

JWT یک توکن امضاشده است که می‌تواند اطلاعاتی مثل موارد زیر را در خود داشته باشد:

- شناسه کاربر (`sub`)
- نقش‌ها (`roles`)
- زمان صدور (`iat`)
- زمان انقضا (`exp`)

ساختار JWT از سه قسمت تشکیل شده است:

HEADER

## **.**

PAYLOAD

## **.**

SIGNATURE

Header.Payload.Signature

**Header:** الگوریتم امضا و نوع توکن.

**Payload:** اطلاعات یا Claims مربوط به کاربر.

**Signature:** امضایی برای تشخیص تغییر یا دستکاری توکن.

نکته امنیتی مهم: Payload معمولاً فقط Base64URL-encoded است، نه رمزگذاری‌شده. بنابراین اطلاعات محرمانه مثل Password یا اطلاعات حساس را داخل آن قرار نمی‌دهیم.

## **۴. چرخه کامل کار با JWT**

در یک سیستم مبتنی بر JWT دو مرحله اصلی داریم:

### **مرحله اول: Login و دریافت Token**

**1. Client**

ارسال Username و Password

**2. AuthenticationManager**

بررسی اطلاعات کاربر

**3. UserDetailsService + PasswordEncoder**

خواندن کاربر و بررسی Password

**4. JWT Issuer**

صدور JWT امضاشده

**5. Client**

دریافت و نگهداری Token

مثلاً پاسخ Login می‌تواند چنین باشد:

```
{
  "accessToken": "eyJhbGciOiJSUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

### **مرحله دوم: ارسال درخواست‌های بعدی**

کاربر برای دسترسی به API، توکن را در Header درخواست ارسال می‌کند:

```
GET /api/orders
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
```

سپس Spring Security:

1. توکن را استخراج می‌کند.
2. امضای آن را اعتبارسنجی می‌کند.
3. زمان انقضا (`exp`) و سایر محدودیت‌های اعتبار را بررسی می‌کند.
4. اطلاعات هویتی و مجوزهای کاربر را استخراج می‌کند.
5. Authentication را در Security Context قرار می‌دهد.
6. دسترسی کاربر به Endpoint را بررسی می‌کند.

اگر همه مراحل موفق باشند، درخواست به Controller می‌رسد.

## **۵. پیاده‌سازی JWT در Spring Boot**

در Spring Security جدید، پیشنهاد من استفاده از قابلیت داخلی **OAuth2 Resource Server** برای اعتبارسنجی JWT است؛ نه اینکه برای هر پروژه یک JWT Filter اختصاصی بنویسیم.

این روش استانداردتر است و قابلیت‌های اعتبارسنجی توکن را در اختیار Spring Security قرار می‌دهد.

### **قدم اول: اضافه کردن Dependency**

در Maven:

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>
</dependency>
```

### **قدم دوم: تعریف SecurityFilterChain**

```
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http) throws Exception {

        return http
            .csrf(csrf -> csrf.disable())

            .sessionManagement(session ->
                session.sessionCreationPolicy(
                    SessionCreationPolicy.STATELESS
                )
            )

            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**")
                    .hasRole("ADMIN")
                .requestMatchers("/api/user/**")
                    .hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()
            )

            .oauth2ResourceServer(oauth2 ->
                oauth2.jwt(Customizer.withDefaults())
            )

            .build();
    }
}
```

چند نکته مهم درباره این Configuration:

**۱.&#x20;**`csrf.disable()`

در این مثال فرض کرده‌ایم API از Bearer Token استفاده می‌کند و مرورگر به‌صورت خودکار اعتبارنامه را همراه درخواست ارسال نمی‌کند.

اگر JWT را در Cookie قرار دهیم یا از Session و Cookie Authentication استفاده کنیم، غیرفعال کردن CSRF بدون بررسی شرایط امنیتی درست نیست.

**۲.&#x20;**`STATELESS`

```
SessionCreationPolicy.STATELESS
```

یعنی برای نگهداری وضعیت احراز هویت درخواست‌ها به HTTP Session متکی نیستیم. هر درخواست باید اعتبارنامه موردنیاز خودش را ارائه کند.

**۳.&#x20;**`oauth2ResourceServer()`

این بخش به Spring Security می‌گوید JWTهای ارسال‌شده در Bearer Header را پردازش و اعتبارسنجی کند.

**۴.&#x20;**`hasRole("ADMIN")`

Spring به‌صورت پیش‌فرض این شرط را با Authority به نام `ROLE_ADMIN` بررسی می‌کند.

### **قدم سوم: تنظیم اعتبارسنجی JWT**

اگر از یک Authorization Server استفاده کنیم، می‌توانیم آدرس Issuer را مشخص کنیم:

```
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com
```

Spring با استفاده از اطلاعات منتشرشده توسط Issuer، کلیدهای لازم برای اعتبارسنجی امضا و اطلاعات مربوط به Issuer را دریافت می‌کند.

اگر خودمان JWT صادر می‌کنیم، باید کلید امضا و سازوکار اعتبارسنجی را به‌درستی تنظیم کنیم. برای مثال، می‌توان از RSA و کلید عمومی/خصوصی استفاده کرد.

## **۶. نقش Authentication و Authorization در JWT**

این دو مفهوم را نباید با یکدیگر اشتباه بگیریم.

فرض کن JWT متعلق به کاربری با نقش USER باشد.

```
{
  "sub": "1001",
  "roles": ["USER"],
  "exp": 1795120000
}
```

این کاربر احراز هویت شده است، اما اجازه دسترسی به بخش Admin را ندارد.

در Spring Security:

```
.requestMatchers("/api/admin/**")
.hasRole("ADMIN")
```

در این حالت:

- اگر توکن معتبر نباشد یا وجود نداشته باشد: معمولاً `401 Unauthorized`
- اگر توکن معتبر باشد ولی کاربر مجوز کافی نداشته باشد: `403 Forbidden`

می‌توانیم Authorization را در سطح متد هم انجام دهیم:

```
@Configuration
@EnableMethodSecurity
public class MethodSecurityConfig {
}
```

و سپس:

```
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    // Delete user
}
```

این کار باعث می‌شود حتی اگر متد از مسیر دیگری فراخوانی شود، کنترل دسترسی در لایه Service هم اعمال شود.

## **۷. JWT چه مزایا و محدودیت‌هایی دارد؟**

| مزایا                                | محدودیت‌ها                                    |
| ------------------------------------ | --------------------------------------------- |
| مناسب برای REST API                  | ابطال فوری توکن دشوارتر است                   |
| مناسب برای معماری Microservices      | مدیریت کلیدها اهمیت زیادی دارد                |
| عدم نیاز به Session برای هر درخواست  | اندازه Token می‌تواند زیاد شود                |
| امکان اعتبارسنجی مستقل توسط سرویس‌ها | تغییر Role ممکن است تا انقضای توکن منعکس نشود |
| مناسب برای ارتباط با OAuth2/OIDC     | نگهداری امن Token در Client ضروری است         |

### **نکات امنیتی مهم در Production**

1. از الگوریتم‌های امن مثل RS256 یا ES256 استفاده کن و الگوریتم مجاز را محدود کن.
2. برای Access Token زمان انقضای کوتاه در نظر بگیر.
3. Refresh Token را جداگانه و با سیاست امنیتی مناسب مدیریت کن.
4. Secret Key یا Private Key را داخل Git قرار نده.
5. از HTTPS استفاده کن.
6. اطلاعات حساس را داخل JWT قرار نده.
7. `issuer`، `audience` و زمان انقضا را متناسب با معماری اعتبارسنجی کن.
8. برای ابطال توکن‌های سرقت‌شده، بسته به نیاز از Token Revocation، Token Versioning یا سازوکارهای مشابه استفاده کن.
9. اگر از OAuth2/OIDC استفاده می‌کنی، ترجیحاً صدور Token را به Authorization Server بسپار.

نکته مهم: JWT به‌خودی‌خود معادل OAuth2 نیست. JWT یک قالب توکن است؛ OAuth2 یک چارچوب Authorization است و OpenID Connect لایه احراز هویت مبتنی بر OAuth2 را فراهم می‌کند.

## **۸. تفاوت Session-Based Authentication و JWT**

| ویژگی             | Session-Based                  | JWT-Based                         |
| ----------------- | ------------------------------ | --------------------------------- |
| محل نگهداری وضعیت | سمت سرور                       | اطلاعات هویتی در Token سمت Client |
| ارسال اعتبارنامه  | معمولاً Cookie                 | معمولاً Bearer Header             |
| Stateless         | خیر                            | معمولاً بله                       |
| ابطال دسترسی      | با حذف یا غیرفعال کردن Session | نیازمند سازوکار تکمیلی            |
| مناسب برای        | برنامه‌های وب سنتی             | REST API و معماری توزیع‌شده       |

البته JWT همیشه بهترین انتخاب نیست. برای یک وب‌اپلیکیشن سنتی که Backend و Frontend آن با هم هستند، Session-Based Authentication می‌تواند ساده‌تر و امن‌تر باشد.

## **۹. پاسخ مناسب برای مصاحبه (English)**

> I would implement Spring Security using a SecurityFilterChain-based configuration.
>
> First, I would separate authentication from authorization. Authentication verifies the user's identity, while authorization determines what resources the user can access.
>
> Spring Security processes incoming HTTP requests through a chain of security filters before they reach the controller.
>
> For a REST API, I would typically use stateless authentication with JWT. During login, the credentials are authenticated using AuthenticationManager and an appropriate AuthenticationProvider.
>
> After successful authentication, an access token is issued. The client sends this token in the Authorization header using the Bearer scheme.
>
> Spring Security's OAuth2 Resource Server support validates the JWT signature and claims, creates an authenticated SecurityContext, and applies authorization rules.
>
> Finally, I would secure the application with HTTPS, short-lived access tokens, secure key management, appropriate role-based access control, and a suitable refresh-token strategy.
