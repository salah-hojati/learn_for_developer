Annotation `@Transactional` در Spring برای مدیریت خودکار Transactionهای دیتابیس استفاده می‌شود؛ اما محدودیت‌هایی دارد که یکی از مهم‌ترین آن‌ها **Self-invocation** است.

برای درک این موضوع، ابتدا باید بدانیم Spring چگونه Transaction را مدیریت می‌کند.

# **۱. @Transactional چگونه کار می‌کند؟**

وقتی روی یک متد از `@Transactional` استفاده می‌کنیم، Spring معمولاً با استفاده از **AOP Proxy** اجرای آن متد را کنترل می‌کند.

یعنی فراخوانی متد از Proxy عبور می‌کند و Proxy مسئول موارد زیر می‌شود:

1. شروع Transaction یا پیوستن به Transaction موجود
2. اجرای متد
3. Commit در صورت موفقیت
4. Rollback در صورت وقوع Exception مناسب

مثال:

```
@Service
public class UserService {

    @Transactional
    public void createUser(User user) {

        userRepository.save(user);

        // Other database operations
    }
}
```

به‌صورت مفهومی، Spring چیزی شبیه این رفتار ایجاد می‌کند:

```
beginTransaction();

try {
    createUser(user);
    commit();
} catch (RuntimeException e) {
    rollback();
    throw e;
}
```

البته این فقط نمایش مفهومی است؛ پیاده‌سازی واقعی Spring از Transaction Manager و AOP استفاده می‌کند.

# **۲. Self-invocation چیست؟**

Self-invocation یعنی یک متد داخل یک کلاس، متد دیگری از همان کلاس را مستقیماً فراخوانی کند.

به مثال زیر توجه کن:

```
@Service
public class UserService {

    public void registerUser(User user) {

        saveUser(user);
    }

    @Transactional
    public void saveUser(User user) {

        userRepository.save(user);
    }
}
```

شاید انتظار داشته باشیم وقتی `registerUser()` متد `saveUser()` را صدا می‌زند، Spring یک Transaction ایجاد کند.

اما مشکل اینجاست:

**فراخوانی داخلی متد از Proxy عبور نمی‌کند.**

چرا؟

چون `registerUser()` مستقیماً متد `saveUser()` را روی همان Object فراخوانی می‌کند.

**فراخوانی عادی از خارج Bean**

Controller

Spring Proxy

شروع Transaction

UserService.saveUser()

**فراخوانی داخلی (Self-invocation)**

UserService.registerUser()

UserService.saveUser()

بدون عبور از Proxy

در نتیجه، تنظیمات `@Transactional` روی `saveUser()` در این فراخوانی داخلی اعمال نمی‌شوند.

البته اگر متد بیرونی خودش Transaction داشته باشد، متد داخلی همچنان داخل همان Transaction اجرا می‌شود؛ مشکل این است که تنظیمات اختصاصی متد داخلی از طریق Proxy اعمال نمی‌شوند.

# **۳. راه‌حل Self-invocation چیست؟**

چند روش وجود دارد.

## **روش اول: انتقال متد به یک Service دیگر (پیشنهاد اصلی)**

بهترین روش معمولاً جداسازی مسئولیت‌ها است.

کلاس اول:

```
@Service
public class UserService {

    @Autowired
    private UserTransactionService transactionService;

    public void registerUser(User user) {

        transactionService.saveUser(user);
    }
}
```

کلاس دوم:

```
@Service
public class UserTransactionService {

    @Transactional
    public void saveUser(User user) {

        userRepository.save(user);
    }
}
```

حالا فراخوانی از Bean اول به Bean دوم از Proxy عبور می‌کند.

راهکار پیشنهادی

مزایا:

- معماری تمیزتر
- جداسازی مسئولیت‌ها
- تست‌پذیری بهتر
- قابل‌اعتماد بودن Transaction Management

## **روش دوم: استفاده از Proxy خود Bean**

می‌توانیم Proxy خود Bean را تزریق کنیم و متد را از طریق آن صدا بزنیم.

مثلاً:

```
@Service
public class UserService {

    @Autowired
    private UserService self;

    public void registerUser(User user) {

        self.saveUser(user);
    }

    @Transactional
    public void saveUser(User user) {

        userRepository.save(user);
    }
}
```

در این حالت باید مطمئن باشیم `self` واقعاً Proxy مدیریت‌شده توسط Spring است.

این روش نسبت به روش اول پیچیدگی بیشتری دارد و معمولاً پیشنهاد نمی‌شود.

## **روش سوم: استفاده از AspectJ**

Spring علاوه بر Proxy-based AOP، امکان استفاده از AspectJ را نیز فراهم می‌کند.

در AspectJ، Transaction Advice می‌تواند به‌صورت Bytecode Weaving اعمال شود؛ بنابراین مشکل Self-invocation به شکل Proxy-based وجود ندارد.

اما پیکربندی و نگهداری آن پیچیده‌تر است.

# **۴. سایر محدودیت‌های مهم @Transactional**

علاوه بر Self-invocation، چند محدودیت دیگر هم وجود دارد.

### **محدودیت اول: Rollback روی Exceptionها**

به‌صورت پیش‌فرض در Spring:

| نوع Exception      | رفتار پیش‌فرض |
| ------------------ | ------------- |
| `RuntimeException` | Rollback      |
| `Error`            | Rollback      |
| Checked Exception  | Commit        |

مثال:

```
@Transactional
public void saveUser() throws IOException {

    userRepository.save(user);

    throw new IOException("File error");
}
```

در این مثال، چون `IOException` یک Checked Exception است، Spring به‌صورت پیش‌فرض Transaction را Rollback نمی‌کند.

برای تغییر رفتار:

```
@Transactional(rollbackFor = Exception.class)
public void saveUser() throws IOException {

    userRepository.save(user);

    throw new IOException("File error");
}
```

حالا Exception باعث Rollback می‌شود.

### **محدودیت دوم: متدهای Private**

در حالت استاندارد Proxy-based Spring AOP، متدهای `private` از طریق Proxy قابل Intercept نیستند.

مثال:

```
@Service
public class UserService {

    public void register() {
        save();
    }

    @Transactional
    private void save() {
        // Database operation
    }
}
```

در این مثال `@Transactional` روی متد private اعمال نمی‌شود.

بهتر است متد Transactional را در یک Bean جداگانه یا متد قابل فراخوانی از Proxy قرار دهیم.

### **محدودیت سوم: تفاوت رفتار در Propagation**

فرض کن یک متد Transactional متد دیگری را فراخوانی می‌کند.

نوع Propagation تعیین می‌کند که Transaction جدید ایجاد شود یا Transaction فعلی استفاده شود.

مهم‌ترین حالت‌ها:

| Propagation     | رفتار                                                  |
| --------------- | ------------------------------------------------------ |
| `REQUIRED`      | استفاده از Transaction موجود یا ایجاد Transaction جدید |
| `REQUIRES_NEW`  | ایجاد Transaction مستقل و تعلیق Transaction قبلی       |
| `SUPPORTS`      | استفاده از Transaction در صورت وجود                    |
| `MANDATORY`     | الزام به وجود Transaction                              |
| `NOT_SUPPORTED` | اجرای متد بدون Transaction و تعلیق Transaction موجود   |
| `NEVER`         | خطا در صورت وجود Transaction                           |

مثال:

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveLog() {

    logRepository.save(log);
}
```

نکته مهم: اگر این متد با Self-invocation فراخوانی شود، `REQUIRES_NEW` هم اعمال نخواهد شد؛ چون Proxy فرصت اجرای منطق Propagation را پیدا نمی‌کند.

### **محدودیت چهارم: Transaction به معنی Rollback همه عملیات نیست**

فرض کن داخل یک Transaction این کارها را انجام می‌دهیم:

```
@Transactional
public void processOrder() {

    orderRepository.save(order);

    emailService.sendEmail();

    paymentGateway.charge();
}
```

اگر Transaction دیتابیس Rollback شود:

- عملیات دیتابیس می‌تواند Rollback شود.
- ایمیل ارسال‌شده برنمی‌گردد.
- پرداخت خارجی لزوماً برگشت داده نمی‌شود.

چون Transaction دیتابیس به‌صورت خودکار عملیات سرویس‌های خارجی را کنترل نمی‌کند.

برای چنین سیستم‌هایی ممکن است به الگوهایی مانند **Saga Pattern** یا **Transactional Outbox Pattern** نیاز داشته باشیم.

# **۵. یک مثال مهم برای درک کامل Self-invocation**

فرض کن این کد را داریم:

```
@Service
public class OrderService {

    @Transactional
    public void createOrder() {

        orderRepository.save(new Order());

        savePayment();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void savePayment() {

        paymentRepository.save(new Payment());
    }
}
```

**سؤال: آیا&#x20;**`savePayment()`**&#x20;یک Transaction مستقل ایجاد می‌کند؟**

خیر

چون `savePayment()` از داخل همان کلاس فراخوانی شده و از Proxy عبور نمی‌کند.

بنابراین `REQUIRES_NEW` اعمال نمی‌شود و عملیات پرداخت در Transaction فعلی `createOrder()` اجرا خواهد شد.

اگر `createOrder()` با Rollback مواجه شود، عملیات ذخیره Payment نیز Rollback می‌شود.

راه‌حل: انتقال `savePayment()` به یک Bean جداگانه و فراخوانی آن از طریق Spring Proxy.

# **۶. نکات مهم برای مصاحبه**

این موارد را حتماً به خاطر بسپار:

1. Spring معمولاً `@Transactional` را با AOP Proxy پیاده‌سازی می‌کند.
2. Self-invocation باعث می‌شود فراخوانی داخلی از Proxy عبور نکند.
3. در حالت پیش‌فرض، Checked Exception باعث Rollback نمی‌شود.
4. متدهای Private در Proxy-based AOP قابل Intercept نیستند.
5. `REQUIRES_NEW` فقط وقتی کار می‌کند که فراخوانی از مسیر Transaction Interceptor عبور کند.
6. عملیات خارجی مانند ارسال ایمیل و پرداخت بانکی با Rollback دیتابیس برنمی‌گردند.

## **سؤال تمرینی مصاحبه**

کد زیر را بررسی کن:

```
@Service
public class PaymentService {

    @Transactional
    public void processPayment() {

        savePayment();

        throw new RuntimeException("Failed");
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void savePayment() {

        paymentRepository.save(new Payment());
    }
}
```

به این دو سؤال پاسخ بده:

1. آیا `savePayment()` دارای Transaction مستقل است؟
2. وقتی `RuntimeException` اتفاق می‌افتد، اطلاعات Payment در دیتابیس باقی می‌ماند یا Rollback می‌شود؟

این دقیقاً یکی از سؤال‌های مفهومی و پرتکرار مصاحبه‌های Spring است.
