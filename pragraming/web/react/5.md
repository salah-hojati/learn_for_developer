## 1. What is a "side effect"?

A **side effect** is anything a component does that isn't "compute JSX from props/state." Examples:

- Fetching data from a server
- Setting a `setTimeout` / `setInterval`
- Reading/writing `localStorage`
- Adding an event listener on `window`
- Changing `document.title`
- Subscribing to a websocket

Rendering must be **pure**: same props + state → same JSX, no side effects. Side effects go in `useEffect`.

> Rule of thumb: if you're about to do something that reaches *outside* React, it goes in `useEffect`.

## 2. The shape of `useEffect`

```jsx
import { useEffect } from "react";

useEffect(() => {
  // side effect goes here
  return () => {
    // optional cleanup: runs before the next effect and on unmount
  };
}, [dependencies]);
```

Two things are always true:

1. **The effect runs after render.** Not during. React first renders the JSX to the screen, *then* runs the effect.
2. **The dependency array controls when it runs.**

### Dependency array rules (memorize these)

| Array | When the effect runs |
|---|---|
| `[]` (empty) | Once, after the first render only |
| `[a, b]` | After first render, and again whenever `a` or `b` **changes** |
| *(omitted)* | After **every** render — almost always a bug |

"Changes" means: compared with the previous render using `Object.is`. Primitives compare by value, objects/arrays/functions by reference.

## 3. The four classic patterns

### Pattern 1: run once on mount

```jsx
useEffect(() => {
  console.log("Mounted");
}, []);
```

### Pattern 2: react to a value changing

```jsx
const [query, setQuery] = useState("");

useEffect(() => {
  console.log("Query changed:", query);
}, [query]);
```

### Pattern 3: cleanup (intervals, timers, listeners)

```jsx
useEffect(() => {
  const id = setInterval(() => {
    console.log("tick");
  }, 1000);

  return () => clearInterval(id);
}, []);
```

Without `clearInterval`, the interval keeps running after the component disappears → memory leak. This is what the cleanup function is for. **Any effect that "starts something" must return a function that "stops it."**

### Pattern 4: fetch data

```jsx
import { useEffect, useState } from "react";

function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;

    async function load() {
      try {
        setLoading(true);
        setError(null);
        const res = await fetch("https://jsonplaceholder.typicode.com/users");
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        if (!cancelled) setUsers(data);
      } catch (err) {
        if (!cancelled) setError(err.message);
      } finally {
        if (!cancelled) setLoading(false);
      }
    }

    load();

    return () => {
      cancelled = true;
    };
  }, []);

  if (loading) return <p>Loading…</p>;
  if (error) return <p style={{ color: "red" }}>Error: {error}</p>;

  return (
    <ul>
      {users.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}
```

**Why `let cancelled`?** If the user navigates away (or the deps change) while the fetch is in-flight, the cleanup runs and sets `cancelled = true`. The fetch still resolves, but we skip `setState` — avoiding a "state update on an unmounted component" warning and stale data overwriting fresh data.

**Why can't the effect callback be `async`?** Because it must return either nothing or a cleanup function — an `async` function returns a **promise**. So we define an inner async function `load()` and call it.

**Why the three states (`users`, `loading`, `error`)?** Because a fetch has three phases: *loading*, *success*, *failure*. Always model all three. A fetch that only sets `data` on success will show an empty list forever if the request fails.

## 4. The infinite loop — the #1 `useEffect` bug

```jsx
useEffect(() => {
  setUsers([...users, newUser]);  // ❌
}, [users]);                       // deps: users
```

`users` changes → effect runs → sets `users` → `users` changed → effect runs → …**infinite loop**.

Two fixes depending on intent:

- **You don't want it to react to `users`:** remove `users` from deps (usually correct).
- **You genuinely want to append once:** move the append into an event handler (e.g. `handleAddUser`), *not* an effect. Effects are for **synchronizing with the outside world**, not for deriving state from state.

> **Big principle:** if you're computing one piece of state from another, you usually **don't need `useEffect` at all** — just compute it during render:
>
> ```jsx
> const [users, setUsers] = useState(allUsers);
> const filtered = users.filter(u => u.name.includes(search));  // no effect needed
> ```
>
> Lesson 3's exercise already did this. That's the right pattern. Only reach for `useEffect` when you actually need to *interact with the outside world*.

## 5. Other classic pitfalls

1. **Missing deps** → stale values.
   ```jsx
   useEffect(() => {
     document.title = `You typed: ${query}`;  // query is used
   }, []);                                     // ❌ query missing
   ```
   ESLint will flag this. Trust the linter.

2. **Object/array/function in deps** → runs every render, because they're new references each time.
   ```jsx
   useEffect(() => { ... }, [{}]);          // ❌ new object each render
   useEffect(() => { ... }, [fetchData]);   // ❌ if fetchData is defined inside the component, new each render
   ```
   Fix: move the function inside the effect, or wrap with `useCallback` (later lesson).

3. **Setting state unconditionally in a fetch effect with a dependency on that state** → loop again. Same rule as §4.

4. **Forgetting cleanup for `setInterval` / `addEventListener`** → leak. Symmetry rule: every `+` in the effect needs a `-` in the cleanup.

5. **StrictMode double-invoke.** In dev, React 18 runs effects **twice** (mount → unmount → mount) to surface bugs. Your effect must be idempotent, and your cleanup must be real. If you see double console logs in dev — that's expected, not a bug.

## 6. When you should NOT use `useEffect`

Because beginners overuse it, here's the list:

- **Deriving values from props/state** → just compute during render.
- **Resetting state when a prop changes** → use `key` on the component, or compute directly.
- **Handling user events** → put it in the event handler (`onClick`, `onSubmit`).
- **"Run once after mount" for setting up a variable** → not a side effect; just initialize with `useState(initialValue)`.

Use `useEffect` only for *synchronizing with something outside React*: network, DOM APIs, browser APIs, timers, third-party libraries.
