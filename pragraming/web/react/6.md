## 1. What we're building

A **tasks app**:

- Lets you **delete** a task

## 2. The architecture question: where does state live?

> **Rule:** state lives in the **lowest common ancestor** of all components that need it.

Who needs the task list?

- `App` (renders the list and the counts)
- `TaskItem` (each row needs its task + a way to delete/toggle it)
- `TaskForm` (needs to add to the list)

The common ancestor is `App`. So `App` owns `tasks`. Children receive data and functions as **props**.

```
App  ←── owns state
├── TaskForm     (prop: onAdd)
├── FilterBar    (props: filter, onChange, counts)
└── TaskItem[]   (props: task, onToggle, onDelete)
```

This is the pattern called **"data down, actions up."** State flows down as props. Events flow up as callbacks.

Children **never** mutate the parent's state directly. They call the function the parent gave them. That function is defined in `App`, so it has access to `setTasks`.

```jsx
// in App
function handleDelete(id) { setTasks(prev => prev.filter(t => t.id !== id)); }

// passed down
<TaskItem task={t} onDelete={handleDelete} />

// in TaskItem
<button onClick={() => onDelete(task.id)}>Delete</button>
```

## 3. The immutable-update cheat sheet (memorize this)

Almost every bug in a task app is a mutation bug. Print this:

| Goal | Code |
|---|---|
| **Add** an item | `prev => [...prev, newItem]` |
| **Delete** an item | `prev => prev.filter(x => x.id !== id)` |
| **Update** one item | `prev => prev.map(x => x.id === id ? { ...x, done: !x.done } : x)` |
| **Sort** | `prev => [...prev].sort((a, b) => ...)` |
| **Reverse** | `prev => [...prev].reverse()` |

Notice the two verbs that **never** appear: `push` and `splice`. They mutate. React will not re-render if you mutate the existing array — the reference hasn't changed.

And for **nested** objects (like updating just `done`), you must spread:

```jsx
{ ...task, done: !task.done }  // ✅ a new task object with flipped done
{ done: !task.done }           // ❌ loses title and id
task.done = !task.done         // ❌ mutation, no re-render
```

Also: inside the updater, always use `prev =>`, not `tasks` directly — `prev` is guaranteed to be the *latest* value, `tasks` might be stale in a rapid sequence of updates.

## 4. What happens after the fetch?

You fetch 5 tasks. Then the user adds a new one. Two schools of thought:

**Refetch after every change.** Send the change to the server, then re-run `GET /tasks`. Correct for a real API. Slow. More code.

**Update local state only.** Fetch once, then `setTasks` for all changes. Fast. Simple. **This is what we'll do for this exercise** — because the exercise is about state management, not API writing.

Real apps use a hybrid: `POST` to server, then update local state from the response (or optimistically, then reconcile). We cover that when you're ready for React Query. For now, local state after fetch is the right call.

One consequence to notice: if you refresh the page, your added tasks disappear. That's *correct behavior* for this exercise — we're not persisting yet. `localStorage` is a fun bonus (see §7).

            onClick={() => setFilter(f)}

### `TaskForm.jsx`

```jsx
import { useState } from "react";

function TaskForm({ onAdd }) {
  const [title, setTitle] = useState("");

  function handleSubmit(e) {
    e.preventDefault();
    const trimmed = title.trim();
    if (!trimmed) return;
    onAdd(trimmed);
    setTitle("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="What needs doing?"
      />
      <button type="submit">Add</button>
    </form>
  );
}

export default TaskForm;
```

Note: `TaskForm` does **not** own the task list. It owns only its own input text. When submitted, it calls `onAdd(title)` — the parent handles the rest. That's the pattern.

### `TaskItem.jsx`

```jsx
function TaskItem({ task, onToggle, onDelete }) {
  return (
    <li>
      <input
        type="checkbox"
        checked={task.done}
        onChange={() => onToggle(task.id)}
      />
      <span style={{ textDecoration: task.done ? "line-through" : "none" }}>
        {task.title}
      </span>
      <button onClick={() => onDelete(task.id)}>✕</button>
    </li>
  );
}

export default TaskItem;
```

Note the two `onClick`/`onChange` handlers pass `task.id` — the parent doesn't need to know which task it is, the child knows.

## 6. Common pitfalls (you will hit at least three)

1. **`prev.map` returns the item, not the JSX.** If your toggle button suddenly renders `[object Object]` you've got a JSX/object mix-up.
2. **Missing `...t` in the toggle updater** — every other field vanishes from that row.
3. **`handleAdd` called with the whole event instead of the string** — because you wrote `onSubmit={onAdd}` somewhere by mistake. Pass the value, not the event.
4. **Filter counts frozen** — because you put them in `useState` and never updated them, or in a `useEffect`. Just compute them during render. The comment says so.
5. **Filter buttons with no visible change** — because `setFilter(f)` was written as `setFilter(f())` (calling f) or `setFilter` alone (returning the setter).
6. **`key` on the `<ul>`** instead of the `<TaskItem>` — the key belongs on the outermost element *inside* `.map()`.
7. **Refreshing the page and the list is empty** — you commented out the fetch by accident. It happens.
