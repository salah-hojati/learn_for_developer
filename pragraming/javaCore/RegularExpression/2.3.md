# اشکالات الگوی `^.+@.+\..+$`

این الگو **فقط یک ظاهر ساده** را چک می‌کند و خیلی چیزهای نامعتبر را می‌پذیرد. مهم‌ترین اشکالات:

## ۱. چند `@` را قبول می‌کند

`.+` حریص (greedy) است و محدودیتی روی `@` ندارد. پس این‌ها **match** می‌شوند:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
a@b@c.d      ✅ (ولی نامعتبر است)
user@@x.com  ✅ (ولی نامعتبر است)
@a.b         ✅ (local part خالی)
a@.b         ✅ (دامنه با نقطه شروع می‌شود)
```

</div>


دلیل: `^.+` می‌تواند تا آخرین `@` را ببلعد و بعد backtrack کند.

## ۲. فاصله و کاراکترهای ممنوع را قبول می‌کند

`"."` در regex هر کاراکتری جز newline است — از جمله **فاصله**:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
"a b@c d.e f"   ✅ match می‌شود (کاملاً نامعتبر)
"a\tb@c.d"      ✅
"a\"b@c.d"      ✅
```

</div>


کاراکترهای مجاز در local part (طبق RFC 5322) فقط این‌ها هستند:
`a-z A-Z 0-9 ! # $ % & ' * + - / = ? ^ _ ` { | } ~ .`
و کاراکترهایی مثل `"`, `(`, `)`, `,`, `:`, `;`, `<`, `>`, `@`, `[`, `\`, `]`, فاصله و کنترلی‌ها **ممنوع** هستند.

## ۳. نقطه‌های پشت‌سرهم و ابتدا/انتها را قبول می‌کند

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
"a..b@c.d"     ✅ (دو نقطه پشت‌سرهم در local part)
".a@c.d"       ✅ (local با نقطه شروع)
"a.@c.d"       ✅ (local با نقطه تمام)
"a@b..c"       ✅ (دامنه با .. )
"a@b.c."       ✅ (دامنه با نقطه تمام)
```

</div>


## ۴. TLD را بی‌قید می‌پذیرد

`\..+$` هر چیزی بعد از آخرین نقطه را قبول می‌کند:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```
"a@b.c"        ✅ (TLD یک‌حرفی)
"a@b.1"        ✅ (TLD عددی)
"a@b.-x"       ✅
"a@b.c d"      ✅ (TLD با فاصله!)
```

</div>


TLD معتبر: حداقل دو حرف alphabetic.

## ۵. محدودیت طول ندارد

RFC 5321 می‌گوید local part حداکثر ۶۴ و کل آدرس حداکثر ۲۵۴ کاراکتر است. `.+` این‌ها را چک نمی‌کند.

## ۶. `$` در جاوا فقط «انتهای رشته» نیست

در جاوا `$` قبل از newline پایانی هم match می‌شود. اگر از `find()` استفاده کنید:

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```java
Pattern.compile("^.+@.+\\..+$").matcher("a@b.c\nX").find()  // true!
```

</div>


اگر می‌خواهید مطمئن شوید کل رشته مصرف شده، از `\z` استفاده کنید یا از `matches()` که خودش کل رشته را anchor می‌کند.

## ۷. `String` به‌جای `Pattern`

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```java
String email = "^.+@.+\\..+$";   // ❌ فقط رشته
```

</div>


اگر در حلقه استفاده شود، هر بار دوباره کامپایل می‌شود. بهتر است `static final Pattern` باشد.

---

## نسخه‌ی بهتر (هنوز کامل نیست، ولی خیلی امن‌تر)

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```java
private static final Pattern EMAIL = Pattern.compile(
    "^[A-Za-z0-9!#$%&'*+/=?^_`{|}~-]+" +
    "(?:\\.[A-Za-z0-9!#$%&'*+/=?^_`{|}~-]+)*" +   // dot-atom
    "@" +
    "(?:[A-Za-z0-9](?:[A-Za-z0-9-]{0,61}[A-Za-z0-9])?\\.)+" + // labels
    "[A-Za-z]{2,63}\\z"                            // TLD
);
```

</div>


این نسخه:
- فقط یک `@` می‌پذیرد
- نقطه‌ی پشت‌سرهم / ابتدا / انتها را رد می‌کند
- هر label دامنه را ۱ تا ۶۳ کاراکتر و بدون `-` در ابتدا/انتها چک می‌کند
- TLD را حداقل ۲ حرف alphabetic می‌خواهد
- با `\z` مطمئن می‌شود کل رشته مصرف شده

<div dir="ltr" style="text-align: left; font-family: 'B Nazanin', Tahoma, sans-serif;">

```java
public static boolean isValidEmail(String s) {
    return s != null && s.length() <= 254 && EMAIL.matcher(s).matches();
}
```

</div>


## نکته‌ی مهم

**هیچ regex‌ای نمی‌تواند ایمیل را ۱۰۰٪ معتبرسنجی کند** — RFC 5322 کامل خیلی پیچیده است (quoted strings، comments، IP literals، …). رویکرد رایج و توصیه‌شده:

1. یک regex **محافظه‌کارانه** مثل بالا برای رد کردن ورودی‌های بدیهی
2. **تأیید واقعی** با ارسال ایمیل (verification link)
3. (اختیاری) DNS/MX lookup روی دامنه

اگر فقط می‌خواهید جلوی `"a@b"` و `"asdf"` را بگیرید، همان نسخه‌ی بالا کافی است.
