# Kafka + Spring Boot: Q&A Study Guide

Organized by topic, from fundamentals to advanced. Each answer is short enough to memorize and detailed enough to actually use.

---

## 🟢 Section 1 — Kafka Fundamentals

**Q1. What is Kafka, in one sentence?**
A distributed, partitioned, replicated **commit log** where producers append records and consumers read them at their own pace by tracking an offset.

**Q2. What is a topic, a partition, and an offset?**
- **Topic** — a named logical stream (e.g., `order-events`).
- **Partition** — an ordered, append-only slice of a topic. Ordering is guaranteed **only within a partition**.
- **Offset** — a monotonically increasing ID of a record within a partition. Consumers commit offsets to remember where they are.

**Q3. Why does Kafka scale horizontally?**
Because a topic is split into partitions, and each partition can live on a different broker. Producers and consumers work in parallel per partition.

**Q4. What determines which partition a message goes to?**
The **message key**. `hash(key) % numPartitions`. Same key → same partition → guaranteed order. No key → round-robin/sticky.

**Q5. What is a consumer group?**
A set of consumers sharing a `group.id`. Kafka assigns each partition to **exactly one** consumer in the group, so work is split. Multiple groups each get the full stream independently (pub/sub vs queue semantics in one).

**Q6. What happens when a consumer dies?**
The group **rebalances**: partitions owned by the dead consumer are reassigned to survivors. This is why long processing can trigger false rebalances (tune `max.poll.interval.ms`).

**Q7. What's the difference between `auto.offset.reset=earliest` and `latest`?**
Only applies when a group has **no committed offset**: `earliest` reads from the beginning, `latest` reads only new messages. It has no effect once offsets exist.

**Q8. What is KRaft, and why does it matter?**
Kafka's built-in consensus mode that replaces ZooKeeper (default since 3.3+). Fewer moving parts, faster controller failover, simpler dev setup — that's why the standalone example uses it.

**Q9. What does replication factor (RF) and `min.insync.replicas` (minISR) mean?**
- **RF** — how many copies of each partition exist.
- **minISR** — how many copies must acknowledge a write for `acks=all` to succeed.
  Rule of thumb: `RF=3`, `minISR=2` → survives one broker loss without data loss.

**Q10. What's the difference between `acks=0`, `1`, `all`?**
- `0` — fire and forget (can lose data).
- `1` — leader ack only (loss if leader dies before replication).
- `all` (`-1`) — leader + all ISR acks (durable; use with idempotence for EOS).

## 🟡 Section 2 — Spring Boot Integration

**Q11. What does `spring-kafka` auto-configure for you?**
`KafkaTemplate`, `ProducerFactory`, `ConsumerFactory`, `KafkaAdmin`, the listener container factory, and the `@EnableKafka` machinery — all from `application.properties`.

**Q12. What's the minimum config to send/receive a String?**
```properties
spring.kafka.bootstrap-servers=localhost:9092
spring.kafka.consumer.group-id=my-group
spring.kafka.consumer.auto-offset-reset=earliest
```
That's it — `KafkaTemplate<String,String>` and `@KafkaListener(topics="my-topic")` work out of the box.

**Q13. How does `@KafkaListener` know which topics to poll?**
The annotation's `topics`/`topicPattern`/`topicPartitions` attribute is read by the `KafkaListenerEndpointRegistry` at startup, which creates one `MessageListenerContainer` per listener.

**Q14. How do you send a message with a key?**
```java
kafkaTemplate.send("orders-topic", order.getId(), order);
```
The 2nd arg is the key — critical for per-order ordering.

**Q15. How do you auto-create topics on startup?**
Declare a `NewTopic` bean. `KafkaAdmin` (auto-configured) calls the AdminClient to create it if missing:
```java
@Bean NewTopic orders() {
  return TopicBuilder.name("orders-topic").partitions(3).replicas(1).build();
}
```

**Q16. Why does JSON deserialization fail with "not in trusted packages"?**
`JsonDeserializer` blocks arbitrary class types by default (a security guard against gadget attacks). Fix:
```properties
spring.kafka.consumer.properties.spring.json.trusted.packages=com.example.dto
```

**Q17. How would you register two different listeners with different configs?**
Define two `ConcurrentKafkaListenerContainerFactory` beans with distinct names and reference them via `@KafkaListener(containerFactory="...")`.

## 🟠 Section 3 — Error Handling & Retries

**Q18. What happens if a `@KafkaListener` throws an exception?**
The configured `ErrorHandler` (default `DefaultErrorHandler` in modern Spring Kafka) applies a `BackOff` and retries by re-invoking the listener with the **same record**, without committing the offset. After retries are exhausted → `recoverer` (typically DLT) or the record is skipped (older `SeekToCurrentErrorHandler` behavior).

**Q19. What is a Dead Letter Topic (DLT)?**
A topic where "poison pill" messages go after retries fail — so a malformed record doesn't block the whole partition forever.

**Q20. How do you configure retries + DLT?**
```java
@Bean
ErrorHandler handler(KafkaTemplate<Object,Object> tpl) {
    var recoverer = new DeadLetterPublishingRecoverer(tpl,
        (r, ex) -> new TopicPartition(r.topic() + ".DLT", -1));
    return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
}
```
Spring Boot applies this bean to every listener container automatically.

**Q21. Why can a single bad message "block" a consumer?**
Kafka guarantees **order within a partition**. If you don't ack a bad record, the same partition's next records can't advance past it. DLT + ack-after-recover unblocks the partition.

**Q22. What's the difference between `RetryTopic` and `DefaultErrorHandler` retries?**
- `DefaultErrorHandler` retries **in-memory** — blocks the partition during backoff.
- Non-blocking retries (`@RetryableTopic`) publish the record to intermediate retry topics with delays → the partition keeps flowing.

## 🔴 Section 4 — Delivery Guarantees & Transactions

**Q23. List the three delivery guarantees.**
- **At-most-once** — commit offset before processing → possible message loss.
- **At-least-once** — commit offset after processing → possible duplicates.
- **Exactly-once** — processing + offset commit + downstream produce happen atomically → no loss, no dupes.

**Q24. What two mechanisms enable exactly-once in Kafka?**
1. **Idempotent producer** (`enable.idempotence=true`) — dedupes retries within a producer session using sequence numbers.
2. **Transactions** — atomically write to multiple topics **and** commit consumer offsets via `sendOffsetsToTransaction`.

**Q25. Why is `isolation.level=read_committed` mandatory for consumers reading transactional data?**
Otherwise they'd see **aborted** records (from rolled-back transactions). `read_committed` filters them out until the commit marker arrives.

**Q26. What is the difference between `auto-commit` and manual ack?**
- `auto-commit` — the consumer commits offsets periodically **on a timer**, regardless of whether your listener succeeded. Risk of loss.
- **Manual ack** — you call `ack.acknowledge()` after success. Risk of duplicates, not loss.

**Q27. When should you avoid transactions?**
When latency matters more than atomicity, or when the downstream system can't participate in the Kafka transaction (e.g., a REST API). Use **idempotency keys** instead.

**Q28. What's the outbox pattern, and why does it pair with Kafka?**
Store the "intent to publish" in the **same DB transaction** as the business write. A separate poller publishes from the outbox to Kafka. This gives exactly-once-style semantics without needing Kafka transactions to span the database.

## 🔵 Section 5 — Avro & Schema Registry

**Q29. Why use Avro over JSON?**
- **Compact binary** encoding (schema is not repeated per message).
- **Schema enforcement** — incompatible writes are rejected at produce time.
- **Compatibility rules** are explicit and enforceable by Schema Registry.

**Q30. What are the compatibility modes?**
- **BACKWARD** — new schema can read old data (add fields with defaults). Default.
- **FORWARD** — old schema can read new data (remove fields).
- **FULL** — both.
- **NONE** — anything goes (don't).

**Q31. What is the Confluent Schema Registry?**
A separate service that stores Avro/JSON/Protobuf schemas by ID. Producers send the **schema ID + binary payload**; consumers fetch the schema by ID and deserialize. `KafkaAvroSerializer`/`KafkaAvroDeserializer` handle this transparently.

**Q32. How does the Avro Maven plugin fit in?**
It reads `.avsc` files at build time and generates Java classes (e.g., `OrderEvent`) into `target/generated-sources/avro`. You write code against the generated types.

## 🟣 Section 6 — Testing

**Q33. What is `@EmbeddedKafka`?**
A Spring test annotation that boots an **in-JVM Kafka broker** for the test's duration. No Docker, no external processes. Fast, isolated.

**Q34. What broker properties are required to test transactions with embedded Kafka?**
```properties
transaction.state.log.replication.factor=1
transaction.state.log.min.isr=1
offsets.topic.replication.factor=1
```
Otherwise the embedded single-node broker rejects transactional writes.

**Q35. What's the difference between `@EmbeddedKafka` and Testcontainers?**
- **`@EmbeddedKafka`** — in-process, fast, but **no Schema Registry, no ZooKeeper/KRaft controller, no real network** — great for producer/consumer logic.
- **Testcontainers** — real Docker Kafka + Schema Registry — slower but **production-like**. Use it when Avro or AdminClient features are involved.

**Q36. How do you test an async consumer?**
Use `Awaitility` or a `CountDownLatch`:
```java
kafkaTemplate.send("test-topic", "hello");
await().atMost(Duration.ofSeconds(5))
     .until(() -> latch.await(100, MILLISECONDS));
```

## ⚫ Section 7 — Operations & Monitoring

**Q37. What are the three most important consumer metrics?**
- **`records-lag`** — how far behind the consumer is.
- **`fetch-latency`** — broker read time.
- **`commit-latency`** — offset commit latency.

**Q38. What does Micrometer add over JMX?**
A vendor-neutral facade. Kafka's `KafkaClientMetrics` (a `MetricName` → tag mapping) is bridged into Micrometer, so you get Prometheus/Grafana/OTLP exporters without code changes.

**Q39. How do you add custom tags to producer/consumer metrics?**
```java
factory.addListener(new MicrometerProducerListener<>(registry,
    List.of(new ImmutableTag("app", "order-service"))));
```

**Q40. How does tracing propagate through Kafka?**
Micrometer Observation injects `traceparent`/`tracestate` into **Kafka record headers** — the consumer side extracts them and continues the span. Same request, one trace.

## 🎯 Section 8 — Scenario Questions (Interview-style)

**Q41. "Our consumer is falling behind. What do you check first?"**
1. **Lag per partition** — is it one partition (skewed key) or all (throughput)?
2. **Consumer parallelism** — is `concurrency` >= number of partitions?
3. **Downstream latency** — DB/HTTP calls in the listener?
4. **Rebalances** — check logs for `Member ... has left` — long processing?
5. If one key is hot → **re-key** (e.g., add salt) or increase partitions.

**Q42. "A message was processed twice. How do you fix it?"**
The consumer is **at-least-once**. Fixes, in order of preference:
1. **Idempotency guard** — dedupe on a business key.
2. **Transactional consume-transform-produce** if downstream is Kafka.
3. **Outbox pattern** if downstream is a database.
4. **Enable idempotence on the producer** (already default) — dedupes retries only, not duplicates from redelivery.

**Q43. "Producer throws `TimeoutException: Expiring 5 record(s)`."**
Broker didn't ack within `delivery.timeout.ms`. Causes:
- Broker down or slow → check broker health.
- `minISR` unmet (only 1 replica alive with `minISR=2`) → restore replicas.
- Network partition between client and broker.
  Fix is **not** to bump the timeout blindly — find the root cause first.

**Q44. "Topic deleted but consumer keeps redelivering old messages."**
You consumed from a **different topic name** or from a consumer group that still has offsets. Check `spring.kafka.consumer.group-id` and `kafka-consumer-groups --describe`.

**Q45. "We want to change the `OrderEvent` schema without breaking consumers."**
Use Avro + Schema Registry in **BACKWARD** compatibility:
- **Add new fields with defaults** → old consumers still work.
- **Never remove or rename required fields** without a major version topic.
- If a breaking change is unavoidable → **new topic** (`order-events.v2`) and dual-write during migration.

**Q46. "Producer sends messages out of order. Why?"**
- **No key** → round-robin across partitions → order lost.
- **Key present** but partition count > 1 and you didn't set `max.in.flight.requests.per.connection=1` on old clients (with idempotence, this is now safe up to 5).
  Fix: always key by an entity ID that needs ordering.

## 🧠 Cheat Sheet (memorize these)

| Concept | One-liner |
|---|---|
| Ordering | Guaranteed per partition only |
| Key | Determines partition |
| Consumer group | Splits partitions among members |
| `earliest`/`latest` | Only when no committed offset |
| `acks=all` + idempotence | Durable + deduped writes |
| Transaction | Atomic offsets + multi-topic writes |
| `read_committed` | Hide aborted txn records |
| DLT | Poison pill quarantine |
| `@EmbeddedKafka` | Fast in-JVM tests, no Docker |
| Avro + Registry | Schema contract enforcement |
| Micrometer | Vendor-neutral metrics |
| Outbox | Cross-resource atomicity without Kafka txns |
