برای پیاده‌سازی **امنیت سطح ردیف (Row-Level Security)** مستقیماً در کوئری‌های **Spring Data JPA** به‌جای استفاده از `@PostFilter`، بهترین و کارآمدترین روش این است که شرط مجوزدهی را **در سطح SQL / JPQL** اعمال کنید تا دیتابیس فقط رکوردهای مجاز را برگرداند.

با این کار:

* **کارایی بالاتر** دارید (ردیف‌های غیرمجاز اصلاً به حافظه برنامه منتقل نمی‌شوند).
* **`Page` و `Pageable` درست کار می‌کنند** (تعداد کل صفحات و آیتم‌ها دقیق است).
* **امنیت همگام با منطق واکشی داده** باقی می‌ماند.

در ادامه، سه رویکرد رایج و تمیز را از ساده تا قابل‌استفاده مجدد مرور می‌کنیم.

### ۱. ارجاع به `SecurityContext` در JPQL با SpEL (ساده و مستقیم)

در Spring Data JPA می‌توانید مستقیماً در عبارت `@Query` به `authentication` (یا `principal`) در `SecurityContext` دسترسی داشته باشید:

```java
public interface TaskRepository extends JpaRepository<Task, Long> {

    @Query("""
        SELECT t FROM Task t
        WHERE t.assignee = :#{authentication.name}
           OR t.isPublic = true
           OR :#{hasRole('MANAGER')} = true
        """)
    List<Task> findAllVisibleTasks();

    @Query("""
        SELECT t FROM Task t
        WHERE t.assignee = :#{authentication.name}
           OR t.isPublic = true
           OR :#{hasRole('MANAGER')} = true
        """)
    Page<Task> findAllVisibleTasks(Pageable pageable);
}

```

> **نکته:** در صورت استفاده از Spring Security 6 و جدیدتر، مطمئن شوید وابستگی `spring-security-data` در پروژه وجود داشته باشد تا توابع امنیتی SpEL در کوئری‌های Spring Data در دسترس باشند.

### ۲. پاس دادن نام کاربر یا شناسه از لایه Service (قابل تست‌تر و شفاف‌تر)

اگر نمی‌خواهید کوئری‌های Repository وابسته به `SecurityContext` باشند یا می‌خواهید تست واحد (Unit Test) ساده و صریحی بنویسید، کاربر فعلی را از لایه Service استخراج کرده و به متد Repository پاس دهید:

```java
@Repository
public interface TaskRepository extends JpaRepository<Task, Long> {

    @Query("""
        SELECT t FROM Task t
        WHERE (:isManager = true OR t.assignee = :username OR t.isPublic = true)
        """)
    Page<Task> findVisibleForUser(
            @Param("username") String username,
            @Param("isManager") boolean isManager,
            Pageable pageable
    );
}

```

```java
@Service
@RequiredArgsConstructor
public class TaskService {

    private final TaskRepository taskRepository;

    public Page<Task> getTasks(Authentication auth, Pageable pageable) {
        boolean isManager = auth.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals("ROLE_MANAGER"));
        return taskRepository.findVisibleForUser(auth.getName(), isManager, pageable);
    }
}

```

**مزیت این روش:** وابستگی مستقیم به `SecurityContextHolder` در لایه داده از بین می‌رود و می‌توانید `findVisibleForUser` را بدون نیاز به ساخت `SecurityContext` تست کنید.

### ۳. استفاده از `Specification` برای ترکیب شرط‌های امنیتی در چند کوئری

وقتی چندین نوع جستجو یا فیلتر (مثلاً فیلتر وضعیت، تاریخ، یا جستجوی متنی) دارید و می‌خواهید در **همه آن‌ها** شرط امنیت سطح ردیف یکسان باشد، `JpaSpecificationExecutor` بهترین گزینه است:

```java
public class TaskSpecifications {

    public static Specification<Task> visibleTo(Authentication auth) {
        return (root, query, cb) -> {
            boolean isManager = auth.getAuthorities().stream()
                    .anyMatch(a -> a.getAuthority().equals("ROLE_MANAGER"));

            if (isManager) {
                return cb.conjunction(); // بدون محدودیت ردیف
            }

            return cb.or(
                    cb.equal(root.get("assignee"), auth.getName()),
                    cb.isTrue(root.get("isPublic"))
            );
        };
    }

    public static Specification<Task> hasStatus(TaskStatus status) {
        return (root, query, cb) ->
                status == null ? cb.conjunction() : cb.equal(root.get("status"), status);
    }
}

```

در لایه Service به‌راحتی ترکیب می‌شوند:

```java
Specification<Task> spec = Specification
        .where(TaskSpecifications.visibleTo(auth))
        .and(TaskSpecifications.hasStatus(status));

Page<Task> result = taskRepository.findAll(spec, pageable);

```

### ۴. چک‌لیست انتخاب روش و نکات مهم

| سناریو | پیشنهاد مناسب |
| --- | --- |
| کوئری ثابت و محدود با `Pageable` | `@Query` با SpEL یا پاس دادن `username` و نقش از Service |
| جستجوهای پویا با فیلترهای متعدد در چند Endpoint | `Specification` قابل ترکیب (`visibleTo` + سایر فیلترها) |
| جلوگیری از فراموش شدن شرط امنیتی در متدهای جدید | لایه Service/Repository اختصاصی برای دسترسی‌های امن یا View/Policy در دیتابیس |

* **عملیات تکی (`findById`):** برای واکشی یک رکورد خاص بر اساس `id`، ترکیب `findById` با `@PostAuthorize` یا کوئریِ همراه با شرط مالکیت، جلوی نشت اطلاعات (`404` در برابر `403`) را بسته به سیاست امنیتی سیستم شما کنترل می‌کند.
* **ایندکس دیتابیس:** ستون‌هایی که در شرط امنیت ردیف می‌آیند (مانند `owner_id`، `assignee` یا `tenant_id`) را حتماً ایندکس کنید تا کوئری‌ها در جداول بزرگ کند نشوند.
