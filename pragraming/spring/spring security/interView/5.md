در **Apache Kafka**، تفاوت **at-least-once** و **exactly-once** در نحوه برخورد با خطاها، ارسال مجدد (Retry) و ثبت `offset`ها هنگام انتقال یا پردازش پیام‌هاست:

* **`at-least-once` (حداقل یک‌بار):** هیچ پیامی از دست نمی‌رود، اما در صورت بروز خطای شبکه یا قطع ارتباط پس از commit شدن داده در Broker یا پیش از ثبت `offset` توسط Consumer، ممکن است یک پیام **چند بار** ارسال یا پردازش شود. برای جلوگیری از اثر تکراری، Consumer یا سیستم مقصد باید **idempotent** باشد.
* **`exactly-once` (دقیقاً یک‌بار / EOS):** تضمین می‌کند که پیام‌ها در جریان **خواندن → پردازش → نوشتن و ثبت offset** به‌صورت اتمی اعمال شوند؛ یعنی یا کل عملیات با هم `commit` می‌شود و در دسترس قرار می‌گیرد، یا در صورت خطا `abort` می‌شود و اثر ناقصی باقی نمی‌گذارد (در مرز سیستم‌های خارجی مثل دیتابیس نیز برای تکمیل زنجیره، idempotency یا Outbox لازم است).

---

### ۱. تفاوت کلیدی در یک نگاه

| معیار | `at-least-once` | `exactly-once` |
| --- | --- | --- |
| **احتمال تکرار پیام** | بله (در زمان retry یا crash پس از پردازش) | خیر، در مرزهای تراکنشی Kafka |
| **احتمال از دست رفتن پیام** | خیر | خیر |
| **سربار و پیچیدگی** | کم‌تر، سریع‌تر | بیش‌تر (هماهنگی تراکنش‌ها، `Transaction Coordinator`، تاخیر اندک) |
| **نیاز به Idempotency در مقصد** | ضروری | در ارتباط با سیستم‌های خارجی (مثل SQL/HTTP) همچنان مهم است |

---

### ۲. چگونه `exactly-once` را در Kafka پیاده‌سازی کنیم؟

پیاده‌سازی واقعی `exactly-once` در Kafka بر پایه دو ستون اصلی است: **Idempotent Producer** (جلوگیری از تکرار هنگام نوشتن در یک پارتیشن یا ارسال مجدد) و **Transactional API** (اتمی کردن نوشتن روی چند Topic/Partition همراه با commit کردن offsetهای Consumer در الگوی *Consume-Transform-Produce*).

#### الف) تنظیمات Producer برای Idempotence و Transactions

در کافکاهای مدرن (`3.0+`)، `enable.idempotence=true` به‌صورت پیش‌فرض فعال است، اما برای تراکنش حتماً باید یک `transactional.id` یکتا و پایدار تعیین کنید:

```properties
# تنظیمات Producer
bootstrap.servers=localhost:9092
enable.idempotence=true
acks=all
retries=2147483647
transactional.id=order-processor-tx-01

```

* **`Producer ID (PID)` + `Sequence Number`:** Broker پیام‌های تکراری ناشی از retry را در سطح پارتیشن تشخیص می‌دهد و رد می‌کند.
* **`transactional.id`:** اگر instance ای از کار بیفتد و instance جدید با همان ID بالا بیاید، Broker تراکنش‌های معلق قبلی را `abort` می‌کند (*Zombie Fencing*).

#### ب) الگوی Consume-Transform-Produce با تراکنش (Java / Kafka Clients)

```java
producer.initTransactions();

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) continue;

    try {
        producer.beginTransaction();

        for (ConsumerRecord<String, String> record : records) {
            String processedValue = transform(record.value());
            producer.send(new ProducerRecord<>("orders-enriched", record.key(), processedValue));
        }

        // ثبت offsetهای مصرف‌شده درون همان تراکنش
        Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
        for (TopicPartition tp : records.partitions()) {
            List<ConsumerRecord<String, String>> partitionRecords = records.records(tp);
            long lastOffset = partitionRecords.get(partitionRecords.size() - 1).offset();
            offsets.put(tp, new OffsetAndMetadata(lastOffset + 1));
        }

        ConsumerGroupMetadata groupMetadata = consumer.groupMetadata();
        producer.sendOffsetsToTransaction(offsets, groupMetadata);

        producer.commitTransaction();
    } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException e) {
        producer.close();
        throw e;
    } catch (KafkaException e) {
        producer.abortTransaction();
    }
}

```

#### ج) تنظیم Consumer با `read_committed`

اگر Consumer روی حالت پیش‌فرض (`read_uncommitted`) باشد، پیام‌های تراکنش‌های هنوز-commit-نشده یا `aborted` را نیز می‌بیند. برای تکمیل زنجیره `exactly-once`:

```properties
# تنظیمات Consumer
group.id=order-processor-group
enable.auto.commit=false
isolation.level=read_committed

```

### ۳. نکات عملی در تولید (Production)

* **جریان‌های تک‌طرفه (فقط Produce یا فقط Consume):** اگر فقط داده تولید می‌کنید و مصرف‌کننده‌ای در کار نیست، `enable.idempotence=true` به تنهایی تکرار ناشی از retry را می‌گیرد و نیازی به تراکنش سنگین ندارید.
* **نوشتن در دیتابیس بیرونی:** تراکنش Kafka اتمی بودن میان Topicها و offsetهای Kafka را تضمین می‌کند؛ اگر در میانه کار به دیتابیس رابطه‌ای می‌نویسید، از **Transactional Outbox** یا کلید یکتای idempotency در دیتابیس استفاده کنید.
* **تنظیم `transaction.timeout.ms`:** این مقدار نباید از حداکثر زمان پردازش یک batch بزرگ‌تر شود؛ در غیر این صورت Coordinator تراکنش را به دلیل timeout لغو می‌کند.
