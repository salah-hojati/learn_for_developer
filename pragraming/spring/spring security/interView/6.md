در **Kafka Streams**، تفاوت اصلی **KStream** و **KTable** به مدل ذهنی و نحوه تفسیر رکوردها (کلید و مقدار) بازمی‌گردد:

* **`KStream` (جریان رویدادها / Event Stream):** هر رکورد را یک **رویداد مستقل و غیرقابل بازنویسی** در نظر می‌گیرد. اگر برای کلید `user-1` سه رویداد `login`، `click` و `logout` بیاید، هر سه رخداد جداگانه حفظ و پردازش می‌شوند (شبیه ردیف‌های یک لاگ `INSERT-only`).
* **`KTable` (جدول تغییرپذیر / Changelog Table):** هر رکورد را یک **به‌روزرسانیِ وضعیتِ فعلی برای یک کلید (`key`)** می‌بیند؛ یعنی مقادیر جدید برای یک کلید، مقدار قبلی آن کلید را بازنویسی (`UPSERT`) می‌کنند و پیام با مقدار `null` (*Tombstone*) به معنای **حذف (`DELETE`)** آن کلید است.

---

### ۱. مقایسه کلیدی `KStream` و `KTable`

| ویژگی | `KStream` | `KTable` |
| --- | --- | --- |
| **معنای هر رکورد** | رویداد جدید و مستقل (`INSERT`) | آخرین وضعیت کلید (`UPSERT` یا `DELETE` با `null`) |
| **برخورد با کلید تکراری** | هر دو رکورد به‌عنوان رویداد مجزا پردازش می‌شوند | رکورد جدید جایگزین مقدار قبلی همان کلید می‌شود |
| **حذف داده** | مفهوم حذف ذاتاً تعریف نمی‌شود (فقط رویداد است) | ارسال مقدار `null` برای یک کلید، آن را حذف می‌کند |
| **نیاز به State Store** | معمولاً بدون حالت (مگر در join یا windowing) | ذاتاً حالت‌دار (`Stateful`) است و وضعیت فعلی هر کلید را نگه می‌دارد |
| **مثال کاربردی** | کلیک کاربران، تراکنش‌های مالی، لاگ خطاها | پروفایل فعلی کاربر، موجودی لحظه‌ای کالا، تنظیمات فعال |

---

### ۲. مثال عملی در Kafka Streams

فرض کنید تاپیک `user-scores` پیام‌هایی با کلید نام کاربر و مقدار امتیاز می‌فرستد:

1. `("alice", 10)`
2. `("bob", 5)`
3. `("alice", 25)`

در **`KStream`**:

* خروجی شمارش یا پردازش، هر سه رویداد را جداگانه می‌بیند؛ مثلاً جمع امتیازهای `alice` برابر `10 + 25 = 35` خواهد بود.

در **`KTable`**:

* پس از پیام اول: `alice -> 10`
* پس از پیام دوم: `alice -> 10`, `bob -> 5`
* پس از پیام سوم: `alice -> 25`, `bob -> 5` (امتیاز `alice` از `10` به `25` آپدیت شد؛ اگر `("alice", null)` بیاید، `alice` از جدول حذف می‌شود).

```java
StreamsBuilder builder = new StreamsBuilder();

// تفسیر تاپیک به صورت KStream (هر پیام یک رویداد است)
KStream<String, Long> eventsStream = builder.stream("user-scores");

// تفسیر همان تاپیک به صورت KTable (آخرین مقدار هر کلید نگه داشته می‌شود)
KTable<String, Long> latestScoresTable = builder.table("user-scores");

// تبدیل KTable به KStream (جریان تغییرات / changelog)
KStream<String, Long> scoreUpdatesStream = latestScoresTable.toStream();

```

### ۳. کی از `KStream` و کی از `KTable` استفاده کنیم؟

* **از `KStream` استفاده کنید وقتی:** تاریخچه هر اتفاق مهم است (مثل سبد خرید: `addItem`، `removeItem`، `checkout`)، می‌خواهید روی پنجره‌های زمانی (`Windowing`) تجمیع کنید، یا می‌خواهید رویدادها را به یک `KTable` وصل کنید تا اطلاعات تکمیلی (مثلاً نام یا سطح کاربر) را به رویداد بچسبانید (`KStream-KTable Join`).
* **از `KTable` استفاده کنید وقتی:** فقط **وضعیت فعلی** هر کلید برایتان مهم است (مثل آخرین قیمت نماد، وضعیت فعلی سفارش، یا جدول مرجع کاربران برای غنی‌سازی رویدادها).
* **نکته مهم در `KTable`:** برای اینکه `KTable` هنگام ری‌استارت شدن یا خواندن تاپیک، وضعیت واقعی هر کلید را بدون از دست رفتن آپدیت‌های میانی حفظ کند، بهتر است تاپیک مبدا روی حالت `cleanup.policy=compact` (یا مناسب با نیاز کسب‌وکار) تنظیم شده باشد و کلیدها به‌درستی انتخاب شوند.
