هر چهار Annotation در Spring برای معرفی یک کلاس به‌عنوان **Spring Bean** استفاده می‌شوند؛ اما هرکدام نشان‌دهنده نقش متفاوتی در معماری برنامه هستند.

به زبان ساده:

- `@Component`: یک کامپوننت عمومی
- `@Service`: لایه منطق کسب‌وکار
- `@Repository`: لایه دسترسی به دیتابیس
- `@Controller`: لایه کنترل درخواست‌های وب

# **۱. تفاوت اصلی این چهار Annotation**

| Annotation    | کاربرد                      | لایه معماری  |
| ------------- | --------------------------- | ------------ |
| `@Component`  | کامپوننت عمومی              | عمومی        |
| `@Service`    | منطق کسب‌وکار               | Service      |
| `@Repository` | ارتباط با دیتابیس           | Persistence  |
| `@Controller` | مدیریت درخواست‌های وب و MVC | Presentation |

نکته مهم: هر سه Annotation یعنی `@Service`، `@Repository` و `@Controller` از `@Component` مشتق شده‌اند؛ به همین دلیل Spring آن‌ها را با Component Scanning شناسایی می‌کند.

# **۲. بررسی هر Annotation با مثال**

## **الف) @Component**

برای کلاس‌هایی استفاده می‌شود که نقش مشخصی مانند Service یا Repository ندارند.

مثال:

```
@Component
public class EmailFormatter {

    public String format(String email) {
        return email.toLowerCase().trim();
    }
}
```

Spring این کلاس را شناسایی می‌کند و یک Bean از آن می‌سازد.

استفاده:

```
@Autowired
private EmailFormatter emailFormatter;
```

مثلاً برای کلاس‌های زیر مناسب است:

- Helper
- Utility
- Formatter
- Custom Component

## **ب) @Service**

برای کلاس‌هایی استفاده می‌شود که منطق کسب‌وکار برنامه را پیاده‌سازی می‌کنند.

مثال:

```
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;

    public void registerUser(User user) {

        if (userRepository.existsByEmail(user.getEmail())) {
            throw new RuntimeException(
                "Email already exists"
            );
        }

        userRepository.save(user);
    }
}
```

وظایف Service معمولاً عبارت‌اند از:

- اجرای Business Logic
- مدیریت عملیات چندمرحله‌ای
- هماهنگی بین چند Repository
- مدیریت Transaction

مثلاً اگر ثبت سفارش شامل بررسی موجودی، ثبت سفارش و کاهش موجودی باشد، این منطق بهتر است در Service قرار بگیرد.

## **ج) @Repository**

برای کلاس‌هایی استفاده می‌شود که مسئول دسترسی به داده‌ها هستند.

مثال:

```
@Repository
public class UserRepository {

    @PersistenceContext
    private EntityManager entityManager;

    public void save(User user) {
        entityManager.persist(user);
    }

    public User findById(Long id) {
        return entityManager.find(User.class, id);
    }
}
```

یکی از ویژگی‌های مهم `@Repository`، پشتیبانی از **Exception Translation** است.

یعنی Spring می‌تواند برخی Exceptionهای اختصاصی Persistence مانند Exceptionهای مربوط به JPA یا Hibernate را به Exceptionهای استاندارد Spring مانند `DataAccessException` تبدیل کند.

نکته: این قابلیت از طریق سازوکارهای Persistence Exception Translation انجام می‌شود و صرفاً به معنی تغییر همه Exceptionها نیست.

همچنین اگر از Spring Data JPA استفاده کنیم، معمولاً نیازی نیست Repository را دستی با `@Repository` علامت‌گذاری کنیم:

```
public interface UserRepository
        extends JpaRepository<User, Long> {
}
```

Spring Data JPA پیاده‌سازی لازم را به‌صورت خودکار فراهم می‌کند.

## **د) @Controller**

برای کلاس‌هایی استفاده می‌شود که درخواست‌های HTTP را در معماری Spring MVC مدیریت می‌کنند.

مثال:

```
@Controller
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping("/users")
    public String users(Model model) {

        model.addAttribute(
            "users",
            userService.findAll()
        );

        return "users";
    }
}
```

در این مثال:

- درخواست HTTP دریافت می‌شود.
- Controller، متد Service را فراخوانی می‌کند.
- اطلاعات در Model قرار می‌گیرد.
- نام View برای نمایش به کاربر برگردانده می‌شود.

### **تفاوت @Controller و @RestController**

این تفاوت در مصاحبه بسیار مهم است.

`@Controller` معمولاً برای MVC و بازگرداندن View استفاده می‌شود.

اما `@RestController` برای ساخت REST API است و در واقع ترکیب دو Annotation زیر است:

```
@Controller
@ResponseBody
```

مثال:

```
@RestController
@RequestMapping("/api/users")
public class UserRestController {

    @GetMapping
    public List<User> getUsers() {
        return userService.findAll();
    }
}
```

در اینجا خروجی متد به‌صورت HTTP Response Body، معمولاً JSON، ارسال می‌شود.

# **۳. ارتباط این چهار Annotation در معماری واقعی**

فرض کن یک سیستم مدیریت کاربران داریم.

معماری مناسب می‌تواند به شکل زیر باشد:

**UserController**

@Controller

دریافت درخواست HTTP

**UserService**

@Service

اجرای Business Logic

**UserRepository**

@Repository

دسترسی به دیتابیس

**Database**

برای مثال، وقتی کاربر درخواست زیر را ارسال می‌کند:

```
POST /api/users
```

مراحل به این صورت است:

1. `UserController` درخواست را دریافت می‌کند.
2. `UserService` قوانین کسب‌وکار را اجرا می‌کند.
3. `UserRepository` اطلاعات را ذخیره می‌کند.
4. نتیجه به Controller برمی‌گردد.
5. Controller پاسخ HTTP را ارسال می‌کند.

# **۴. آیا از نظر فنی می‌توانیم همه را با @Component جایگزین کنیم؟**

از نظر شناسایی Bean، در اغلب موارد بله.

مثلاً این کد:

```
@Service
public class UserService {
}
```

از نظر Component Scanning می‌تواند با این کد جایگزین شود:

```
@Component
public class UserService {
}
```

اما چرا از Annotationهای تخصصی استفاده می‌کنیم؟

سه دلیل مهم:

1. **خوانایی کد:** نقش هر کلاس مشخص می‌شود.
2. **معماری بهتر:** مسئولیت هر لایه مشخص است.
3. **رفتارهای تخصصی:** مانند Exception Translation در `@Repository` و رفتارهای خاص Spring MVC در `@Controller`.

نکته فنی: `@Service` به‌تنهایی Transaction ایجاد نمی‌کند. برای مدیریت Transaction معمولاً از `@Transactional` استفاده می‌کنیم.

# **۵. جمع‌بندی برای مصاحبه**

نکته طلایی

هر چهار Annotation باعث می‌شوند Spring کلاس را به‌عنوان Bean شناسایی کند، اما هدف آن‌ها متفاوت است:

- `@Component`: برای کامپوننت‌های عمومی
- `@Service`: برای Business Logic
- `@Repository`: برای Data Access و Exception Translation
- `@Controller`: برای مدیریت درخواست‌های Web MVC

**سؤال مصاحبه‌ای:**

اگر یک کلاس را با `@Component` علامت‌گذاری کنیم، آیا می‌توانیم روی همان کلاس از `@Transactional` استفاده کنیم؟

پاسخ: بله. `@Transactional` محدود به `@Service` نیست؛ روی Beanهای Spring که شرایط لازم برای مدیریت Transaction را دارند نیز قابل استفاده است. البته باید Transaction Management فعال باشد و محدودیت‌های Proxy مانند فراخوانی داخلی متدها (Self-invocation) را هم در نظر گرفت.
