در Spring Boot، برای مدیریت تنظیمات محیط‌های مختلف از قابلیتی به نام **Profiles** استفاده می‌کنیم.

فرض کن یک پروژه داریم که در سه محیط اجرا می‌شود:

- `dev`: محیط توسعه
- `test`: محیط تست
- `prod`: محیط Production

در هر محیط ممکن است تنظیمات دیتابیس، آدرس سرویس‌های خارجی، سطح Logging و سایر پارامترها متفاوت باشند.

هدف این است که بدون تغییر کد برنامه، بتوانیم تنظیمات مناسب هر محیط را بارگذاری کنیم.

# **۱. Spring Profile چیست؟**

با استفاده از `@Profile` می‌توانیم مشخص کنیم یک Bean فقط در محیط خاصی ساخته شود.

مثلاً:

```
@Component
@Profile("dev")
public class DevEmailService implements EmailService {

    @Override
    public void send(String message) {
        System.out.println("Sending email in DEV mode");
    }
}
```

و برای Production:

```
@Component
@Profile("prod")
public class ProdEmailService implements EmailService {

    @Override
    public void send(String message) {
        // Real email sending
    }
}
```

حالا Spring براساس Profile فعال، Bean مناسب را انتخاب می‌کند.

اگر Profile برابر `dev` باشد، `DevEmailService` ساخته می‌شود و اگر `prod` باشد، `ProdEmailService`.

# **۲. مدیریت تنظیمات با application.properties**

یکی از روش‌های رایج، استفاده از فایل‌های تنظیمات جداگانه است.

ساختار پروژه:

```
src/main/resources/
    application.properties
    application-dev.properties
    application-test.properties
    application-prod.properties
```

فایل اصلی:

`application.properties`

```
spring.application.name=my-app

spring.profiles.active=dev
```

تنظیمات Development:

`application-dev.properties`

```
server.port=8080

spring.datasource.url=jdbc:postgresql://localhost:5432/dev_db
spring.datasource.username=dev_user
spring.datasource.password=dev_password

logging.level.root=DEBUG
```

تنظیمات Production:

`application-prod.properties`

```
server.port=8080

spring.datasource.url=jdbc:postgresql://prod-db:5432/prod_db
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}

logging.level.root=INFO
```

وقتی Profile برابر `prod` باشد، Spring Boot علاوه بر تنظیمات عمومی، تنظیمات `application-prod.properties` را نیز بارگذاری می‌کند.

نکته مهم: رمز عبور دیتابیس را نباید مستقیماً در فایل تنظیمات یا Git قرار دهیم.

# **۳. چگونه Profile را فعال کنیم؟**

چند روش برای فعال‌کردن Profile وجود دارد.

**روش اول: در application.properties**

```
spring.profiles.active=dev
```

**روش دوم: هنگام اجرای برنامه**

```
java -jar app.jar --spring.profiles.active=prod
```

**روش سوم: با Environment Variable**

```
export SPRING_PROFILES_ACTIVE=prod
```

**روش چهارم: در Docker**

```
services:
  app:
    image: my-spring-app
    environment:
      SPRING_PROFILES_ACTIVE: prod
```

در محیط Production معمولاً بهتر است Profile از طریق Environment Variable یا تنظیمات Deployment تعیین شود، نه اینکه مقدار آن داخل کد یا فایل اصلی ثابت باشد.

# **۴. استفاده از @Profile برای Configuration**

می‌توانیم به‌جای Beanهای جداگانه، کل Configuration را وابسته به Profile کنیم.

```
@Configuration
@Profile("dev")
public class DevConfig {

    @Bean
    public EmailService emailService() {
        return new MockEmailService();
    }
}
```

و:

```
@Configuration
@Profile("prod")
public class ProdConfig {

    @Bean
    public EmailService emailService() {
        return new SmtpEmailService();
    }
}
```

در این حالت فقط Configuration مربوط به Profile فعال اجرا می‌شود.

همچنین می‌توانیم چند Profile را با هم مشخص کنیم:

```
@Profile({"dev", "test"})
```

یعنی Bean در هرکدام از این دو محیط فعال باشد.

# **۵. تفاوت application.properties و @Profile چیست؟**

این دو مفهوم با هم مرتبط هستند، اما وظیفه متفاوتی دارند.

| قابلیت                       | کاربرد                                       |
| ---------------------------- | -------------------------------------------- |
| `application.properties`     | تعریف مقادیر تنظیمات                         |
| `application-dev.properties` | تنظیمات مخصوص محیط Dev                       |
| `@Profile`                   | فعال‌سازی Bean یا Configuration در محیط مشخص |
| `spring.profiles.active`     | تعیین Profile فعال                           |

مثلاً برای تغییر آدرس دیتابیس از فایل تنظیمات استفاده می‌کنیم، اما برای استفاده از سرویس ایمیل واقعی یا Mock می‌توانیم از `@Profile` استفاده کنیم.

# **۶. مدیریت تنظیمات با @ConfigurationProperties**

در پروژه‌های واقعی بهتر است به‌جای استفاده مکرر از `@Value`، تنظیمات مرتبط را با `@ConfigurationProperties` گروه‌بندی کنیم.

فرض کن تنظیمات سرویس پرداخت به این شکل باشد:

```
payment:
  gateway-url: https://payment.example.com
  timeout: 5000
  enabled: true
```

کلاس تنظیمات:

```
@ConfigurationProperties(prefix = "payment")
@Component
public class PaymentProperties {

    private String gatewayUrl;
    private int timeout;
    private boolean enabled;

    // Getters and Setters
}
```

استفاده در Service:

```
@Service
public class PaymentService {

    private final PaymentProperties properties;

    public PaymentService(PaymentProperties properties) {
        this.properties = properties;
    }

    public void processPayment() {

        if (properties.isEnabled()) {
            System.out.println(
                properties.getGatewayUrl()
            );
        }
    }
}
```

مزایای این روش:

- گروه‌بندی تنظیمات مرتبط
- Type Safety
- امکان اعتبارسنجی تنظیمات
- نگهداری آسان‌تر
- مناسب برای پروژه‌های بزرگ

می‌توانیم اعتبارسنجی هم اضافه کنیم:

```
@ConfigurationProperties(prefix = "payment")
@Validated
@Component
public class PaymentProperties {

    @NotBlank
    private String gatewayUrl;

    @Min(1000)
    private int timeout;

    // Getters and Setters
}
```

در صورت نامعتبر بودن تنظیمات، برنامه هنگام راه‌اندازی با خطا مواجه می‌شود.

# **۷. تفاوت Profile و Environment Variable**

یک نکته مهم در مصاحبه:

**Profile مشخص می‌کند کدام مجموعه تنظیمات فعال باشد؛ Environment Variable مقداری را در اختیار برنامه قرار می‌دهد.**

مثلاً:

```
spring.profiles.active=prod

spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
```

در سرور:

```
export SPRING_PROFILES_ACTIVE=prod
export DB_USERNAME=app_user
export DB_PASSWORD=secret
```

Spring Boot مقدار متغیرها را هنگام بارگذاری تنظیمات جایگزین می‌کند.

نکته امنیتی: برای Production بهتر است Secretها از Secret Manager یا سازوکار امن مدیریت Secret در زیرساخت دریافت شوند؛ نه اینکه در فایل‌های Properties ذخیره شوند.

# **۸. مدیریت تنظیمات در محیط‌های مختلف**

در پروژه‌های حرفه‌ای، من معمولاً چنین ساختاری در نظر می‌گیرم:

## **ساختار تنظیمات پیشنهادی**

**application.yml**

تنظیمات مشترک تمام محیط‌ها

**dev**

Local DB

DEBUG

**test**

Test DB

INFO

**prod**

Prod DB

INFO

**منابع تأمین تنظیمات**

- Environment Variables
- Docker / Kubernetes ConfigMap
- Kubernetes Secrets
- Secret Manager

مثلاً فایل اصلی:

```
spring:
  application:
    name: my-app

  jpa:
    open-in-view: false

server:
  port: 8080
```

فایل `application-dev.yml`:

```
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/dev_db
    username: dev
    password: dev

logging:
  level:
    root: DEBUG
```

فایل `application-prod.yml`:

```
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

logging:
  level:
    root: INFO
```

برای فعال‌سازی Profile:

```
java -jar app.jar \
  --spring.profiles.active=prod
```

# **۹. نکات مهم و اشتباهات رایج**

1. اطلاعات محرمانه مانند Password و API Key را داخل Git قرار نمی‌دهم.
2. برای Production از `ddl-auto=create` یا `create-drop` استفاده نمی‌کنم؛ معمولاً Migration کنترل‌شده با Flyway یا Liquibase مناسب‌تر است.
3. تنظیمات مشترک را در فایل اصلی نگه می‌دارم و فقط تفاوت محیط‌ها را در فایل‌های Profile قرار می‌دهم.
4. برای تنظیمات پیچیده از `@ConfigurationProperties` استفاده می‌کنم.
5. از فعال‌شدن اشتباهی Profile توسعه در Production جلوگیری می‌کنم.
6. در تست‌ها از `@ActiveProfiles("test")` استفاده می‌کنم:

```
@SpringBootTest
@ActiveProfiles("test")
class UserServiceTest {

    @Test
    void shouldCreateUser() {
        // Test
    }
}
```

# **۱۰. پاسخ مناسب برای مصاحبه**

اگر در مصاحبه بپرسند:

**How do you manage environment-specific configurations in Spring Boot?**

می‌توانی این‌طور پاسخ بدهی:

> I use Spring Profiles to separate configuration for development, testing, and production environments.
>
> I keep common properties in application.yml and environment-specific properties in files such as application-dev.yml and application-prod.yml.
>
> I activate profiles through environment variables or deployment arguments rather than hardcoding them.
>
> For structured configuration, I prefer @ConfigurationProperties because it provides type safety and validation.
>
> I never store sensitive information such as database passwords or API keys in source control. Instead, I use environment variables or a secret management solution.
>
> For testing, I use @ActiveProfiles("test") to load test-specific configurations.

## **سؤال تمرینی مصاحبه**

فرض کن برنامه Spring Boot در محیط Production اجرا شده، اما به‌اشتباه تنظیمات دیتابیس Development را بارگذاری می‌کند.

**چه مواردی را بررسی می‌کنی تا علت مشکل را پیدا کنی؟**

نکته مهم: فقط `spring.profiles.active` را بررسی نکن؛ باید اولویت منابع تنظیمات، Environment Variableها، آرگومان‌های اجرای برنامه و تنظیمات Deployment را هم بررسی کنی.
