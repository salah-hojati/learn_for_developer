# 🔐 Lesson 3: In-Memory Authentication & Password Encoding

In this lesson, we move beyond `application.properties` and define users properly in code. We’ll also introduce password encoding — one of the most important security concepts you must get right.

---

## 🎯 Lesson 3 Goal
By the end of this lesson, you should be able to:

- Define multiple users using `InMemoryUserDetailsManager`
- Explain why passwords must be encoded (hashed)
- Use `BCryptPasswordEncoder` correctly
- Understand the difference between `UserDetails` and `UserDetailsService`
- Avoid the most common password encoding mistakes

---

## 1. Why Do We Need a Proper User Setup?

Using `application.properties` works for a single user, but it has limits:

- You can only define **one** user
- Passwords are stored in **plain text**
- You cannot assign **multiple roles** easily
- It’s not reusable in real applications

The proper approach is to define a `UserDetailsService` bean that manages users.

---

## 2. The Building Blocks

Before writing code, let’s clarify the core interfaces:

| Interface / Class | Purpose |
|---|---|
| `UserDetails` | Represents a user (username, password, authorities, account status) |
| `UserDetailsService` | Loads a user by username |
| `UserDetailsManager` | Extends `UserDetailsService` with create/update/delete operations |
| `InMemoryUserDetailsManager` | An in-memory implementation of `UserDetailsManager` |
| `User` (builder) | A convenient builder for creating `UserDetails` objects |
| `PasswordEncoder` | Encodes and verifies passwords |
| `BCryptPasswordEncoder` | A strong, recommended `PasswordEncoder` |

---

## 3. Why Password Encoding Matters

### The problem

If you store passwords like this:

```text
admin → admin123
student → learn123
```

…and your database is leaked, every user’s password is exposed immediately.

### The solution: hashing

A **password encoder** transforms the raw password into a hash:

```text
admin123 → $2a$10$7EqJtq98hPqEX7fNZaFWoO...
```

Key properties of a good encoder:

- **One-way**: You cannot reverse the hash back to the original password.
- **Salted**: The same password produces different hashes each time (BCrypt does this automatically).
- **Slow by design**: It takes intentional time to compute, making brute-force attacks expensive.

### ⚠️ Common mistake

Never compare passwords like this:

```java
// ❌ WRONG
if (rawPassword.equals(storedPassword)) { ... }
```

Always use the encoder:

```java
// ✅ CORRECT
if (passwordEncoder.matches(rawPassword, storedHash)) { ... }
```

## 4. Creating the PasswordEncoder Bean

Create a configuration class:

```java
package com.example.demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class PasswordConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

> 💡 **Why BCrypt?** It is the de-facto standard for password hashing. It includes a salt automatically and has a configurable cost factor (default 10). Alternatives include `Argon2PasswordEncoder` (stronger but needs extra dependency) and `Pbkdf2PasswordEncoder`.

## 5. Defining Users In-Memory

Now create a `UserDetailsService` bean with multiple users:

```java
package com.example.demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;

@Configuration
public class UserConfig {

    @Bean
    public UserDetailsService userDetailsService(PasswordEncoder passwordEncoder) {

        UserDetails admin = User.builder()
                .username("admin")
                .password(passwordEncoder.encode("admin123"))
                .roles("ADMIN", "USER")   // stored as ROLE_ADMIN, ROLE_USER
                .build();

        UserDetails student = User.builder()
                .username("student")
                .password(passwordEncoder.encode("learn123"))
                .roles("USER")
                .build();

        return new InMemoryUserDetailsManager(admin, student);
    }
}
```

### What’s happening here?

| Line | Explanation |
|---|---|
| `User.builder()` | Fluent builder for creating a `UserDetails` |
| `.password(passwordEncoder.encode(...))` | **Critical**: the password is hashed before storage |
| `.roles("ADMIN", "USER")` | Automatically prepends `ROLE_` |
| `new InMemoryUserDetailsManager(...)` | Stores users in memory for this session |

---

## 6. `roles()` vs `authorities()`

This is a common source of bugs. Understand the difference:

### `roles("ADMIN")`
Stores the authority as `ROLE_ADMIN`.

### `authorities("ROLE_ADMIN")`
Stores the authority exactly as written: `ROLE_ADMIN`.

### `authorities("READ_USERS")`
Stores the authority exactly as written: `READ_USERS`.

### Matching in configuration

```java
.requestMatchers("/admin/**").hasRole("ADMIN")          // expects ROLE_ADMIN
.requestMatchers("/admin/**").hasAuthority("ROLE_ADMIN") // expects ROLE_ADMIN
.requestMatchers("/reports/**").hasAuthority("READ_REPORTS") // expects READ_REPORTS
```

### Rule of thumb

- Use `roles()` for coarse-grained access (ADMIN, USER, MANAGER)
- Use `authorities()` for fine-grained permissions (READ_USERS, DELETE_ORDER)

## 7. Wiring It All Together

Now update `SecurityConfig` to protect routes based on roles:

```java
package com.example.demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .requestMatchers("/user/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()
            )
            .formLogin(form -> form.permitAll())
            .httpBasic(basic -> {});

        return http.build();
    }
}
```

Add new endpoints to test:

```java
@GetMapping("/admin/dashboard")
public String adminDashboard() {
    return "Welcome, Admin!";
}

@GetMapping("/user/profile")
public String userProfile() {
    return "User profile page.";
}
```

## 9. Common Mistakes to Avoid

### ❌ Forgetting to encode the password

```java
.password("admin123")   // BUG: plain text
```

Spring Security will not match this against the raw input because the encoder expects a hashed value.

**Fix:** always use `passwordEncoder.encode(...)`.

### ❌ Using two different PasswordEncoders

If you encode with BCrypt but declare a `NoOpPasswordEncoder` bean, authentication will fail. There must be **exactly one** `PasswordEncoder` bean in context (unless you're doing something advanced).

### ❌ Mixing `roles()` and `hasAuthority()`

```java
.roles("ADMIN")                              // stores ROLE_ADMIN
.hasAuthority("ADMIN")                       // looks for ADMIN → MISMATCH
```

**Fix:** match them correctly, or use `hasRole("ADMIN")`.

### ❌ Defining a `UserDetailsService` and `application.properties` user

If both exist, the `application.properties` user is silently ignored. Choose one approach.

## 10. Inspecting the Hash

Want to see what BCrypt looks like? Add a temporary test:

```java
@Bean
public CommandLineRunner inspectPassword(PasswordEncoder encoder) {
    return args -> {
        String hash = encoder.encode("admin123");
        System.out.println("Hash: " + hash);
        System.out.println("Matches: " + encoder.matches("admin123", hash));
    };
}
```

Output example:

```text
Hash: $2a$10$K3f9...ZmXK8c1w
Matches: true
```

Notice each run produces a **different hash** for the same password — that’s the salt at work.
