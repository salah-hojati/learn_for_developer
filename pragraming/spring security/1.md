## 1. Authentication vs Authorization

Think of a building:

- **Authentication** = the security guard checks your ID.  
  *“Who are you?”*

- **Authorization** = your access card decides which rooms you can enter.  
  *“What are you allowed to do?”*

In Spring Security:

| Concept | Meaning | Example |
|---|---|---|
| Authentication | Verifying identity | Username + password is correct |
| Authorization | Checking permission | User has `ROLE_ADMIN` to access `/admin` |

A user must usually be **authenticated first**, then **authorized**.

---

## 2. Principal, Authority, and Role

These three terms appear everywhere.

### Principal
The currently logged-in user.  
It could be a `UserDetails` object, a username, or a custom object.

### Authority
A fine-grained permission.  
Examples:
- `READ_USERS`
- `DELETE_ORDER`
- `ROLE_ADMIN`

### Role
A coarse-grained group of authorities.  
In Spring Security, roles are just authorities with the prefix `ROLE_`.

So:

```text
Role: ADMIN
Actual authority stored: ROLE_ADMIN
```

That is why `hasRole("ADMIN")` checks for `ROLE_ADMIN`, while `hasAuthority("ROLE_ADMIN")` checks the exact string.

---

## 3. The SecurityContext

When a user is authenticated, Spring Security stores their identity in the **SecurityContext**.

You can think of it as:

> “For this request, here is the authenticated user and their permissions.”

Later, authorization checks read from this context.

The `SecurityContextHolder` is the class that gives access to the current `SecurityContext`.

---

## 4. The Filter Chain — The Heart of Spring Security

Spring Security is not a single check. It is a **chain of servlet filters**.

Every HTTP request passes through a sequence of security filters before reaching your controller.

Simplified flow:

```text
HTTP Request
   ↓
Security Filter Chain
   ↓
Authentication Filter
   ↓
AuthenticationManager
   ↓
AuthenticationProvider
   ↓
UserDetailsService
   ↓
Database / In-Memory Users
   ↓
PasswordEncoder checks password
   ↓
Authenticated Authentication object
   ↓
SecurityContext
   ↓
Authorization check
   ↓
Your Controller
```

### Key components

| Component | Job |
|---|---|
| `SecurityFilterChain` | Defines which security filters run and in what order |
| `AuthenticationManager` | Main entry point for authentication |
| `AuthenticationProvider` | Performs the actual authentication logic |
| `UserDetailsService` | Loads user details by username |
| `PasswordEncoder` | Hashes and verifies passwords |
| `SecurityContextHolder` | Stores the authenticated user for the request |

---

## 5. What Happens During Login?

Here is the simplified story:

1. A request arrives at your app.
2. It enters the Spring Security filter chain.
3. An authentication filter extracts credentials, such as username and password.
4. The `AuthenticationManager` receives them.
5. It delegates to an `AuthenticationProvider`.
6. The provider calls `UserDetailsService` to load the user.
7. The provider compares the submitted password with the stored encoded password using a `PasswordEncoder`.
8. If correct, it creates an authenticated `Authentication` object.
9. That object is stored in the `SecurityContext`.
10. Authorization rules then decide whether the user can access the requested URL or method.

---

## 6. The Default Behavior You Will See Soon

When you add:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

Spring Boot automatically:

- Secures all endpoints
- Creates a default user named `user`
- Generates a random password printed in the console
- Shows a default login page

That is Spring Security’s “hello world.”
