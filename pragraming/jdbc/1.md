## 🗺️ Area 1: Complete CRUD Example — A `Product` DAO

CRUD (Create, Read, Update, Delete) is the foundation. The best way to internalize JDBC is to build a **Data Access Object (DAO)** that encapsulates all SQL for a single entity.

### Step 1: Define the Data Model

Use a Java **Record** (Java 16+) to represent a database row. Records automatically generate constructors, accessors, `equals()`, `hashCode()`, and `toString()`, making them ideal immutable data carriers.

```java
public record Product(int id, String name, double price, int stock) {
    // Compact canonical constructor can validate data
    public Product {
        if (price < 0) throw new IllegalArgumentException("price must be ≥ 0");
    }
}
```

### Step 2: Set Up the Database Schema

For learning, use an in-memory **H2** database. It requires no external server and exists only while the application runs, making it perfect for development and testing.

```sql
CREATE TABLE products (
    id    INT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(100) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0
);
```

### Step 3: Implement the DAO

The DAO centralizes all JDBC logic. Every method follows the same pattern: obtain a connection, create a `PreparedStatement`, bind parameters, execute, and handle the `ResultSet` (for queries).

```java
import java.sql.*;
import java.util.*;

public class ProductDao {
    private final DataSource dataSource;   // injected pool (see Area 3)

    public ProductDao(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    // CREATE
    public int create(Product p) throws SQLException {
        String sql = "INSERT INTO products (name, price, stock) VALUES (?, ?, ?)";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, p.name());
            ps.setDouble(2, p.price());
            ps.setInt(3, p.stock());
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                if (keys.next()) return keys.getInt(1);
            }
        }
        throw new SQLException("Insert failed, no generated key");
    }

    // READ (single)
    public Optional<Product> findById(int id) throws SQLException {
        String sql = "SELECT id, name, price, stock FROM products WHERE id = ?";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) return Optional.of(mapRow(rs));
            }
        }
        return Optional.empty();
    }

    // READ (all)
    public List<Product> findAll() throws SQLException {
        List<Product> list = new ArrayList<>();
        String sql = "SELECT id, name, price, stock FROM products ORDER BY id";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql);
             ResultSet rs = ps.executeQuery()) {
            while (rs.next()) list.add(mapRow(rs));
        }
        return list;
    }

    // UPDATE
    public boolean update(Product p) throws SQLException {
        String sql = "UPDATE products SET name = ?, price = ?, stock = ? WHERE id = ?";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, p.name());
            ps.setDouble(2, p.price());
            ps.setInt(3, p.stock());
            ps.setInt(4, p.id());
            return ps.executeUpdate() > 0;
        }
    }

    // DELETE
    public boolean delete(int id) throws SQLException {
        String sql = "DELETE FROM products WHERE id = ?";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, id);
            return ps.executeUpdate() > 0;
        }
    }

    private Product mapRow(ResultSet rs) throws SQLException {
        return new Product(
            rs.getInt("id"),
            rs.getString("name"),
            rs.getDouble("price"),
            rs.getInt("stock")
        );
    }
}
```

**Key takeaways for this area:**
- Always use **`PreparedStatement`** with `?` placeholders — never string concatenation — to prevent SQL injection.
- Use **`try-with-resources`** so connections, statements, and result sets close automatically.
- For inserts, request `RETURN_GENERATED_KEYS` to retrieve auto-incremented IDs.

## ⚖️ Area 2: Spring JDBC vs. Raw JDBC

Raw JDBC works, but it forces you to repeat infrastructure code in every method. **Spring JDBC** (specifically `JdbcTemplate`) is an abstraction layer that eliminates this boilerplate.

### The Problem: Raw JDBC Boilerplate

Even a simple query requires connection handling, statement creation, result set iteration, exception handling, and resource cleanup:

```java
// Raw JDBC — lots of plumbing
try (Connection conn = ds.getConnection();
     Statement st = conn.createStatement();
     ResultSet rs = st.executeQuery("SELECT COUNT(*) FROM orders")) {
    rs.next();
    int count = rs.getInt(1);
} catch (SQLException e) {
    // handle checked exception
}
```

### The Solution: Spring `JdbcTemplate`

`JdbcTemplate` uses the **Template Method pattern** to hide all the low-level plumbing. You provide only the SQL and the mapping logic.

```java
// Spring JDBC — one line
int count = jdbcTemplate.queryForObject(
    "SELECT COUNT(*) FROM orders", Integer.class);
```

### Key Differences at a Glance

| Concern | Raw JDBC | Spring JDBC |
|---|---|---|
| **Connection management** | Manual `try/finally` or try-with-resources | Handled automatically |
| **Exception handling** | Checked `SQLException` everywhere | Translated to unchecked `DataAccessException` hierarchy |
| **Boilerplate** | High (open, prepare, execute, iterate, close) | Minimal — template handles it |
| **Result mapping** | Manual `rs.getXxx()` calls | `RowMapper` / `BeanPropertyRowMapper` |
| **Transaction management** | Manual `setAutoCommit(false)` / `commit` / `rollback` | Declarative `@Transactional` |
| **Database dialect differences** | You handle them | Exception translation smooths them over |

### Critical Nuance

**Spring JDBC does not replace JDBC — it builds on top of it.** Under the hood, it still uses `PreparedStatement`, `ResultSet`, and connection pools. Learning raw JDBC first is essential because Spring JDBC is just a smarter, safer wrapper around the same concepts.

## 🔌 Area 3: Connection Pooling with HikariCP

Creating a new physical database connection for every request is catastrophically slow. A **connection pool** maintains a set of open, reusable connections.

### Why HikariCP?

HikariCP is the **de-facto standard** connection pool in modern Java applications. It is the default in Spring Boot and is renowned for its performance and reliability.

### Step 1: Add the Dependency

```xml
<dependency>
    <groupId>com.zaxxer</groupId>
    <artifactId>HikariCP</artifactId>
    <version>5.1.0</version>
</dependency>
```

### Step 2: Configure the Pool

```java
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import javax.sql.DataSource;

public class DatabaseConfig {
    private static final HikariDataSource DATA_SOURCE;

    static {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:mysql://localhost:3306/myapp");
        config.setUsername("appuser");
        config.setPassword("secret");

        // Pool sizing — the most important tuning knob
        config.setMaximumPoolSize(10);     // max connections in pool
        config.setMinimumIdle(2);          // keep at least 2 ready

        // Timeouts (milliseconds)
        config.setConnectionTimeout(30_000);  // wait max 30s for a connection
        config.setIdleTimeout(600_000);       // close idle conns after 10min
        config.setMaxLifetime(1_800_000);     // retire conns after 30min

        DATA_SOURCE = new HikariDataSource(config);
    }

    public static DataSource get() {
        return DATA_SOURCE;
    }
}
```

### Step 3: Use the Pool in Your DAO

```java
try (Connection conn = DatabaseConfig.get().getConnection()) {
    // conn is a pooled connection — obtained instantly if available
}
// close() returns the connection to the pool, NOT closes the physical connection
```

### Pool Sizing Rule of Thumb

A common starting formula is: `connections = (core_count × 2) + effective_spindle_count`. For most web apps, a pool of **10–20** connections is sufficient. Larger pools often degrade performance due to context switching and lock contention.

## 🔒 Area 4: Transactions, Isolation Levels & Savepoints

### Why Transactions Matter

A transaction groups multiple SQL statements into a single **all-or-nothing** unit. If any part fails, the database rolls back to the state before the transaction began, preventing partial writes and data corruption.

### The Core JDBC Transaction API

```java
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false);   // 1. start transaction mode

    try {
        // 2. perform multiple operations
        debitAccount(conn, fromId, amount);
        creditAccount(conn, toId, amount);

        conn.commit();           // 3. commit if all succeed
    } catch (SQLException e) {
        conn.rollback();         // 4. rollback on any failure
        throw e;
    } finally {
        conn.setAutoCommit(true); // 5. restore default
    }
}
```

### Isolation Levels

Isolation levels control how concurrent transactions interact. Higher isolation = more consistency but less concurrency.

| Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| `READ_UNCOMMITTED` | ✅ Possible | ✅ Possible | ✅ Possible |
| `READ_COMMITTED` (common default) | ❌ | ✅ Possible | ✅ Possible |
| `REPEATABLE_READ` | ❌ | ❌ | ✅ Possible |
| `SERIALIZABLE` | ❌ | ❌ | ❌ |

```java
conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
```

### Savepoints — Partial Rollback

A `Savepoint` marks a checkpoint within a transaction. You can roll back to it without discarding the entire transaction.

```java
conn.setAutoCommit(false);

try {
    insertOrder(conn, order);                    // step 1
    Savepoint afterOrder = conn.setSavepoint("after_order");

    try {
        insertOrderItems(conn, order, items);    // step 2
        conn.commit();
    } catch (SQLException e) {
        conn.rollback(afterOrder);               // undo step 2 only
        // step 1 is still intact — can retry or commit partial data
        conn.commit();
    }
} finally {
    conn.setAutoCommit(true);
}
```

**Savepoints are especially useful** when you want to attempt an optional enrichment step but still keep the essential write if the enrichment fails.

## ⚡ Area 5: Batch Processing for Performance

Sending 1,000 individual `INSERT` statements to the database means 1,000 network round-trips. **Batch processing** groups them into a single round-trip, often yielding **10–100× throughput improvement**.

### Standard JDBC Batch

```java
String sql = "INSERT INTO products (name, price, stock) VALUES (?, ?, ?)";

try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {

    for (Product p : products) {
        ps.setString(1, p.name());
        ps.setDouble(2, p.price());
        ps.setInt(3, p.stock());
        ps.addBatch();               // queue this row
    }

    int[] counts = ps.executeBatch(); // send all at once
}
```

### Tuning Batch Performance

| Tuning | Effect |
|---|---|
| **Batch size** (e.g., 500–1,000 rows per batch) | Avoids memory bloat; too large a batch can backfire |
| **`rewriteBatchedInserts=true`** (PostgreSQL) | Driver rewrites `INSERT` batches into multi-row `INSERT` statements |
| **`useBulkCopyForBatchInsert=true`** (SQL Server) | Enables the driver's internal bulk-copy API for dramatic speedup |
| **`rewriteBatchedStatements=true`** (MySQL) | Similar rewrite for MySQL |

> ⚠️ **Caveat**: Some drivers silently decompose batches into individual statements unless explicitly configured. For example, OceanBase's driver ignores `executeBatch()` by default unless certain flags are set. Always verify batch behavior with a quick performance test.

## 🗄️ Area 6: Database-Specific Connection Details

The JDBC API is database-agnostic, but the **connection URL** and **driver dependency** are vendor-specific.

### Connection URL Format

```
jdbc:<database_type>://<host>:<port>/<database_name>?<property>=<value>&...
```

| Database | JDBC URL Example | Driver Artifact |
|---|---|---|
| **MySQL** | `jdbc:mysql://localhost:3306/mydb?useSSL=false&serverTimezone=UTC` | `com.mysql:mysql-connector-j` |
| **PostgreSQL** | `jdbc:postgresql://localhost:5432/mydb?ssl=true&sslmode=require` | `org.postgresql:postgresql` |
| **Oracle** | `jdbc:oracle:thin:@localhost:1521:mydb` | `com.oracle.database.jdbc:ojdbc11` |
| **SQL Server** | `jdbc:sqlserver://localhost:1433;databaseName=mydb;encrypt=true;trustServerCertificate=true` | `com.microsoft.sqlserver:mssql-jdbc` |
| **H2 (in-memory)** | `jdbc:h2:mem:testdb` | `com.h2database:h2` |

### Critical Notes for Each Database

- **MySQL**: Include `serverTimezone` to avoid timezone-related data corruption. Use `useSSL=false` **only in development** — enable SSL in production.
- **PostgreSQL**: The driver supports `reWriteBatchedInserts=true` for automatic batch optimization.
- **Oracle**: The `thin` driver is a pure-Java driver (no native libraries). The SID (`mydb`) identifies the database instance.
- **SQL Server**: Add `encrypt=true` and `trustServerCertificate=true` for local/dev environments with self-signed certificates.

### Security Best Practice

**Never hardcode credentials in the connection URL or source code.** Use environment variables, configuration files, or a secrets manager.

## 🎯 Putting It All Together — Recommended Learning Order

1. **Build the `ProductDao` CRUD** on H2 (Area 1) — feel the manual boilerplate.
2. **Introduce HikariCP** (Area 3) — replace `DriverManager` with a `DataSource`.
3. **Add a transaction** (Area 4) — wrap a two-step operation (e.g., "purchase" = decrement stock + insert order) in `commit`/`rollback`.
4. **Add batch inserts** (Area 5) — measure the speedup with 10,000 rows.
5. **Refactor to Spring JDBC** (Area 2) — delete the try-with-resources boilerplate and compare line counts.
6. **Switch the URL and driver** (Area 6) — run the same DAO against PostgreSQL without changing SQL.

Each layer addresses a real pain point from the previous one, so the "why" behind each abstraction becomes viscerally clear.
