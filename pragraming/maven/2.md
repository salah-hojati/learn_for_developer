# Maven: Step-by-Step Learning Guide

I'll walk you through Maven progressively, with hands-on commands and file contents at each step. Follow these lessons in order and actually type the commands — that's how it sticks.

---

## 🧱 LESSON 1: Install & Verify Maven

**Step 1.1 — Check Java first**

```bash
java -version
```

You need Java 8+ (Java 11/17 recommended). If missing, install a JDK first.

**Step 1.2 — Install Maven**

- **Windows**: Download the binary zip from https://maven.apache.org/download.cgi, extract to `C:\Program Files\Apache\maven`, then add `C:\Program Files\Apache\maven\bin` to your `PATH`.
- **macOS**: `brew install maven`
- **Ubuntu/Debian**: `sudo apt install maven`

**Step 1.3 — Verify**

```bash
mvn -version
```

Expected output (versions will differ):

```
Apache Maven 3.9.6
Maven home: /usr/share/maven
Java version: 17.0.9, vendor: Eclipse Adoptium
```

**✅ Checkpoint**: You see the Maven version and it correctly detects your Java version.

## 🧱 LESSON 2: Create Your First Project

**Step 2.1 — Generate a project skeleton**

Navigate to a folder where you want your project, then run:

```bash
mvn archetype:generate \
  -DgroupId=com.example \
  -DartifactId=hello-maven \
  -DarchetypeArtifactId=maven-archetype-quickstart \
  -DinteractiveMode=false
```

(On Windows cmd, put everything on one line without backslashes.)

**Step 2.2 — Enter the project and look around**

```bash
cd hello-maven
tree .        # or: find . -type f (Linux/Mac)
```

You should see:

```
hello-maven/
├── pom.xml
└── src/
    ├── main/java/com/example/App.java
    └── test/java/com/example/AppTest.java
```

This is the **standard directory layout** — Maven's "convention over configuration." Remember it:

| Folder | Purpose |
|---|---|
| `src/main/java` | Production Java source |
| `src/main/resources` | Production resources (config, XML, etc.) |
| `src/test/java` | Test source |
| `src/test/resources` | Test resources |
| `target/` | Build output (auto-generated, never edit) |

**Step 2.3 — Build it**

```bash
mvn package
```

Watch the console. You'll see phases running: `compile` → `test` → `package`. At the end there's a `BUILD SUCCESS`.

**Step 2.4 — Look at the output**

```bash
ls target/
```

You'll find `hello-maven-1.0-SNAPSHOT.jar` — your packaged app.

**Step 2.5 — Run it**

```bash
java -cp target/hello-maven-1.0-SNAPSHOT.jar com.example.App
```

Output: `Hello World!`

**✅ Checkpoint**: You built and ran a JAR with only two commands (`mvn package`, `java`). This alone is 80% of daily Maven usage.

## 🧱 LESSON 3: Understand the `pom.xml`

Open `pom.xml`. It looks like this (abbreviated):

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0" ...>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>hello-maven</artifactId>
  <version>1.0-SNAPSHOT</version>
  <packaging>jar</packaging>

  <properties>
    <maven.compiler.source>1.8</maven.compiler.source>
    <maven.compiler.target>1.8</maven.compiler.target>
  </properties>

  <dependencies>
    <dependency>
      <groupId>junit</groupId>
      <artifactId>junit</artifactId>
      <version>4.11</version>
      <scope>test</scope>
    </dependency>
  </dependencies>
</project>
```

**Understand each element:**

- **`groupId`** — your organization (reverse domain: `com.example`)
- **`artifactId`** — the project name (`hello-maven`)
- **`version`** — project version; `-SNAPSHOT` means "in development"
- **`packaging`** — output type: `jar`, `war`, `pom`, etc.
- **`properties`** — variables you can reference with `${name}`
- **`dependencies`** — libraries your project needs

The triple `groupId:artifactId:version` is called the **GAV coordinates** — it uniquely identifies any artifact in the Maven universe.

**🏋️ Exercise**: Change `<version>` to `1.0.0` and rebuild. Notice the JAR name changed.

**✅ Checkpoint**: You can read a POM and identify where dependencies and settings live.

## 🧱 LESSON 4: The Build Lifecycle & Core Commands

Maven's `default` lifecycle is a **sequence of phases**. Running a phase runs all phases before it.

```
validate → compile → test → package → verify → install → deploy
```

**Try each command — watch how much it does:**

```bash
mvn clean      # Delete the target/ folder
mvn compile    # Compile src/main/java → target/classes
mvn test       # Compile tests + run them (uses Surefire plugin)
mvn package    # Build the JAR into target/
mvn install    # Also copy the JAR into ~/.m2/repository for local reuse
```

**Key insight**: `mvn install` runs **everything** up to and including install. `mvn package` does everything up to package. This "phase accumulation" is a Maven superpower — you rarely need to specify many steps.

**Combining commands:**

```bash
mvn clean package   # Clean, then build from scratch (very common)
```

**✅ Checkpoint**: You know which command to run for each stage of the build, and why.

## 🧱 LESSON 5: Add a Dependency (and Watch Maven Work)

**Step 5.1 — Add Apache Commons Lang**

Edit `pom.xml` inside `<dependencies>`:

```xml
<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-lang3</artifactId>
  <version>3.14.0</version>
</dependency>
```

**Step 5.2 — Use it in code**

Edit `src/main/java/com/example/App.java`:

```java
package com.example;

import org.apache.commons.lang3.StringUtils;

public class App {
    public static void main(String[] args) {
        System.out.println(StringUtils.capitalize("hello maven"));
    }
}
```

**Step 5.3 — Build and run**

```bash
mvn clean package
java -cp target/hello-maven-1.0.0.jar com.example.App
```

Output: `Hello maven`

**Notice**: You did NOT download the JAR manually. Maven found `commons-lang3` on Maven Central, downloaded it to `~/.m2/repository`, and put it on the classpath during compile and packaging.

**Step 5.4 — See the dependency tree**

```bash
mvn dependency:tree
```

You'll see `commons-lang3` in the tree. If it had its own dependencies, they'd be listed below it as **transitive dependencies**.

**✅ Checkpoint**: You can add any library by pasting its GAV into the POM, and inspect what gets pulled in.

## 🧱 LESSON 6: Dependency Scopes & Conflicts

**Scopes** control *when* a dependency is on the classpath:

| Scope | Compile | Test | Runtime | Packaged in JAR |
|---|---|---|---|---|
| `compile` (default) | ✔ | ✔ | ✔ | ✔ |
| `test` | ✘ | ✔ | ✘ | ✘ |
| `provided` | ✔ | ✔ | ✘ | ✘ (e.g., servlet-api) |
| `runtime` | ✘ | ✔ | ✔ | ✔ (e.g., JDBC drivers) |

**🏋️ Exercise**: Change the `commons-lang3` scope to `test`. Try to `mvn compile` — it fails because the class is unavailable at compile time.

**Handling conflicts** — Maven picks one version when two paths bring different versions. See it with:

```bash
mvn dependency:tree -Dverbose
```

Exclude a problematic transitive dependency:

```xml
<dependency>
  <groupId>some.group</groupId>
  <artifactId>some-artifact</artifactId>
  <version>1.0</version>
  <exclusions>
    <exclusion>
      <groupId>bad.group</groupId>
      <artifactId>bad-artifact</artifactId>
    </exclusion>
  </exclusions>
</dependency>
```

**✅ Checkpoint**: You understand `compile` vs `test` vs `provided`, and can exclude unwanted transitive deps.

## 🧱 LESSON 7: Configure a Plugin (The Java Version Example)

Plugins are what actually execute Maven's work. Let's set Java 17 compilation explicitly via `maven-compiler-plugin`.

Replace the `<properties>` block with:

```xml
<properties>
  <maven.compiler.release>17</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
```

Or, more explicitly, in `<build><plugins>`:

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.11.0</version>
      <configuration>
        <release>17</release>
      </configuration>
    </plugin>
  </plugins>
</build>
```

**Step 7.1 — Run a plugin goal directly**

```bash
mvn help:effective-pom       # See the fully resolved POM
mvn dependency:analyze       # Find unused/undeclared deps
mvn site                     # Generate a project website
```

**✅ Checkpoint**: You can pin a plugin version, configure it, and call goals directly from the CLI.

## 🧱 LESSON 8: Profiles (Environment-Specific Builds)

Profiles let you vary the build without editing the POM each time. Add to `pom.xml`:

```xml
<profiles>
  <profile>
    <id>dev</id>
    <properties>
      <env.name>development</env.name>
    </properties>
  </profile>
  <profile>
    <id>prod</id>
    <properties>
      <env.name>production</env.name>
    </properties>
  </profile>
</profiles>
```

Then use the property somewhere, e.g., in a resource:

`src/main/resources/config.properties`:

```
environment=${env.name}
```

Enable resource filtering in `<build>`:

```xml
<build>
  <resources>
    <resource>
      <directory>src/main/resources</directory>
      <filtering>true</filtering>
    </resource>
  </resources>
</build>
```

Build with a profile:

```bash
mvn clean package -P prod
```

Now `target/classes/config.properties` contains `environment=production`.

**✅ Checkpoint**: You can activate different configurations without touching source files.

## 🧱 LESSON 9: Multi-Module Projects (The Reactor)

This is the biggest leap. Multi-module builds are how real-world Java projects are structured.

**Step 9.1 — Create the parent**

```bash
mkdir my-app && cd my-app
```

Create `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.example</groupId>
  <artifactId>my-app</artifactId>
  <version>1.0.0</version>
  <packaging>pom</packaging>

  <modules>
    <module>core</module>
    <module>web</module>
  </modules>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.example</groupId>
        <artifactId>core</artifactId>
        <version>${project.version}</version>
      </dependency>
    </dependencies>
  </dependencyManagement>
</project>
```

**Step 9.2 — Create the `core` module**

```bash
mkdir -p core/src/main/java/com/example
```

`core/pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <parent>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
  </parent>
  <artifactId>core</artifactId>
</project>
```

`core/src/main/java/com/example/Greeter.java`:

```java
package com.example;

public class Greeter {
    public String greet(String name) {
        return "Hello, " + name + "!";
    }
}
```

**Step 9.3 — Create the `web` module that uses `core`**

```bash
mkdir -p web/src/main/java/com/example
```

`web/pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <parent>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
  </parent>
  <artifactId>web</artifactId>
  <dependencies>
    <dependency>
      <groupId>com.example</groupId>
      <artifactId>core</artifactId>
    </dependency>
  </dependencies>
</project>
```

`web/src/main/java/com/example/Main.java`:

```java
package com.example;

public class Main {
    public static void main(String[] args) {
        System.out.println(new Greeter().greet("Maven"));
    }
}
```

**Step 9.4 — Build the whole thing from the parent**

```bash
cd my-app
mvn clean install
```

Watch the reactor order: Maven builds `core` **before** `web` automatically because `web` depends on `core`. That's the **reactor**.

**✅ Checkpoint**: You can build a multi-module project and understand why module order matters.

## 🧱 LESSON 10: Advanced — BOM & Custom Plugin (Overview)

**BOM (Bill of Materials)** — a POM that only centralizes versions:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.2.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

After importing, you can declare Spring deps **without versions** — versions come from the BOM.

**Custom plugin** — create a project with `<packaging>maven-plugin</packaging>`, write a `Mojo` class extending `AbstractMojo`, implement `execute()`. This is advanced; tackle it after you're comfortable with the above.

**✅ Checkpoint**: You know where BOMs fit and can imagine writing a plugin when needed.
