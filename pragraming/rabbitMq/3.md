### 🐳 Step 1: The Production-Ready Docker Compose File

A simple RabbitMQ container is fine for a "Hello World," but a reliable setup requires **persistent storage**, **custom credentials** (the default `guest` user is restricted to localhost), and **resource limits**.

Create a file named `docker-compose.yml` in your project root:

```yaml
version: '3.8'

services:
  rabbitmq:
    image: rabbitmq:3.13-management # Includes the Management UI
    container_name: rabbitmq
    hostname: my-rabbit # Fixed hostname for consistent data persistence
    ports:
      - "5672:5672"   # AMQP protocol
      - "15672:15672" # Management UI
    environment:
      RABBITMQ_DEFAULT_USER: app
      RABBITMQ_DEFAULT_PASS: app_secret
      RABBITMQ_DEFAULT_VHOST: /app
      # Prevent RabbitMQ from consuming all host memory in containers
      RABBITMQ_VM_MEMORY_HIGH_WATERMARK: "0.6" # 60% limit
    volumes:
      - rabbitmq_data:/var/lib/rabbitmq # Persists queues, exchanges, and messages
    networks:
      - rabbitmq_net
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "check_port_connectivity"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  rabbitmq_data: # Named volume ensures data survives `docker compose down`

networks:
  rabbitmq_net:
    driver: bridge
```

**Key Details:**
*   **Persistent Volume (`rabbitmq_data`)**: Without this, all queues and messages are lost when the container stops.
*   **Fixed Hostname (`my-rabbit`)**: RabbitMQ uses the hostname as part of its node identifier. Changing it can make persisted data unreadable.
*   **Memory Watermark**: In containers, RabbitMQ can misjudge the host's memory. Setting an absolute limit (or a relative fraction) prevents OOM crashes.

Start the broker with:
```bash
docker compose up -d
```
Access the Management UI at `http://localhost:15672` with `app` / `app_secret`.

### 🔀 Step 2: Mastering Exchange Types (with Code)

Now that the broker is running, you can implement the four exchange types. The **Docker Compose network** allows your Java applications (whether running on the host or in other containers) to connect using the hostname `localhost` (if exposed) or the service name `rabbitmq` (if containerized together).

| Exchange Type | Routing Mechanism | Use Case |
| :--- | :--- | :--- |
| **Direct** | Exact routing key match | Task queues, point-to-point |
| **Fanout** | Broadcast to all bound queues | Notifications, cache invalidation |
| **Topic** | Pattern matching (`order.*.eu`) | Event filtering by region/severity |
| **Headers** | Matches on message header attributes | Complex routing rules |

**Spring Boot Implementation (Declaring Exchanges):**

```java
@Configuration
public class ExchangeConfig {

    // 1. Direct Exchange
    @Bean
    public DirectExchange directExchange() {
        return new DirectExchange("app.direct.exchange");
    }

    // 2. Fanout Exchange
    @Bean
    public FanoutExchange fanoutExchange() {
        return new FanoutExchange("app.fanout.exchange");
    }

    // 3. Topic Exchange
    @Bean
    public TopicExchange topicExchange() {
        return new TopicExchange("app.topic.exchange");
    }

    // 4. Headers Exchange
    @Bean
    public HeadersExchange headersExchange() {
        return new HeadersExchange("app.headers.exchange");
    }
}
```

**Pure Java Implementation (Publishing to a Topic Exchange):**

```java
Channel channel = connection.createChannel();
channel.exchangeDeclare("app.topic.exchange", BuiltinExchangeType.TOPIC);

// Routing key pattern: "order.created.eu"
String routingKey = "order.created.eu";
String message = "New order from Europe";
channel.basicPublish("app.topic.exchange", routingKey, null, message.getBytes());
```

### 🛡️ Step 3: Ensuring Delivery (Publisher Confirms & Returns)

A message is not truly sent until the broker **confirms** it has taken responsibility. Additionally, if a message cannot be routed to any queue, it should be **returned** to you rather than silently dropped.

**Spring Boot Configuration (`application.yml`):**

```yaml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: app
    password: app_secret
    virtual-host: /app
    publisher-confirm-type: correlated # Enables async confirms
    publisher-returns: true            # Enables returns for unroutable messages
    template:
      mandatory: true                  # Required for returns to fire
```

**Spring Boot Callback Implementation:**

```java
@Configuration
public class RabbitTemplateConfig {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void configureTemplate() {
        // Confirm Callback: Did the broker accept the message?
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                System.err.println("Message NACKed by broker. Cause: " + cause);
                // Implement retry logic or alerting here
            } else {
                System.out.println("Message confirmed by broker.");
            }
        });

        // Return Callback: Was the message routable to a queue?
        rabbitTemplate.setReturnsCallback(returned -> {
            System.err.println("Message returned (unroutable): " + returned);
            // Log, send to a parking queue, or alert
        });
    }
}
```

**Pure Java Implementation:**

```java
Channel channel = connection.createChannel();
channel.confirmSelect(); // Enable publisher confirms

// Listen for confirms
channel.addConfirmListener(
    (sequenceNumber, multiple) -> System.out.println("Confirmed: " + sequenceNumber),
    (sequenceNumber, multiple) -> System.err.println("Nacked: " + sequenceNumber)
);

// Listen for returns
channel.addReturnListener(returned -> 
    System.err.println("Returned: " + returned.getReplyText())
);

// Publish with the `mandatory` flag set to true
channel.basicPublish("app.direct.exchange", "bad.routing.key", true, null, "Test".getBytes());
```

### ⚙️ Step 4: Consumer Reliability (Manual Ack & Prefetch)

Auto-acknowledgment is dangerous because a message is lost if the consumer crashes mid-processing. **Manual acknowledgment** gives you control, while **prefetch** prevents a consumer from being overwhelmed.

**Spring Boot Configuration (`application.yml`):**

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 10 # Fetch up to 10 unacknowledged messages at a time
```

**Spring Boot Listener with Manual Ack:**

```java
@Component
public class ReliableConsumer {

    @RabbitListener(queues = "app.direct.queue")
    public void handleMessage(
            String message,
            @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
            Channel channel) throws IOException {

        try {
            // ... business logic ...
            System.out.println("Processed: " + message);
            channel.basicAck(deliveryTag, false); // Success
        } catch (RetryableException e) {
            // Requeue for another attempt
            channel.basicNack(deliveryTag, false, true);
        } catch (Exception e) {
            // Reject without requeue (will go to DLQ if configured)
            channel.basicNack(deliveryTag, false, false);
        }
    }
}
```

**Pure Java Implementation:**

```java
channel.basicQos(10); // Prefetch limit

channel.basicConsume("app.direct.queue", false, (consumerTag, delivery) -> {
    long tag = delivery.getEnvelope().getDeliveryTag();
    try {
        // ... process ...
        channel.basicAck(tag, false);
    } catch (Exception e) {
        channel.basicNack(tag, false, true); // Requeue on failure
    }
}, consumerTag -> {});
```

### 🪦 Step 5: Handling Failures (Dead Letter Queue)

A **Dead Letter Exchange (DLX)** catches messages that are rejected (with `requeue=false`), expire, or exceed queue length limits. The Docker Compose setup is unchanged; the DLX is configured at the application level.

**Spring Boot DLQ Configuration:**

```java
@Configuration
public class DlqConfig {

    public static final String PRIMARY_QUEUE = "app.primary.queue";
    public static final String DLQ = "app.dead.letter.queue";
    public static final String DLX = "app.dlx.exchange";

    @Bean
    public Queue primaryQueue() {
        return QueueBuilder.durable(PRIMARY_QUEUE)
                .deadLetterExchange(DLX)
                .deadLetterRoutingKey("dlq.key")
                .build();
    }

    @Bean
    public Queue deadLetterQueue() {
        return QueueBuilder.durable(DLQ).build();
    }

    @Bean
    public DirectExchange deadLetterExchange() {
        return new DirectExchange(DLX);
    }

    @Bean
    public Binding dlqBinding() {
        return BindingBuilder.bind(deadLetterQueue())
                .to(deadLetterExchange())
                .with("dlq.key");
    }
}
```

**Pure Java DLQ Declaration:**

```java
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "app.dlx.exchange");
args.put("x-dead-letter-routing-key", "dlq.key");

channel.queueDeclare("app.primary.queue", true, false, false, args);
```

A powerful pattern is to add a **listener on the DLQ** that implements a retry limit before moving the message to a final "parking lot" queue for manual inspection.

### 💎 Summary: How It All Fits Together

| Layer | Component | Role in the Docker Compose Stack |
| :--- | :--- | :--- |
| **Infrastructure** | RabbitMQ container | Provides the broker, Management UI, and persistent volume. |
| **Routing** | Exchanges | Directs messages based on keys or headers. |
| **Producer Reliability** | Confirms & Returns | Ensures the broker accepted the message and it was routable. |
| **Consumer Reliability** | Manual Ack & Prefetch | Prevents message loss on consumer failure and controls flow. |
| **Failure Handling** | DLX / DLQ | Captures and isolates messages that cannot be processed. |

With this Docker Compose foundation, you can now run both your Spring Boot and pure Java applications against the same broker, observing the behavior of confirms, manual acks, and DLQs in real time through the Management UI.
