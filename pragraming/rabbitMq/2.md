Building on the basics, the next crucial step is moving from "Hello World" to building **reliable, production-ready messaging systems**. This involves understanding how messages are routed, ensuring they are not lost, and handling failures gracefully.

Here is a guide to the advanced concepts and their implementation in Spring Boot and pure Java.

---

### 🔀 1. Mastering Exchange Types: Routing Strategies

Exchanges are the core of RabbitMQ's routing. Choosing the right type is fundamental to your system's architecture.

| Exchange Type | Routing Mechanism | Common Use Case | When to Use |
| :--- | :--- | :--- | :--- |
| **Direct** | Exact routing key match | Task queues, point-to-point messaging | Simple, explicit routing where each message type has a specific destination. |
| **Fanout** | Broadcast to all bound queues (ignores routing key) | Notifications, cache invalidation, logging | When multiple consumers all need to receive the same message (publish/subscribe). |
| **Topic** | Pattern matching on routing key (e.g., `order.*.eu`) | Event filtering, log routing (e.g., by severity or region) | Complex, hierarchical routing where consumers subscribe to subsets of messages. |
| **Headers** | Matches on message header attributes | Complex routing rules where the routing key is insufficient | Edge cases where routing must be based on multiple attributes rather than a single key string. |

**Implementation Note:** The **Default Exchange** (an empty string `""`) is a direct exchange to which every queue is automatically bound by its name. This is why in the "Hello World" example, you could publish directly to a queue name.

---

### 🛡️ 2. Ensuring Delivery: Publisher Confirms & Returns

A common pitfall is assuming a message was sent successfully just because no exception was thrown. RabbitMQ provides two mechanisms for producers to verify delivery.

*   **Publisher Confirms**: The broker acknowledges that it has **taken responsibility** for the message. This is an asynchronous confirmation from the exchange.
*   **Publisher Returns**: If a message is **routable to an exchange but not to any queue** (e.g., due to a bad routing key), the broker will return it to the producer. This is only triggered if the `mandatory` flag is set on the message.

#### In Spring Boot
You enable these features in your `application.yml`:
```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true # Important: needed for returns to work
```
Then, you configure the callbacks on the `RabbitTemplate` bean:
```java
@Configuration
public class RabbitMQConfig {
    @Autowired
    private RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void configureTemplate() {
        // Confirm callback: Is the message accepted by the exchange?
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                System.err.println("Message not confirmed by broker. Cause: " + cause);
                // Implement retry or alerting logic here
            }
        });

        // Return callback: Was the message routable to a queue?
        rabbitTemplate.setReturnsCallback(returned -> {
            System.err.println("Message returned: " + returned);
            // Handle unroutable messages (e.g., log, send to a parking queue)
        });
    }
}
```

#### In Pure Java
You use the `confirmSelect()` method on the channel and add listeners:
```java
Channel channel = connection.createChannel();
channel.confirmSelect(); // Enable publisher confirms

// Async confirm listener
channel.addConfirmListener((sequenceNumber, multiple) -> {
    System.out.println("Message confirmed: " + sequenceNumber);
}, (sequenceNumber, multiple) -> {
    System.err.println("Message nacked: " + sequenceNumber);
});

// Return listener (for unroutable messages)
channel.addReturnListener(returnedMessage -> {
    System.err.println("Message returned: " + returnedMessage);
});

// Publish with mandatory flag set to true
channel.basicPublish("exchange", "bad.key", true, null, message.getBytes());
```

### ⚙️ 3. Consumer Reliability: Manual Acknowledgment & Prefetch

By default, RabbitMQ uses **auto-acknowledgment**, meaning it considers a message delivered as soon as it's sent to a consumer. If the consumer crashes, the message is lost. **Manual acknowledgment** is essential for reliability.

When `acknowledge-mode` is set to `manual`, you must explicitly tell the broker the outcome of processing:

*   **`basicAck(deliveryTag, multiple)`**: Message processed successfully.
*   **`basicNack(deliveryTag, multiple, requeue)`** or **`basicReject`**: Message processing failed.
    *   `requeue = true`: The message is put back in the queue for another attempt.
    *   `requeue = false`: The message is discarded or, more usefully, routed to a Dead Letter Queue (if configured).

**Prefetch (QoS)** works with manual ack to control flow. It limits how many unacknowledged messages a consumer can have at once, preventing it from being overwhelmed.

#### In Spring Boot
Configure in `application.yml`:
```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 10 # Consumer will fetch up to 10 messages at a time
```
In your listener, inject the `Channel` and `deliveryTag` to manually acknowledge:
```java
@RabbitListener(queues = "my.queue")
public void handleMessage(MyMessage message,
                          @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag,
                          Channel channel) throws IOException {
    try {
        // ... business logic ...
        channel.basicAck(deliveryTag, false); // Success
    } catch (RetryableException e) {
        channel.basicNack(deliveryTag, false, true); // Requeue for retry
    } catch (Exception e) {
        channel.basicNack(deliveryTag, false, false); // Send to DLQ (if configured)
    }
}
```

#### In Pure Java
You must turn off auto-ack when starting the consumer (`autoAck = false`) and manage the ack in your callback:
```java
channel.basicConsume("my.queue", false, (consumerTag, delivery) -> {
    long deliveryTag = delivery.getEnvelope().getDeliveryTag();
    try {
        // ... business logic ...
        channel.basicAck(deliveryTag, false);
    } catch (Exception e) {
        channel.basicNack(deliveryTag, false, true); // Requeue on failure
    }
}, consumerTag -> {});
```

### 🪦 4. Handling Failures: Dead Letter Queues (DLQ)

A **Dead Letter Exchange (DLX)** and its bound **DLQ** are where messages are sent when they are "dead-lettered." This happens when:
1.  A message is **rejected** (`basicNack` or `basicReject`) with `requeue=false`.
2.  A message **expires** due to a TTL (Time-To-Live) setting.
3.  The queue length limit is **exceeded**.

#### In Spring Boot
You configure the DLX on the primary queue using `QueueBuilder`:
```java
@Bean
public Queue primaryQueue() {
    return QueueBuilder.durable("primary.queue")
            .deadLetterExchange("dlx.exchange")
            .deadLetterRoutingKey("dlx.key")
            .build();
}

@Bean
public Queue deadLetterQueue() {
    return QueueBuilder.durable("dead.letter.queue").build();
}

@Bean
public DirectExchange deadLetterExchange() {
    return new DirectExchange("dlx.exchange");
}

@Bean
public Binding dlqBinding() {
    return BindingBuilder.bind(deadLetterQueue())
            .to(deadLetterExchange())
            .with("dlx.key");
}
```
A powerful pattern is to have a listener on the DLQ that implements a retry limit before moving the message to a final "parking lot" queue.

#### In Pure Java
You declare the queue arguments when creating the queue:
```java
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "dlx.exchange");
args.put("x-dead-letter-routing-key", "dlx.key");
channel.queueDeclare("primary.queue", true, false, false, args);
```

### 💎 Summary and Next Steps

You now have the tools to build a robust messaging system: **correct routing** (exchanges), **producer reliability** (confirms/returns), **consumer reliability** (manual ack + prefetch), and **failure handling** (DLQ).

A natural next step would be to explore **message persistence** (marking queues as `durable` and messages as `PERSISTENT`) and designing **idempotent consumers** to handle the possibility of duplicate message delivery, which can occur in any at-least-once delivery system.
