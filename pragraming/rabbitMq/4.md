Moving beyond reliability primitives, the next step is designing systems that are **resilient to failure and duplicates**. This covers surviving broker restarts, handling duplicate deliveries safely, and controlling the order in which messages are processed.

### 💾 Step 6: Message Persistence & Quorum Queues

Publisher confirms guarantee the broker *received* a message. Persistence guarantees it survives a broker **restart or crash**. This requires **three things to align**: a durable exchange, a durable queue, and a persistent message.

**The Three Pillars of Persistence**

| Layer | Configuration | Why It Matters |
| :--- | :--- | :--- |
| **Exchange** | `durable=true` | The routing metadata survives a broker restart. |
| **Queue** | `durable=true` | The queue definition and its messages survive a restart. |
| **Message** | `deliveryMode = PERSISTENT` (2) | The message body is written to disk, not just memory. |

**Spring Boot: Durable Queue & Persistent Message**

Spring AMQP declares exchanges and queues as durable by default when using `QueueBuilder.durable()`. For the **message itself**, you must set the delivery mode explicitly, typically via a `MessagePostProcessor` so it applies to every send.

```java
@Configuration
public class PersistenceConfig {

    // Durable queue (and quorum queue discussed below)
    @Bean
    public Queue durableQueue() {
        return QueueBuilder.durable("persistent.queue").build();
    }

    // Configure the template to make every message persistent
    @Bean
    public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);
        template.setBeforePublishPostProcessors(message -> {
            message.getMessageProperties()
                   .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
            return message;
        });
        return template;
    }
}
```

**Pure Java: Persistent Message**

```java
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
        .deliveryMode(2) // 2 = PERSISTENT
        .build();
channel.basicPublish("exchange", "key", props, message.getBytes());
```

**Upgrading to Quorum Queues for High Availability**

For production, **quorum queues** are the recommended durable queue type. They replicate data across multiple RabbitMQ nodes using the Raft consensus algorithm, protecting against single-node failure.

In Spring Boot, declare a quorum queue by chaining `.quorum()`:

```java
@Bean
public Queue quorumQueue() {
    return QueueBuilder.durable("orders.processing")
            .quorum() // Forces durable=true and disables exclusive/auto-delete
            .build();
}
```

> **Important**: Your RabbitMQ cluster must have **at least 3 nodes** for quorum queues to function correctly. The single-node Docker Compose setup from earlier is sufficient for learning, but production requires a cluster.

### 🔁 Step 7: Idempotent Consumers (Handling Duplicates)

In any at-least-once delivery system, duplicates are inevitable. A consumer may process a message successfully but crash **before** sending the `basicAck`. When it restarts, the broker redelivers the message. The solution is to make the consumer **idempotent**: processing the same message twice should have the same effect as processing it once.

**The Standard Pattern: Deduplication Key**

1.  The producer assigns a **globally unique `messageId`** to every message.
2.  The consumer checks if this `messageId` has been seen before (in Redis, a database, or a local cache).
3.  If it is new, process the message and **atomically record** the `messageId`.
4.  If it already exists, **acknowledge and discard** the duplicate.

**Producer: Injecting a Unique `messageId`**

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    converter.setCreateMessageIds(true); // Auto-generates a UUID per message
    return converter;
}
```

**Consumer: Idempotency Check with Redis**

A common and performant approach is to use Redis `SETNX` (set-if-not-exists) with a TTL.

```java
@Service
public class IdempotentConsumer {

    private final StringRedisTemplate redisTemplate;

    public IdempotentConsumer(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    @RabbitListener(queues = "persistent.queue")
    public void consume(Message message, Channel channel,
                         @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        String messageId = message.getMessageProperties().getMessageId();

        // SETNX with a 24-hour TTL: returns true only if the key was newly set
        Boolean isNew = redisTemplate.opsForValue()
                .setIfAbsent("msg:id:" + messageId, "1", Duration.ofHours(24));

        if (Boolean.FALSE.equals(isNew)) {
            System.out.println("Duplicate detected, skipping: " + messageId);
            channel.basicAck(tag, false); // Acknowledge without processing
            return;
        }

        try {
            // ... business logic ...
            channel.basicAck(tag, false);
        } catch (Exception e) {
            // If processing fails, remove the idempotency key so a retry can proceed
            redisTemplate.delete("msg:id:" + messageId);
            channel.basicNack(tag, false, true);
        }
    }
}
```

> **Database alternative**: If Redis is unavailable, a **unique index** on a `processed_messages` table provides the same guarantee. Insert the `messageId` in the same transaction as the business logic; a `DuplicateKeyException` indicates a duplicate.

### ⏳ Step 8: Delayed Retry with TTL + Dead Letter Queue

A simple `basicNack` with `requeue=true` causes an **immediate** redelivery, which can hammer a failing consumer in a tight loop. A **delayed retry** pattern inserts a controlled wait between attempts.

**How It Works**

1.  The primary queue rejects the message **without requeue** (`requeue=false`).
2.  The message is dead-lettered to a **retry queue** that has a **TTL** (Time-To-Live).
3.  When the TTL expires, the message is dead-lettered **again**, back to the primary queue.
4.  After a maximum number of retries, the message is routed to a final **parking lot DLQ** for human inspection.

**Spring Boot Configuration**

```java
@Configuration
public class RetryDlqConfig {

    public static final String PRIMARY_QUEUE = "retry.primary.queue";
    public static final String RETRY_QUEUE   = "retry.delay.queue";
    public static final String PARKING_QUEUE = "retry.parking.queue";

    // Primary queue: on rejection, send to the retry (delay) queue
    @Bean
    public Queue primaryQueue() {
        return QueueBuilder.durable(PRIMARY_QUEUE)
                .deadLetterExchange("")
                .deadLetterRoutingKey(RETRY_QUEUE)
                .build();
    }

    // Delay queue: TTL of 5 seconds, then dead-letter back to the primary queue
    @Bean
    public Queue retryQueue() {
        return QueueBuilder.durable(RETRY_QUEUE)
                .ttl(5000) // 5-second delay
                .deadLetterExchange("")
                .deadLetterRoutingKey(PRIMARY_QUEUE)
                .build();
    }

    @Bean
    public Queue parkingQueue() {
        return QueueBuilder.durable(PARKING_QUEUE).build();
    }
}
```

**Consumer with Retry Count Tracking**

Use the `x-death` header (RabbitMQ's built-in dead-letter counter) to decide when to stop retrying.

```java
@RabbitListener(queues = RetryDlqConfig.PRIMARY_QUEUE)
public void consume(String message, Channel channel,
                    @Header(AmqpHeaders.DELIVERY_TAG) long tag,
                    @Header(name = "x-death", required = false) List<Map<String, Object>> xDeath)
        throws IOException {

    long retryCount = 0;
    if (xDeath != null) {
        retryCount = ((Number) xDeath.get(0).get("count")).longValue();
    }

    try {
        // ... business logic ...
        channel.basicAck(tag, false);
    } catch (Exception e) {
        if (retryCount < 3) {
            // Reject -> goes to retry queue (5s delay) -> back to primary
            channel.basicNack(tag, false, false);
        } else {
            // Exhausted retries -> route to parking queue for manual review
            channel.basicPublish("", RetryDlqConfig.PARKING_QUEUE, null,
                    message.getBytes());
            channel.basicAck(tag, false);
        }
    }
}
```

> **Caveat — Head-of-Line Blocking**: With a **single** TTL queue, RabbitMQ's FIFO nature means a message at the **head** with a long TTL blocks later messages with shorter TTLs from expiring. For precise per-message delays, use the `rabbitmq_delayed_message_exchange` plugin instead.

### 🎯 Step 9: Priority Queues

When some messages are objectively more urgent than others (e.g., high-value customer orders), a **priority queue** ensures they jump ahead of lower-priority messages already waiting.

**Configuration**: Set `x-max-priority` on the queue, and assign a `priority` on each message.

```java
@Bean
public Queue priorityQueue() {
    return QueueBuilder.durable("priority.queue")
            .maxPriority(10) // Allowed range: 0–255; avoid very high values (CPU/memory cost)
            .build();
}
```

**Sending with a Priority**

```java
public void sendWithPriority(String message, int priority) {
    rabbitTemplate.convertAndSend("priority.queue", message, msg -> {
        msg.getMessageProperties().setPriority(priority);
        return msg;
    });
}
```

**Pure Java**

```java
Map<String, Object> args = new HashMap<>();
args.put("x-max-priority", 10);
channel.queueDeclare("priority.queue", true, false, false, args);

AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
        .priority(9) // Higher number = consumed first
        .build();
channel.basicPublish("", "priority.queue", props, message.getBytes());
```

> **Best practice**: Keep `x-max-priority` small (10 is typical). A large range increases RabbitMQ's internal sorting overhead without practical benefit.

### 🔄 Step 10: RPC (Request-Reply) over RabbitMQ

Although RabbitMQ is fundamentally asynchronous, Spring AMQP provides a clean abstraction for **synchronous RPC** using the `convertSendAndReceive` method.

**How It Works**: Spring automatically creates a **callback queue** for the client, sets the `replyTo` and `correlationId` message properties, and matches the response back to the correct request.

**Client (Synchronous Call)**

```java
@Service
public class RpcClient {

    private final RabbitTemplate rabbitTemplate;

    public RpcClient(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    public Integer getFibonacci(int n) {
        // Blocks until the server responds (or times out)
        Integer result = (Integer) rabbitTemplate.convertSendAndReceive(
                "rpc.exchange", "rpc.fib", n);
        return result;
    }
}
```

**Server (Listener that Returns a Value)**

```java
@RabbitListener(queues = "rpc.fib.queue")
public Integer computeFibonacci(int n) {
    // The return value is automatically sent back to the client's callback queue
    return fib(n);
}

private int fib(int n) {
    return n <= 1 ? n : fib(n - 1) + fib(n - 2);
}
```

> **Use RPC sparingly**. As the RabbitMQ tutorial notes, RPC can make an asynchronous system feel synchronous and introduce hidden coupling. Prefer **async pipelines** (events with separate response queues) when the result is not needed immediately.

### 🐳 Step 11: Spring Boot Docker Compose Support (Dev Convenience)

You already have a `docker-compose.yml`. Spring Boot 3.1+ can **automatically detect and start it** when your application runs, removing the need to manually run `docker compose up` during development.

**1. Add the Dependency**

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-docker-compose</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
```

**2. Keep Your `docker-compose.yml` in the Project Root**

When you run the Spring Boot application:
- Spring Boot searches for `compose.yml` / `docker-compose.yml`.
- It runs `docker compose up` automatically.
- It creates a `ConnectionDetails` bean pointing to the RabbitMQ container, so you can **remove** `spring.rabbitmq.host/port/username/password` from `application.yml` (they are auto-configured).
- On shutdown, it runs `docker compose stop`.

> **Remove this dependency before deploying to production**; it is a development-only convenience.

### 💎 Summary: What You Can Now Build

| Pattern | Problem It Solves | Key Mechanism |
| :--- | :--- | :--- |
| **Persistence + Quorum** | Broker restart loses messages | `durable` + `deliveryMode=2` + `.quorum()` |
| **Idempotency** | Duplicate delivery causes double-processing | Unique `messageId` + Redis `SETNX` / DB unique index |
| **Delayed Retry + DLQ** | Immediate requeue hammers a failing consumer | TTL retry queue + `x-death` count + parking queue |
| **Priority Queue** | Urgent messages wait behind bulk messages | `x-max-priority` + per-message `priority` |
| **RPC** | Synchronous request-response over an async broker | `convertSendAndReceive` + `replyTo`/`correlationId` |

A natural next topic would be the **Outbox Pattern** for guaranteeing that a database write and a message publish happen atomically—a common requirement when RabbitMQ is part of a larger transactional workflow.
